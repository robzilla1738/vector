# Persistent Aux backup runner — prepared, inactive

These are executable local operator artifacts for the [reviewed dedicated runner](../../../../docs/cloud/dedicated-backup-runner-review/README.md), not an installed or operating backup service. No server, schedule, monitor, credential or source connection is created by this directory. They preserve the payment-free desktop and backend launch policy.

## What the wrapper does

`node scripts/cloud-backup-runner.mjs capture /etc/aux-backup/runner-review.json` creates one persistent intent, invokes the existing current-schema online capture/local delivery CLI, authenticates its exact job and frozen ciphertext, then delivers and hash-verifies R2. Seven-day retention comes from the authenticated existing capture manifest. R2 recipient/budget comes from the reviewed runner JSON; every remote review is bound to the actual authenticated inventory hash, job and bundle.

`expiry` runs hourly, authenticates retained inventory, deletes remote completion marker first and the exact remaining remote set, then expires the matching local ciphertext. Already fully expired jobs are skipped. Metadata/status/inode bindings remain for review. A separate operator `resume REVIEW_JSON JOB_ID` retries the exact pending capture's ciphertext only; `resume-expiry REVIEW_JSON` retries the exact retained expiry job set. Neither recaptures source data.

One mode0700 persistent filesystem contains **three separate roots**, with one shared process-independent runner lock plus the existing job locks. Mode0600 owned review/intent files are required. An existing lock, partial capture, unknown remote result, changed directory, inconsistent status/inventory, new unexpected file, changed frozen job set, missing keys, expired credential, low disk reserve or bound violation stops the operation. The active intent survives process death and suppresses automatic recapture/deletion retries. There is no automatic stale-lock deletion, PID-only custody assertion, remote overwrite, orphan purge or source credential rotation. A failed fresh capture can require manual disposal/review because the current format deliberately cannot resume a half-created database snapshot.

Daily capture requires free space of at least four times the capture budget plus 1 GiB. The default byte cap is 1 GiB; this is a budget/refusal boundary, not evidence that every production workload fits. A maximum of366 retained job directories bounds metadata scanning. Plan a reviewed archival/retirement process for fully expired metadata before that limit; do not delete/move unfinished inode-bound jobs or change the maximum blindly.

## Installation preparation after approval

1. Provision only the separately approved dedicated resource/admin key/IP scope. Use Ubuntu24.04, reviewed Node24 and PostgreSQL18 client binaries. This source assumes `/usr/bin/node`, `/usr/bin/pg_dump` and `/usr/bin/pg_restore`; check the actual version/path, change the reviewed env file if needed, and pin package versions. No installation/provisioning script is executed here.
2. Install the exact reviewed repository commit and frozen dependency lock into a root-owned, service-unwritable `/opt/aux-backup/releases/<commit>`, install service dependencies including the pinned S3 operator SDK with `pnpm install --frozen-lockfile --ignore-scripts`, then point `/opt/aux-backup/current` to that exact release. Never use a moving branch or unattended code pull. Keep enough preceding code for rollback.
3. Create the non-login `aux-backup` user/group. Create `/etc/aux-backup` owned by root mode0750 with group `aux-backup`, and `/var/lib/aux-backup/{jobs,delivery,control}` owned by `aux-backup:aux-backup`, each mode0700. These directories must be on the same persistent filesystem. Keep source/temp archives on the unit's private temp disk; budget includes archive and ciphertext duplication.
4. Through the approved secret-manager/admin flow only, install `production.env` root-owned mode0600 and `recovery.key` owned by `aux-backup` mode0600. Key contents are the existing32-byte recovery key as64hex characters, not a new key. Do not put the general1Password Agents service-account token on the server. Copy the review example to `runner-review.json`, owner `aux-backup`, mode0600; use the exact Aux Cloudflare account, actual credential deadline and reviewed persistent paths. Leave `enabled:false` until that exact source connection/activation is approved. Do not put keys in unit files, argv, Git or journal.
5. Prepare **three** free-tier Healthchecks checks, all independently owned by Aux: daily capture (26-hour period, 2-hour grace), hourly expiry (1-hour period, 30-minute grace), daily credential check (26-hour period, 2-hour grace). The third check warns beginning seven days before credential expiry; existing credential expires **November22, 2026**. Confirm the actual provider expiry/time and update the review explicitly—do not infer automatic extension. Each ping URL is secret. Configure the owner-approved recipient and verify alert delivery directly; no alert is enrolled by these files.
6. Copy the template and three timer units into `/etc/systemd/system`, and run `systemd-analyze verify` on the actual Linux host. Run `systemctl daemon-reload` only under the installation approval. **Do not enable/start the timers yet.** Review all runtime bounds and file permissions first. No public listener/DNS/port5432 is needed; approved SSH allowlist remains separate.
7. After concrete source access and activation approval, set the exact reviewed config `enabled:true`, accept one bounded scheduled output/remote readback, one known failure alert and one missed-success alert, then enable the three timers. Startup `Persistent=true` catches a missed schedule but never overrides a retained unknown-outcome intent or lock. Systemd has `Restart=no`, a two-hour runtime cap, private temp, no privileges/capabilities, fixed memory/task limits and control-group termination.

Changing root-owned `production.env` requires an administrator. The service process can read the necessary production DB/Blob/wrapping key, scoped R2 key and monitor URLs. Secret environment values are inherited by its children; core-dump/log access must remain disabled/restricted by the host. Environment storage is not an independently protected hardware secret vault.

## Rotation and alert handling

The credential checker sends a start/success heartbeat while the R2 credential is more than seven days from expiry. At the warning threshold it sends failure and exits nonzero. Capture/expiry refuse at actual expiry. A warning is **not** automatic renewal and does not establish delivered email; the independent monitor detects missing successes if the host dies or the ping request fails.

For renewal: stop timers and the owned services; preserve active intents/locks and inspect uncertainty first. Create only a newly approved bucket-scoped replacement key through the owner dashboard; store it in1Password Aux Recovery and the private runner env, update `credentialExpiresAt` to the verified actual deadline. Run the bounded exact-job verify/recovery acceptance under that approval, then revoke only the old runner-specific credential. Never rotate `AUX_DATA_ENCRYPTION_KEY` or the owner recovery key as part of R2 renewal. Retained ciphertext keeps its original authenticated deadline and key requirement.

For a stopped job: disable timers, inspect unit/control-group closure and retained mode0600 records locally without printing source credentials/content. An empty stale lock may be removed **only after** the operator proves no process can write that state; do not infer from an absent PID. If `active.json` names a capture and exactly one new authenticated job exists, use `resume` with that exact UUID. If it names expiry, use `resume-expiry` with the unchanged job set. A capture with no authenticated inventory cannot be resumed; keep it for a separately reviewed disposition, and do not auto-start another capture. No wrapper command clears arbitrary intents/locks or deletes job metadata.

Rollback disables timers/stops owned units but retains state, key and remote ciphertext. Restoring the prior code must retain persistent inode bindings and pending intents. Destruction, key revocation, uncertain-job cleanup and moving unfinished jobs to a new server require their own safe disposition. Fetch/restore still uses the existing independent `cloud-backup-fetch.mjs` and isolated restore CLI. Owner emergency key retrieval remains an explicit acceptance step; a successful service read is not that proof.

## Verification boundary

Focused no-network fixtures exercise actual encrypted/HMAC job creation, failed capture with no recapture, exact-job resume, R2 unknown-outcome retention, marker-first expiry and manual expiry resume with an in-memory transport. They are not a scheduled production backup, Linux unit validation, monitor delivery, restore drill or RPO/RTO measurement. Reuse the existing hosted current-schema restore and live R2 evidence rather than repeating unchanged broad drills.
