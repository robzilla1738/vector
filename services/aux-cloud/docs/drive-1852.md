# Actual1852 Drive compatibility

The packaged daemon is the pinned SEA code SHA256 `5e35dfa1eb76d4614246f954b652fd505e271a0b3f1ac3168132fb8bc03814f5`. The Downloads extracted index SHA9012 belongs to a different implementation shape and its object/head adapter remains archival, not suitable for this build.

Apply migration009-drive-1852 after008, mount `drive1852Routes` after authenticated `requireUser`, and route `/drive/*` through the existing Next API handler/custom CAS header normalizer. This preserves the actual per-file hash CAS implementation; it does not add putRemoteHead or change the original merge algorithm.

- GET `/drive/head`: `{formatVersion:2,files:[{path,sha256,size,objectSha256,objectSize,encryption:'aes-256-gcm',generation}]}` plus global revision ETag. Cold native metadata caches omit If-None-Match. Original `agentFileHeadSchema` receives its original formatVersion2 plaintext metadata projection; encrypted transport metadata stays in a user/account/generation-scoped map.
- PUT `/drive/files?path=...`: `{entry:<head entry>,object:<base64 AES-GCM envelope bytes>}`. Exactly one per-file plaintext-hash If-Match ETag or creation If-None-Match:* is required. Native writes use X-Aux-If-Match/X-Aux-If-None-Match, normalized inside Hono to avoid Vercel304-on-PUT behavior. The original retry loop and conflict merger remain intact.
- GET `/drive/files?path=...`: owner-scoped ciphertext envelope bytes. Native downloads verify ciphertext hash/size, AES-GCM owner/path/generation AAD, then original plaintext hash/size before returning bytes to the original merge algorithm.
- DELETE `/drive/files?path=...`: requires expected plaintext-hash ETag, refuses stale deletion and advances the head revision.

Only encrypted envelopes are accepted, including credentials.json. The existing actual account CSK and original wrapped-key/HKDF formats remain unchanged. AAD is the existing Aux transport context `['aux.agent-file.v1',userUuid,path,generation]`. Backend stores private ciphertext in Postgres bytea, not a public URL. Limits are2MiB plaintext per file,3MiB ciphertext per object,1000 files and64MiB total ciphertext per account. Mutations serialize under the existing owner advisory lock, validate account generation and update head revision in the same transaction. This is an initial bounded private storage adapter, not unlimited storage.

`applyCloudDrive1852Adapter(source,{branding:'aside'|'aux'})` has nine checked anchors, verified against both the pinned original and actual shipped static Aux index. Compose before `applyCloudSessionAdapter(source,{version:'1852',branding:'aux'})`; the latter has four anchors and retains the original waiting/coder projection in session previews. The attachment adapter's four anchors match actual1852; root must explicitly transform helper API/error/base URL symbols to Aux when composing it. Neither adapter changes UI or executes during staging.

Focused fixtures verify both actual-source compositions, authenticated encrypted upload/download mapping, malformed/hash/size/plaintext rejection, and actual1852 original JSONL writer/turn-reducer historical restoration. `scripts/check-drive-1852-db.ts` is gated to the reviewed development Neon endpoint and uses synthetic fixture owners plus generated fixture encryption keys; it verifies real SQL storage/ownership, conditional writes and deletion, then cleans only its fixture users. The agent has not run it or activated modified desktop bytes.

Apply010-drive-cookies for encrypted cookie upload/storage/delete through the existing drive1852Routes mount. Plaintext cookies remain rejected. Cookie upload uses the actual account CSK and AES-GCM with AAD `['aux.cookie-snapshot.v1',userUuid,generation]`; no HKDF or wrapped-key domain changes occur. The original one-way consumer still captures and filters cookies through its original CDP path; the two extra checked anchors encrypt before its original PUT and conditionally delete on its original clear action. The server validates authenticated generation, envelope/hash/size, revision CAS and capture ordering, stores ciphertext only and exposes owner-scoped metadata for CAS. Limits are2MiB plaintext and3MiB ciphertext; oversized captures remain local with an explicit failure. Deletion clears ciphertext and retains a monotonic revision tombstone, preventing stale ETag ABA after recreation. The gated check-drive-cookies-db fixture uses synthetic cookie values only and verifies stored ciphertext, ownership, CAS, capture order and delete/recreate behavior. The actual supplied encodeCookies function says CSK encryption is not implemented and emits encryption:none; the only cookie sync consumer uploads Storage.getCookies. No decodeCookies/getRemoteCookies/restoreCookies or Storage.setCookies/Network.setCookies consumer exists in this pinned daemon. Full cookie restore therefore cannot be claimed from a successful encrypted upload. Encrypted upload/storage/delete is implemented; cross-device cookie restoration remains an explicit missing native integration, not merely an untested button.

Encrypted retrieval prerequisite: `GET /drive/cookies/object?generation=N` requires the exact metadata revision in `If-Match`. It returns only the authenticated owner's binary ciphertext at that revision/current key generation, rechecks stored object hash/size and preserves no-store behavior. The explicit `X-Aux-Cookie-Revision` response header must match the requested metadata revision; ETag is retained for compatibility, but deployment transport can rewrite it. Missing preconditions fail428, stale revision/generation fails412, and another owner's/deleted backup is unavailable404. The real-Neon fixture verifies this path and race refusal; `scripts/check-cookie-export.mts` is the separately gated deployed HTTP check. This route does not perform native cookie import. The bounded native source trace and remaining profile-routing requirements are recorded in `docs/integration/proposed/cloud-cookie-restore/` at the workspace root. Current desktop/cloud signing candidate bytes are unchanged.
