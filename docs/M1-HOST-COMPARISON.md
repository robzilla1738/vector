# M1 browser-host comparison — September 24, 2026

This decision compares **current Aux code and its real shell**, not historical screenshots or an extracted competitor design. Run `pnpm --filter @aux/desktop build` then `pnpm host:compare` from the repository root. The bounded runner writes `release/test-artifacts/aux-host-comparison.json` with the source commit, timed commands, full last output, and fresh API probe results. It exits nonzero on a failed or timed-out command. All profiles and sites in the run are disposable fixtures. The artifact is local test output, not a release certificate.

## Decision

**Adopt a Chromium `//chrome` fork as Aux's intended architecture, subject to the remaining candidate compatibility and UI proof.** Keep Electron as the usable preview host while the fork is qualified. Electron's real Aux layout and agent path work, yet its documented Store-extension ceiling and measured missing APIs fail a mandatory 1.0 gate. The pinned CEF Chrome-layer prototype failed Cmd+T inside Aux's shell by opening a stock Chrome window. Preserve Aux's current design in the fork. This is an architecture direction, not a migration or release approval: no Aux candidate has passed the live Store, shell, signed 1Password, Store update, real passkey/SSO, signed update, or upstream security-rebase gates.

The final host commitment depends on evidence. If the fork cannot keep Aux's two layouts and agent/Profile boundary while handling real extensions, revisit the architecture and retain the working Electron preview. A Google Chrome for Testing reference process is useful as an API control, but it is **not** a running Aux fork. The fork is not presumed faster; foreground speed must be measured in the actual Aux candidate against the current host.

### Current run and limitations

The original September 24 run against source `b1db5bed` passed eight commands. The latest current-source runner includes **eleven** commands, adding two regular Profiles, native tab placement and functional native messaging; its exact source SHA and timing are in the local artifact. It used Electron 43.6.0 and a Playwright-bundled Google Chrome for Testing 153.0.8010.12 reference. The runner has per-journey 90–180 second bounds. Earlier combined runs found a stale test error-string expectation and a fixture that treated a connected runtime as complete before all its tabs reappeared. The fixture now waits for the named tabs within its existing 25-second deadline. Neither correction changed broker behavior.

In the earlier eight-command run, local suggestion input-to-two-frame paint was p50 **40.3 ms**, p95 **85.4 ms** across 12 queries; the command palette sample was **27.3 ms**. Three-trial 20-tab restore had active fixture p50 **1,007 ms**, p95 **1,120 ms**, process-tree RSS **895–898 MiB**. The 100-tab run had active fixture p50 **1,056 ms**, p95 **1,141 ms**, RSS **916–923 MiB**. These are fixture measurements, not a cross-host speed comparison.

The latest ten-command rerun measured local suggestion p50 **27.7 ms**, p95 **40.0 ms**, and human click to visible native tab placement p50 **15.3 ms**, p95 **16.4 ms** across 20 switches. The active 20-tab fixture was p95 **900 ms** and 100-tab fixture p95 **1,339 ms** across three trials each. This variance reinforces the need for repeated signed, real-site and presented-frame measurements before a speed claim.

The local paint sample is a fixture of 2,012 synthetic history rows and 12 input queries; it does not benchmark search across accounts or slow sites. The restore fixture uses three trials each at 20 and 100 tabs, not the full M0/M1 performance qualification. None of these probes installs from the Chrome Web Store, exercises an OS passkey, or verifies a signed update. The native-host call is a synthetic protocol echo, not a password manager or signed app bridge. Presence of `runtime.connectNative` or `storage.sync.get` must not be promoted to functional support. [Chrome's native messaging protocol and manifest paths](https://developer.chrome.com/docs/extensions/develop/concepts/native-messaging) informed the probe.

While the candidate compiled, a **reference-only** live Store journey in Playwright-bundled Google Chrome for Testing 153.0.8010.12 loaded the uBlock Origin Lite listing, clicked “Add to Chrome,” accepted the browser's native permission sheet in a disposable profile, and restarted the browser with that same profile. After restart the Store page showed “Remove from Chrome” and the extension toolbar icon remained. The installed version `2026.920.1710` was present under the extension ID `ddkjiahejlhfcafbddmgiahcphecmpfh`; `Secure Preferences` recorded `from_webstore: true`, no disable reasons, and the normal `https://clients2.google.com/service/update2/crx` update URL. The page also displayed a “Switch to Chrome” banner, which did **not** prevent installation in this reference. [The sanitized artifact](evidence/m1-reference-store-2026-09-24.json) records the result. It proves the current machine can reach the live Store and perform a reference install; it is **not Aux candidate evidence**, a Store update, or 1Password compatibility. The candidate must repeat the complete flow independently.

The shell integration is concrete work, not a theme replacement. Aux's [`App.tsx`](../apps/desktop/renderer/src/App.tsx) selects horizontal and vertical layout from current settings and reports stage bounds to native placement; the existing [`preload`](../apps/desktop/preload/index.cts) exposes Electron IPC for tab snapshots, commands, and runtime events. The current `//chrome` `BrowserView` owns its own toolbar, tab strip, side panel and content views. The proof must join these at the native view hierarchy while keeping Aux's React/CSS intact. Aux's existing [`AttachedChromeDriver`](../packages/chromium-driver/src/attached-chrome.ts) can attach an agent runtime to a CDP browser for a bounded test, but its raw debugging endpoint would **not** meet Aux's packaged broker boundary. These are source-inspection findings, not completed candidate integration or a time estimate.

The [current-code integration map](../experiments/chromium-fork/INTEGRATION.md) now names the reuse/replacement boundary for the shell bridge, tab catalog/controller, native stage, Profiles, extensions and agent runtime. It also orders the candidate proof: Store origin and restart first; then Aux WebUI shell, one native tab truth, and agent attachment. The existing API and native-messaging probes now accept `AUX_CANDIDATE_BIN` and write separately labelled candidate output without rerunning Electron or the Chrome for Testing reference; the [prepared shell journey](../tests/host/candidate-shell.mjs) requires an explicit Chromium-fork host marker, both current Aux layouts, real native page targets and matching runtime page IDs. These probes have passed syntax checks only and **have not run in a candidate**. A separate native-window inspection remains necessary for traffic lights, drag, fullscreen, split and popup geometry; a DOM class or successful `setStage` reply does not prove those details.

One specific source-level risk is Aux's transparent shell-over-page composition. Chromium's normal `ContentsWebView` demands an opaque page background and macOS render-widget code substitutes white for a transparent fallback. This is not a measured candidate failure, but it makes live stage pixels, overlay focus and hit testing early shell acceptance criteria. If one full-window WebUI cannot compose correctly, a split trusted-shell-view arrangement is an implementation route to test while keeping Aux's design; its patch and performance cost must be recorded.

Local prerequisites for the external gates are an installed, signed candidate in `/Applications`, a real 1Password app/account and its Store extension, a Developer ID signing identity and update feed, test SSO/IdP and passkey accounts, and two external site accounts for Profile isolation. This machine currently has an Apple Development identity only, no visible Developer ID identity, and no `/Applications/1Password.app`; `mac.identity: null` deliberately keeps the current local package unsigned. The opt-in signing lane is documented in [packaging](packaging.md#signed-update-qualification-lane). Do not ask for credentials in source or issue comments. Run the account/signing checks with the owner present or through approved secret handling.
