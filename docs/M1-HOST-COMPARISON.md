# M1 browser-host comparison — September 24, 2026

This decision compares **current Aux code and its real shell**, not historical screenshots or an extracted competitor design. Run `pnpm --filter @aux/desktop build` then `pnpm host:compare` from the repository root. The bounded runner writes `release/test-artifacts/aux-host-comparison.json` with the source commit, timed commands, full last output, and fresh API probe results. It exits nonzero on a failed or timed-out command. All profiles and sites in the run are disposable fixtures. The artifact is local test output, not a release certificate.

## Decision

**Keep Electron as the usable Aux preview host, but do not declare it the 1.0 browser host.** Its real Aux layout and agent path work, yet its documented Store-extension ceiling and the measured missing APIs fail a mandatory 1.0 gate. **Do not integrate the pinned CEF Chrome-layer prototype**: its observed Cmd+T path opened a stock Chrome window and lost Aux's tab shell. A different CEF integration could be reconsidered only if it passes the same tab and extension proof. **Prioritize a bounded `//chrome` fork prototype as the next candidate**, with Aux's current design kept as the shell. This is a recommendation to build the proof, not a migration go decision. No candidate has passed the signed 1Password, Store update, real passkey/SSO, signed update, or upstream security-rebase gates.

The host decision can be reversed by evidence. If the fork cannot keep Aux's two layouts and agent/profile boundary while handling real extensions, hold the 1.0 compatibility claim and retain the working Electron preview. A Chromium reference process is useful as an API control, but it is **not** a running Aux fork.

### Current run and limitations

The original September 24 run against source `b1db5bed` passed eight commands. The latest current-source rerun passed **ten** commands; its exact source SHA and timing are in the local artifact. It used Electron 43.6.0 and a Playwright-bundled Chromium 153.0.8010.12 reference. The runner has per-journey 90–180 second bounds. Earlier combined runs found a stale test error-string expectation and a fixture that treated a connected runtime as complete before all its tabs reappeared. The fixture now waits for the named tabs within its existing 25-second deadline. Neither correction changed broker behavior.

In the earlier eight-command run, local suggestion input-to-two-frame paint was p50 **40.3 ms**, p95 **85.4 ms** across 12 queries; the command palette sample was **27.3 ms**. Three-trial 20-tab restore had active fixture p50 **1,007 ms**, p95 **1,120 ms**, process-tree RSS **895–898 MiB**. The 100-tab run had active fixture p50 **1,056 ms**, p95 **1,141 ms**, RSS **916–923 MiB**. These are fixture measurements, not a cross-host speed comparison.

The latest ten-command rerun measured local suggestion p50 **27.7 ms**, p95 **40.0 ms**, and human click to visible native tab placement p50 **15.3 ms**, p95 **16.4 ms** across 20 switches. The active 20-tab fixture was p95 **900 ms** and 100-tab fixture p95 **1,339 ms** across three trials each. This variance reinforces the need for repeated signed, real-site and presented-frame measurements before a speed claim.

The local paint sample is a fixture of 2,012 synthetic history rows and 12 input queries; it does not benchmark search across accounts or slow sites. The restore fixture uses three trials each at 20 and 100 tabs, not the full M0/M1 performance qualification. None of these probes installs from the Chrome Web Store, calls a native messaging host, exercises an OS passkey, or verifies a signed update. Presence of `runtime.connectNative`, `runtime.sendNativeMessage`, or `storage.sync.get` must not be promoted to support for those functions.

## Prerequisites and maintenance cost

| Path | Immediate build work | Ongoing ownership and credible update path |
| --- | --- | --- |
| Electron preview | Continue everyday-browser and agent hardening in current code; add signed packaging/update lane. Broad Store parity cannot be achieved by merely adding unpacked fixture tests. | Moderate host maintenance relative to the other paths: track supported Electron/Chromium releases, qualify Aux native modules and broker after upgrades, and rehearse signed update/rollback. Mandatory extension parity remains a product blocker. |
| CEF Chrome-layer | Reacquire pinned SDK and solve Chrome tab lifecycle inside Aux's shell before further API work. Then implement shell/runtime bridge, profiles, popups, extension management and migration. | High integration and rebase burden: CEF and Chromium pins, native shell bindings, packaging and security updates. The measured Cmd+T failure means effort cannot yet be priced as a small embedding change. |
| `//chrome` fork | Obtain Chromium source/build tools and a build owner; make a minimal branded build that hosts Aux's real shell and tabs; run the same matrix before migration. Official macOS build docs require Xcode, macOS SDK, `depot_tools`, GN and Ninja. | Highest likely ownership: maintain patch inventory, automate Chromium security merges/builds/tests, own extension/store behavior, signing, updater, rollback and profile migration. **Actual person-days, build time and rebase conflict rate are unknown until a candidate and one upstream rebase exist.** |

Local prerequisites for the external gates are an installed, signed candidate in `/Applications`, a real 1Password app/account and its Store extension, a Developer ID signing identity and update feed, test SSO/IdP and passkey accounts, and two external site accounts for Profile isolation. This machine currently has an Apple Development identity only, no visible Developer ID identity, and no `/Applications/1Password.app`; `mac.identity: null` deliberately keeps the current local package unsigned. The opt-in signing lane is documented in [packaging](packaging.md#signed-update-qualification-lane). Do not ask for credentials in source or issue comments. Run the account/signing checks with the owner present or through approved secret handling.

## Next proof and decision rule

1. Build the smallest `//chrome` candidate that presents **Aux's real horizontal and vertical shell**, creates/selects/closes tabs and splits within it, and retains the human/agent target identity. Capture layout and command results from current source.
2. On that same candidate, install a real Chrome Web Store extension, restart, update, disable/remove it, and execute storage, content-script/MV3 worker, tabs, downloads, context-menu, cookies, declarative filtering, DevTools, and native-messaging journeys. Treat Store policy/service access as an external dependency to establish, not an inherited Chromium feature.
3. Sign under a stable Aux identity, then run 1Password save/fill/unlock, native passkeys, Apple Passwords, SSO/MFA, permissions/media, two regular Profiles plus private mode, agent takeover/reconnect, and a signed update with preserved identity/data.
4. Measure the same foreground journeys against Electron on the same machine and conduct one upstream security-update/rebase rehearsal. Record build duration, diff size, conflicts, CI resources and named release owner. Only then make a migration go/no-go decision.
