# LinkedIn current-page workflows

Aux reads currently rendered LinkedIn profile, company, job/search, inbox/thread and invitation-manager pages through its existing admitted browser-page route. This is a browser workflow, with the actual current browser Profile/session, Space, run, task revision, page URL/document epoch and observation identity. It grants no LinkedIn API products. There are no Voyager requests, private endpoint adapters, hidden data fetches or separate action execution stack.

## Evidence and scope

Official sources checked 2026-10-18:

- [LinkedIn API product access](https://learn.microsoft.com/en-us/linkedin/shared/authentication/getting-access): API products require their actual granted access; a logged-in browser is not an API grant.
- [Send messages](https://www.linkedin.com/help/linkedin/answer/a541865): messaging goes through the visible recipient/composer and Send control. Connections, message requests and InMail have different availability.
- [Personalize invitations](https://www.linkedin.com/help/linkedin/answer/a563153): profile connection flow exposes an invitation dialog and optional note. The current documented note bound is 200 characters; account quotas and Premium access remain determined by the actual UI.
- [Ways to connect](https://www.linkedin.com/help/linkedin/answer/a541669): Connect may be exposed through a profile or More menu. Aux deliberately never treats an unverified Connect control as a safe opener because it can send directly.

The page reader is a serialized, static DOM function. It performs no fetch or mutation, checks the exact URL before and after reading, accepts only secure LinkedIn product routes, and returns up to 80,000 visible text characters, 60 headings and 100 supported product links. Authentication/checkpoint pages and unrelated origins are refused. Optional service-account identity is only a currently visible "View your profile" profile link. Text is untrusted source material. The existing site-read admission, redaction and source identity remain authoritative.

## Workflow states and authority

`linkedin_workflow` prepares a server-held, ephemeral recipe from an actual native observation. Model input can name a requested recipient URL, exact draft text and an existing native subtree ref; it cannot supply Profile, Space, run, task or document proofs. Research/inbox reads return current evidence. Inbox navigation and a uniquely observed Message opener are ordinary browser actions. Draft proposals require a freshly observed, uniquely identified editor in the exact recipient subtree. Message drafts are bounded to 2,000 characters so the entire exact content and recipient can be presented in the existing bounded handoff UI. Invitation steps additionally require the native-observed final dialog role. Missing/ambiguous controls, missing Profile attestation or missing draft values block the recipe rather than inferring capabilities.

Recipes expire after five minutes, are capped at eight per host, bind exact ownership/destination/task/document/recipient/draft pre-state, and are consumed before normal actuation or approval parking. Execute re-observes and re-plans; changed identity, content, source, uncertainty or stale ownership rejects the action. Concurrent execution can consume a recipe only once. Stop, Take over and retirement invalidate ownership. Recipes are not persisted or reconstructed on resume. An unknown write is inspect-only and never replayed.

Execution delegates to Aux's normal `act`, with its original action ID, authorization, durable write journal and native target proof. Current research, inbox navigation and observed composer openers work through that path. Draft setters and sends carry a private sealed precondition through the existing ExecContext, PagesExecutor and SafetyDispatchGate. The current native target proof binds its form's values but does not bind a LinkedIn recipient header and rich composer subtree together. Consequently these steps currently produce a concrete handoff naming the entire exact recipient/content, with no browser input, no invented write receipt and no automatic retry, even under Auto or Skip confirmation. This is an observed native capability gap; automated LinkedIn edits/sends are not complete. Once a real native subtree source proof exists, ordinary draft setter undo receipts can apply. The recipe itself is not permission. A proposed Send or Send invitation is an external effect; it is never reported as performed until the ordinary receipt and fresh post-state verify it. A sent message/invitation has no guaranteed undo. A missing native capability is an explicit refusal, not a simulated connection.

Current recipes recognize exact observed English control labels only. Localized UIs, InMail/upgrade prompts, account limits and unsupported composer structures remain honest inspection/owner cases. No messages or invitations were sent during development. Fixture success is separate from current native/live LinkedIn acceptance.
