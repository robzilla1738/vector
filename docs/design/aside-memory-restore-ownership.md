## Recommended bounded design

Use **one shared pure logical retirement transform**, then **detached staged generations under existing SpaceMemoryStore/ProtectedStore crypto**, with a metadata-only durable transition owner. Do not introduce another Memory database, API stack, model call or plaintext staging payload.

### A. Capture and pure projection

1. Under the real MemoryPipeline owner, capture one authenticated snapshot containing both current ciphertext inventory/digest and verified logical state (`RecoverySpaceMemory`), with original per-Space generation/key identity. Acquire normal bounded source/projection ownership; use existing32MiB aggregate cap and canonical claim/document/Dream/history limits. No long SQLite transaction around awaits.
2. Reuse the writer's **corrected, independently reviewed retirement-only proven dependency closure**, including actual saved-article roots, canonical authenticated family facts and modern episodic receiver dependencies. The newly proven family↔typed-reference fixed-point gap in frozen legacy v1 must be corrected by writer v2 before this reuse; this design does not clear the v1 closure. Derive proof from the live CURRENT repo and copied staged repo; bind exact source/config/receipt digests through final staging publication.
3. Union only **proven article-derived** IDs/families, not all missing run IDs. A current unrelated note may refer to a run created after the chosen backup; its absence from the older copy alone must not erase it. Conversely a proven article-derived current claim must be retired even if its source run is absent from the old backup. The live CURRENT snapshot supplies that proof.
4. Extract the writer's live Forget claim/document/Dream/tombstone policy as a pure typed function next slice, then call it from live Forget and this copy projection. Do not duplicate subtly different sanitization rules. The function receives immutable logical state plus exact proven source IDs; it performs **no** Repo writes/native calls/model work/key retirement. It removes generated article claims/quotes and all reversible source-bearing history/index/Dream/change/proposal material covered by that policy; preserves independent ownerEdit text via the writer's tombstone form, independent owner documents/pastes, existing tombstones and unrelated notes. No new invented owner note/source authority.
5. Regenerate canonical summary/handbook/rollout/search-index/history inventory from projected authoritative state using the same serialization/builder as normal publication. No partial regex string scrubbing. A removed source cannot survive in before/after diff, proposal, history or reverse index. If proof or limits cannot be established, refuse this restore for review, never clear all Memory or truncate the safety closure.
6. Unchanged Spaces retain their original ciphertext and generation **byte-for-byte**. Only actually changed Spaces receive detached generations. Their policies, unrelated watermarks, workspace identity and Desktop ownership remain governed by existing retainSpaceMemory semantics; no unrelated desktop/saved-chat policy expansion.

### B. Prepare detached generation; do not retire live prior factor

Extract existing SpaceMemoryStore allocation/sealing/publication steps into a shared internal prepared-generation owner. Keep normal write behavior using that same implementation; add a narrowly typed **detached restore preparation** owner, not a tool-supplied boolean or no-op secret bridge.

Preparation creates a new random generation/factor using actual native Profile root and existing per-file AAD. It exposes only typed generation/key-name/ciphertext rows and ownership metadata internally; factor bytes stay private in memory/native credential storage. It never erases or mutates the CURRENT prior factor. A new identity is necessary: changing logical contents under the same generation ID would invalidate expected-generation/revision semantics and can make old proofs appear current.

Existing `importRecoverySnapshot(prior=null)` demonstrates correct detached resealing when copied workspace rows are empty, and its logical validation/serialization is reusable. It alone is not enough: it stores a factor before all copy publication is durable and currently has no ordinary-stage created-key ledger. Add lifecycle ownership rather than call it with fake credentials or normal `prior` semantics.

### C. Minimal durable state: no source text in root codec

Use current pending-restore structure plus a metadata-only FieldCodec-encrypted `aux_meta` transition record, not a new table. A typed versioned record binds: staging operation UUID/Profile; original recovery lineage; original full memorySourceDigest; affected workspace IDs; exact prior generation/key-name identities; prepared new generation/key identities; hashes of prepared ciphertext/logical projections and source-proof digests; state/progress. Key names must be derived/validated by canonical SpaceMemoryStore logic, never arbitrary caller-provided secret names.

**No claims, owner notes, documents, quotes or factor values in aux_meta/root-key payload.** Root-FieldCodec logical snapshots would create a new hidden text copy outside disposable Space erasure. That smaller shortcut is rejected. All such content stays only in the staged Memory rows encrypted under the new detached factors.

Before any new native factor store, durably register its planned identity under the original stage owner. A practical minimum is existing pending metadata with an explicit internal `preparing` versus `ready` phase plus authenticated plan bound to its exact temporary/pending DB inode/hash; atomically fsync/rename through current managed descriptor ownership. Alternatively one exact metadata-only preparation journal may provide that same role. Do not create two competing journals. This is required new lifecycle architecture; current version2 descriptor has no such phases/key ownership.

Build/check the projected DB/artifact inventory, record plan, store+confirm each genuinely new factor, recheck original source/ciphertext digest/native owner/recovery lineage, and only then publish `ready`. Never expose a preparing restore as restorable. Key-store failure/ACK loss must keep the original plan and inspect actual key status, not allocate replacements or automatically replay generation writes. Keep original error/cleanup debt explicit.

### D. Cancel, source Forget and shutdown

- Before apply, source/live factors remain owned by live DB. Cancel only planned newly allocated stage factors **after** proving they are not active in the live DB, not referenced by a different ready owner and belong to this exact authenticated preparation. Read back absence; retain cleanup debt/plan if retirement is uncertain. Never clear all `mem_*` secrets.
- Current digest/recovery-lineage checks fence final publication but do not join an actual held key store/copy. Register original stage controller+done with MemoryPipeline across the entire operation; workspace/source retirement aborts then joins it and its exact new-factor cleanup **before live Forget/key retirement acknowledges**. Recheck after every native/key/file await. No detached continuation using a new current snapshot.
- Once `ready` is durably staged and the RPC has returned, its key ownership must still participate in later source Forget. Existing beforeRemoval/recovery-lineage invalidation needs an exact pending-transition purge hook: retire the staged snapshot's affected source/Space ownership and join original cleanup, not simply advance lineage while leaving a decryptable new-factor copy behind.
- On shutdown, abort/join in-flight preparation and unpublished cleanup. A completed user-staged ready restore may remain for next startup with its exact durable owner; do not accidentally erase intended ready factors as incidental service close. Pause/edits/Forget invalidate the appropriate source/current snapshot, with actual join wherever erasure acknowledgement requires it.
- A crash during `preparing` leaves only its exact durable plan. Startup must not try to apply it; connect to the original native/codec owner against the still-current DB for safe inspect/cleanup or report cleanup required. Do not fail before native initialization in a way that makes its only genuine cleanup path unreachable.

### E. Actual apply and post-apply prior-factor retirement

1. Retain current exclusive restore lock, absence-of-live-runtime check, complete pending hash/artifact checks and original CURRENT memorySourceDigest check. The digest remains the **old live** snapshot; do not overwrite it with projected staged digest. New projected/ciphertext hash is separate.
2. Atomically swap only a `ready` validated staged DB. Affected new generations and metadata-only plan travel in that same DB, so crash after rename retains ownership. A new generation must be readable before the old one can be erased.
3. After actual native channel+FieldCodec+Repo initialization and **before any API/model/Memory source publication**, authenticate transition against the actual newly active DB/Profile and exact prepared per-Space generations/projection hashes. Confirm all new native factors read correctly. Retire **only** recorded exact prior factors, which must no longer be referenced by any active Space. Unchanged Spaces' factors are untouched. Do not derive deletions from the selected backup or a model field.
4. Persist per-Space retirement progress in metadata-only encrypted journal. Lost erase ACK: read original prior key; absence means already retired, surviving unchanged factor permits a safe owner-directed retry or explicit debt policy; ambiguous state must not trigger new generation publication. Never roll back to old plaintext/ciphertexts after an old factor might be erased. Preserve the newly committed generation and real uncertain outcome, matching existing Memory publication handling.
5. Remove transition metadata only once all exact retirements and new generation authentication are confirmed. Restart resumes inspection/finalization of that same operation, not model/extraction or action replay. A changed generation/hash/Profile fails closed without deleting needed keys.
6. **Split success cleanup from cancel.** Current finishRestore→cancelRuntimeRestore is safe only while cancellation deletes files. With stage-owned keys, successful apply must preserve new active factors and retire old factors; pre-apply cancel does the reverse. Keep a shared files-only cleanup leaf if useful, but no ambiguous generic cleanup that can erase active new keys.

No existing route performs all these responsibilities today. This plan deliberately identifies that missing key-owner lifecycle rather than describing source projection alone as sufficient.

## Minimum implementation seams for a later authorized slice

- New small pure logical Memory retirement module extracted from the **frozen writer live Forget** implementation; normal pipeline uses it and staged projection consumes it. Writer patch remains immutable until root merges it; this design does not depend on mutable working files.

- `space-memory-store.ts`: single existing prepared-generation/seal/publish implementation plus detached restore ownership and exact key-name/generation validation; preserve normal live write/uncertain-publication behavior.
- `space-memory-backup.ts`: retain unchanged snapshot ownership and apply only projected changed-Space rows; distinct original versus prepared digests.
- `runtime-backup.ts` plus one bounded metadata-only transition owner leaf: preparing/ready publication, exact cancellation/restart cleanup, original source invalidation, files-only success cleanup, current apply checks. No second public API.
- `main.ts`: actual-native post-apply finalization after protection/Repo and before publication; original pending/preparing cleanup availability; existing source Forget callback integration.
- `recovery-package.ts`: verify whether shared preparation owner must be reused for its already-detached creation cleanup; do not silently impose ordinary source-omission projection on explicit recovery packages that actually retain admitted page sources. No claim of a newly reproduced recovery-package failure from this audit.
- Existing aux_meta and pending descriptor can support metadata-only state without a new SQLite table/migration; exact canonical validation/protection must be implemented and tested, not treated as schema-free authority.
