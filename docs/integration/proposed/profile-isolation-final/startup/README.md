# Fresh-only early browser-root authorization successor

This source successor implements a concrete grant producer and paired native receiver before `ChromeFeatureListCreator::CreatePrefService` resolves or reads Local State. It preserves the default-off cold entry and changes no UI. It is **not activated, packaged, signed or runtime accepted**. Complete browser writer retirement and existing-profile recovery remain unfinished, so this source must not be described as ready protected startup.

## Actual finite grant

Policy v7 adds one exact `browserStartup` object with format `aux.browser.fresh-root-lease.v1`, `dataRoot` and `cacheRoot`. The actual signed-resource loader authenticates it; JSON decoding alone never grants authority. Both paths must be canonical absolute paths and pairwise separate from each other, control/task parents and the historical owner scope. Earlier policies remain decodable historical evidence but cannot enter this successor daemon route. The contained PTY source pin remains unchanged.

`AuxFreshColdInstallerGuard.acquire` obtains the actual two root descriptors through the authenticated parent connection, requires matching transport generations, and invokes `AuxBrowserFreshRootAdmission`. This fresh-only implementation requires **both actual root directories to be empty, owned by the effective UID, mode0700 and without extended ACLs**. Paths from the sealed policy must match the actual physical FD identities. It never accepts caller paths, JS, environment-selected roots, a previous readiness pulse, or arbitrary legacy data as authorization.

The producer checks both empty inventories before mutation, creates one fixed marker in each root with O_EXCL/O_NOFOLLOW, takes nonblocking exclusive advisory locks, writes/fsyncs policy/role/generation/device/inode binding records, then rechecks both inventories. All roots, markers and the authenticated policy remain retained by the genuine cold guard that is in the actual staged context/Owner graph. Failed partial creation leaves durable markers and refuses; it never deletes, repairs, resumes or reinterprets unknown state. Revalidation checks the sealed policy, current parent/transport through the guard, root path+inode, marker identity and exact bytes. The signed policy is the authorization prerequisite; directory locks are not claimed as mandatory access control against an unrelated same-UID process.

The actual retained Dispatcher exposes a native-only finite receipt method. It validates the current Owner before and after acquiring the72-byte result (little-endian transport generation plus SHA256 of the two physical root paths). It does not expose a new JS command. `AuxPreparedDaemonAuthority` routes a new finite operation6 through the existing private authenticated native request/observe/ACK machinery; the authority wire version is5 so old callers/receivers cannot silently accept it. Receipt publication sets a permanent `browserGrantIssued` custody condition **before** returning bytes. A lost reply or ACK cannot make that ownership disappear.

The browser's real selected-home registry calls that operation on its actual retained child/transfer, compares both path digests with its own current held root capture, validates the same current transport generation and live child, ACKs the exact reply, and retains the captured roots alongside that selected owner. The actual selected-home transfer now remains pending until the native authority endpoint has registered, matching the daemon's home-export-then-authority-registration order. This prevents selection from racing the first grant request. A one-shot attempt never falls back to readiness/provenance after failure. The cold-only pre-read patch starts the sealed native daemon and requires this exact grant before Local State IO. Later already-admitted calls revalidate the held owner/generation/roots.

## Shutdown, startup and recovery limits

The backend deliberately returns **pending** from authority close after any browser grant. ACK, elapsed time, JS settlement, a disconnected socket or a late callback cannot prove browser/profile writers drained. There is no implemented release handshake tied to actual browser-wide writer closure; this means graceful completion and restart recovery of this fresh grant are unfinished. Existing markers refuse on the next process; never remove them to make a check pass. This is a concrete finite first-start grant, not an all-writer custody solution.

The fresh roots must be prepared separately from accepted/owner profiles. Native selection creates/chooses a directory before this hook. If Chromium has written any additional bootstrap file by this point, the strict inventory refuses; no compatibility wildcard or owner-data adoption is allowed. A signed disposable actual candidate must determine exact early lifecycle prerequisites later. Native launch's Mach rendezvous, Security checks, monitor thread and callback timing before prefs have compiled but have not been observed here. Refusal currently follows the cold path's existing CHECK termination, before the Local State read; ordinary default-off startup is unaffected.

The roots remain name/FD identity checked, not a universal atomic filesystem broker. Concurrent replacement after a check, unrelated browser writers and shutdown lifetime still require the broader integration work. No live Security, Keychain, owner-state, provider/network request, signing or release operation is part of these checks.
