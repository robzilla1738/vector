# Native first-use home producer

This is an inactive, real filesystem producer for the fresh-install route, separate from legacy migration. It does not replace the required migration work or claim whole-profile custody. No native checkout, GN, current host, packaging, UI or active startup source is changed.

`AuxFreshNativeHome.create(inCanonicalPrivateParent:)` accepts a native caller's fixed reviewed canonical parent. It verifies current UID ownership, exact0700 mode, no extended ACL entries and canonical/no-symlink identity. It atomically claims `.aux-first-installation.v1` using `O_CREAT|O_EXCL`, private0600 and no-follow/nonblocking flags, then durably records a native-generated home name, transaction UUID and scope. It creates that random home with `mkdirat(...,0700)`, retains its parent/reservation/home descriptors and synchronizes file/directories. The scope is the actual existing contract: SHA256 of the complete canonical home path.

Only the successful creator gets the object: no initializer takes a receipt, Boolean, environment scope, arbitrary preopened home, or claimed process ID. Concurrent creators of the same parent cannot each create a home. Existing, empty, FIFO, failed or partial reservations refuse; there is no reopen/adopt-existing/reset/delete/retry-new-home path. Failure and deinit preserve the reservation and any home on disk. This prevents silently converting a damaged first attempt into fresh initialization. Crash recovery of that reservation must use a separately reviewed continuation, not another fresh call.

`validateRetainedIdentity()` rechecks private ownership/modes/ACLs, canonical parent identity, parent→child/reservation inode bindings and the exact original nonsecret reservation bytes. `requireEmptyBeforeAuthorityGeneration()` observes the retained directory itself and refuses any journal/content. `duplicateDirectoryForNativeBootstrap()` returns an actual close-on-exec duplicate of that directory, not a process/Keychain/launch grant. FDs close in deinit. All filesystem operations are non-protected and tests use only newly created disposable directories.

## Actual fresh authority boundary

The supplied fresh factory can generate software/enclave material; the coordinator can create-only persist five secure rows, recover unknown Add outcomes and deliver typed terminal selection. But its input types still explicitly call their reviews caller-asserted. An empty home alone does not authenticate Keychain absence or grant authority. This source does not pass `true` into those reviews or substitute a file lock for secure-row/native-host ownership.

The **concrete blocker** is the current signed-development loader: `AuxReviewedDevelopmentIdentity.home/scope/group` are fixed to the historical disposable installation, and `AuxDevelopmentPolicyContents.decode` requires an existing selected scheme/public keys/four target hashes. `AuxCreateSignedDevelopmentOwner` loads that selected policy, reads four existing rows and imports a runtime context. It cannot authenticate a pre-generation fresh identity; reusing it would either fail or require inventing its selected hashes before authority exists.

The smallest executable next integration is a distinct signed **fresh-bootstrap policy variant** binding a private parent, explicit allowed access group, host roles/team/image set and supported authority selection policy, without fabricated target hashes. The native early-start producer must load/validate that sealed resource before any profile/runtime launch, call this exclusive home creator, use exact Data Protection group/service/account probes for all four target rows plus the fifth transaction-bound stage, and invoke the real factory/coordinator only after every actual probe is absent. Any inaccessible/present/invalid result must refuse, never become absence. Publish authenticated terminal selection before creating profiles or runtime Node workers; retain original reservation, secure stage and partial records on errors. Existing policy/entitlements do not authorize a new scope/group or fifth selector. No signing/provisioning/protected call is performed here.

A genuinely new private home has no preexisting browser profile writers to migrate, so this route need not wait for legacy all-writer migration closure. That conclusion applies only if the real early native launch owner prevents profiles/workers from receiving the new home until terminal handoff. POSIX private directories do not defend against a malicious process with the same UID, and an fd, empty-directory check or reservation is not proof that every process or secure-store writer is excluded. The missing sealed fresh policy/early launch integration remains explicit, not an acceptance flag.

## Focused checks

`check.sh` compiles this source and executes only real disposable filesystem cases: first creation/private FD/scope, existing and partial reservation refusal, preserved originals after deinit, unsafe mode/symlink/FIFO refusal, replaced inode and changed reservation rejection, plus two genuine concurrent creators with exactly one winner. It performs no Security, factory generation, hardware, owner-state, profile/runtime/app launch, cloud, signing or grant operation.
