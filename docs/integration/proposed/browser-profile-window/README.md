# Actual legacy Browser.ensureProfile proposal

Source-only implementation proposal. No shared Chromium source edited, no native compilation or browser/profile/Keychain operation performed. This follows the supplied implementation; it is not an invented success alias. Root will compose the patch after the full native build and actual supplied-authority/profile-security proposals.

The backend refuses non-secure debugging sessions with the recorded exact message, invalid/nonexistent index, locked profile and invalid URL, and reports failed URL opening rather than success.

`shipped-contract.json` records exact table values, strings, addresses and instruction-range hashes; `vendor/provided/framework-profile-contract.py` regenerates it from only the exact pinned thin file without loading/executing it. Xcode static disassembly of those ranges establishes control flow. This is analyst interpretation of shipped bytes, not recovered original C++/PDL text or runtime observation. REA Hopper was unavailable; Ghidra required thinning and its initial whole-program analysis timed out at the300s transport boundary. Its ephemeral session was closed. No Ghidra decompilation or successful string-query evidence is claimed.

The newer Browser.ensureChromiumProfile is not implemented: it was not observed in this older supplied framework. ## Implemented work

The staged legacy PDL/config adds only ensureProfile with exactly those inputs and an async empty result. BrowserHandler invokes the new aux_profile_window helper, mapping genuine errors to original protocol categories; callback success occurs only after existing normal-window activation or Navigate produces actual inserted contents.

Helper selects an existing registered ProfileManager entry by the same unchanged upstream SortedByName routine used by the staged account API/gate. The header-only exposure moves that existing declaration from private to public; comparator/body unchanged. Original comparator was not fully recovered from shipped stripped code, so exact historical sort equivalence remains an uncertainty. Consistent authoritative producer/consumer ordering avoids inventing a second index mapping. The helper never builds a path from an arbitrary ID/index string, creates an unregistered profile directory, selects Guest/OTR, or discovers an Aside profile. It validates canonical selected path beneath current browser's own user-data root, refuses symlink path escape, reloads via LoadProfileByPath rather than creating arbitrary paths, and revalidates registration/order after async work.

Actual FetchProfileSecurity supplies bound account and authenticated Vault/onboarding status before and after profile loading; account change, failure, lock or profile disappearance refuses. This depends on root's already reviewed real supplied metadata/status helper, not the retired security-state.json reader. No private-key export or original key substitution occurs. Forced-incognito policy refuses a normal-mode window request; it does not silently reroute into OTR. Existing normal-window lookup uses upstream ProfileBrowserCollection, avoiding first-match global activation iteration. shouldFocus=false uses inactive show; valid supplied URL opens a real tab/window. No URL produces a real newtab only when a normal window is absent.

The legacy positional wire carries no invented account/profileId parameter. The authoritative metadata reader now exposes actual optional binding.profileIndex. Legacy requests refuse a missing/negative/mismatched stored index versus requested/current registered index before profile load and again after async verification; the status client also compares it when rereading metadata. Thus a stale reordered binding cannot silently open a different bound profile. Recovery must use the actual native getProfileContext -> supplied accounts.ensureProfileAccount flow to refresh metadata, preserving L4's classified local/cloud identity; this helper never writes raw registry JSON. The separate binding-index-followup.patch targets exact2f8265bd4's local-profile-binding sources after that proposal, with independent before/after pins. Its existing disposable profile_state_probe is extended with missing/stale/reordered/refreshed/negative-index fixtures, but is not compiled/run while the lock is held.

## Secure remote session capability

A new generic client virtual returns false by default. Only a browser-GUID WebSocket admitted by the configured HTTP request filter sets the client capability. Page WS, approval-only/unfiltered clients, extension debugger and arbitrary trusted in-process clients retain false. ServerWrapper runs the installed filter before accepted WS dispatch; Aux filter validates loopback/Host/origin and original installation session. ChromeDevToolsSession additionally requires browser agent type before passing the capability to BrowserHandler. Existing IsTrusted is not treated as equivalent and is not widened. This reproduces the original secure-session guard without relying on host/port/name heuristics.

This relies on the filter's authentication contract: the production fixed Aux listener installs the actual authority filter. A future origin-only/non-authenticated filter must not reuse this capability. It cannot be granted by a client-supplied header/body or the legacy command itself. Caller weak lifetime is checked across async metadata/profile work so a retired handler cannot subsequently open a window.
