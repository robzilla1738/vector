# Fresh secure staging and restart adapter proposal

Hash-only fresh journals cannot restore random lost private material. This inactive source adapter proposes one additional secure staging record containing the exact prepared four target payloads. It neither regenerates authority nor persists plaintext DK/private keys to disk. No Security call, hardware factory, owner-state access, startup hook, installed module or packaging input changes here. **The fifth selector and its runtime use require a new explicit review/approval. No authority is assumed.**

## Minimal secure item and selector

For the separately reviewed never-used scope and transaction UUID, propose one generic-password item with service `aux.<scope>.install.secure-stage.v1`, account `aux.<scope>.fresh.<lowercaseUUID>`, and an explicit reviewed Aux-only access group identical to the four target groups. The adapter rejects overlap with target selectors. A future actual Security executor would need Data Protection selection, authentication-UI-fail, AfterFirstUnlockThisDeviceOnly protection and exact return-data/readback checks consistent with reviewed installation storage. No omitted-group fallback, enumeration, synchronizable item, update, overwrite or deletion is allowed by this adapter. These query semantics are proposed, not executed or newly authorized.

The `aux.install.fresh.secure-stage.v1` secret payload contains transaction/scope, exact bindings, candidate digest, four target hashes/public descriptor, and canonical base64 of metadata/signing/KEM/wrapped-root payloads. It contains no plaintext root: only the exact existing Aux-v2 wrapped-root bytes. Software private keys are present inside the sensitive proposed Keychain value, as they are in their eventual target rows. Consequently these bytes must never be written to filesystem journal/log/receipt, Blob, environment or general diagnostics. Data Protection Keychain protection is delegated to an explicitly authorized future executor; the source codec alone does not encrypt or protect an arbitrary file. Memory zeroization is not guaranteed.

Record size is bounded to16KiB using the existing strict duplicate-member-aware parser. Oversized hardware cohorts fail closed; hardware capacity/behavior remains unverified. This proposal does not invent a chunking scheme or silently truncate records.

## Ordering and crash policy

1. Independently establish genuine never-used scope admission and writer custody. Generate/prepare one cohort in memory. Publish the nonsecret fresh draft journal using the reviewed private journal store.
2. Prepare the stage intent, including nonsecret `aux.install.fresh.secure-stage.binding.v1` binding of exact secret-payload SHA256, initial draft SHA256, candidate/transaction/scope and fifth selector. Persist that binding durably before submitting the stage Add. The adapter checks an explicitly named *asserted* durable binding acknowledgement. A production binding store/dispatch integration is not supplied here; it must preserve private-store/CAS mechanics and cannot serialize secret stage bytes.
3. Submit the fifth row add-only exactly once, then capture it under the explicit selector. Duplicate/error/absent/inaccessible/mismatching results do not authorize target writes or replacement. On a restart after a successful Add but before its status, the existing exact stage may be read/validated; no Add replay is necessary. No target Add can be issued by this adapter before exact stage readback, binding/hash validation and actual command-authority validation.
4. Restore validates all four payload hashes, public descriptor/candidate digest, exact selector binding, real signer signature/public continuity, strict Aux-v2 wrapping and root32 recovery through the actual command core. That restores exact private payloads; it does not prove who wrote the secure row or establish external custody.
5. For a draft, `prepareNextIntent` creates a new process-local single-use ticket for the next role. Persist its intended journal before `takeRequest`. The ticket cannot be serialized/recreated from a persisted intent and is consumed under a lock before returning a request. A restarted `.intent` supports observation-only reconciliation. Exact pending bytes may advance; pending absent remains unresolved and **cannot** mint a new Add ticket, even though the earlier pure reducer exposes a lower-level addRequest API. Changed/unavailable captures block. No recovery path regenerates private keys or rewrites pending records.
6. Retain the fifth secure item and partial target rows on all errors and interruptions. Even after journal ready, retain staging until independently authenticated four-row completion and command-core acceptance. This adapter supplies no cleanup/delete method or automatic selection. A later exact-selector cleanup would require a separate reviewed operation and must never precede authenticated completion.

The unavoidable volatile window between generation and durable secure-stage storage is not magically recoverable. If material is lost before stage persistence, this adapter refuses recovery. A genuinely never-used scope could be re-admitted only by the external native authority/absence boundary under a new review; empty new-target names alone are insufficient. If any durable draft/binding/artifact exists, absence of staging is an unresolved failure retained for explicit review, never implicit fresh regeneration. This is a bounded safety proposal, not a promise of arbitrary pre-stage restart completion.

## Focused evidence and remaining work

`check.sh` compiles and exits0 using software-only synthetic authority. The fixture keeps the simulated secure item in memory, checks exact wrapped-root bytes and absence of plaintext DK in the stage envelope, rejects wrong binding acknowledgement/missing or changed/unavailable stage, restores through actual signing/command-core validation, exercises crash-after-target-Add observation, refuses uncertain absent-intent replay and consumes each fresh in-process ticket once. It reaches four captured target rows while retaining the stage. It performs no Security calls or secret disk writes. Hardware dependency branches compile only.

Still missing: native never-used scope/custody authority, approval of the fifth exact selector, actual Data Protection stage executor, private durable stage-binding store and production coordinator, secure crash/cancellation semantics at the external dispatch boundary, authenticated terminal acceptance and separately reviewed cleanup. The historical disposable same-scope migration is not eligible for this fresh mechanism. Current accepted UI/app and historical source evidence remain unchanged.
