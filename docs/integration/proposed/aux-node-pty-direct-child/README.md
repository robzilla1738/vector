# Direct-child PTY source correction

This is a distinct buildable successor source proposal for the official pinned node-pty1.1.0 Unix implementation, not a replacement installed/signed module. The unchanged upstream source, helper and MIT license remain in `../aux-native-pty-custody-feasibility/upstream/`. `pty.patch` applies exactly to that `src/unix/pty.cc`; `source/pty.cc` is the complete result, with its required new `direct-child-wait.h`. Copyright notices and LICENSE are retained. Source provenance is Microsoft commit `1def5774632305246fe21f0f69e23a664d6c5910`; `source-pins.json` records this distinct source revision and compiler dependency lock. This does not assert that the supplied signed prebuild was compiled from these official upstream bytes.

The implementation prepares its TSFN, native state/unknown record and sole reaper thread before spawning. The thread initially waits for either the actual successful syscall PID or cancellation when no child was created. A successful parent publishes the actual child immediately, before nonblocking setup or JS result construction can throw. A scoped master FD closes on those errors; it transfers only after construction succeeds. No signal-by-PID rollback or second reaper is added. Closing the master is not proof of child exit: the original direct-child wait remains pending until its real wait result arrives.

The sole wait retries EINTR, interprets status only when waitpid returns this child and a terminal exit/signal status, and never fabricates an exit on ECHILD/other failures. A preallocated native record retaining the syscall PID and error is retained in a process-local atomic list before best-effort separate JS error delivery. The existing `onexit(code,signal)` is never called for that unknown state, so its JS lease remains unresolved. The completed worker can be joined normally. Environment closing skips further TSFN use after `napi_closing`, following the actual Node26.5 N-API contract. No unknown-record recovery/reset API is introduced; these records intentionally persist until process termination. The PID records are creation provenance, not authority to signal a potentially reused PID.

## Actual verification

The final serialized check compiled the complete actual patched addon against the current Node26.5 source headers and exact registry node-addon-api7.1.0 headers, linked the real Mach-O module with automatic ad-hoc signing disabled, and verified absence of LC_CODE_SIGNATURE. Four compile-time assertions execute the actual shared result decoder for valid exit, failed wait with a plausible status, impossible return and nonterminal status. The exact upstream patch application matched the complete patched file. `evidence/receipt.json` records source/header/output hashes and compiler commands; `evidence/compile.log` records the actual result. Temporary native outputs were removed.

An initial recipe failed because Node's source `util.h` shadowed the system header; the final recipe fixes include ordering. A subsequent unsigned standalone runtime-fixture attempt terminated by SIGKILL before a test result (session85268, terminal247), consistent with unsigned executable enforcement; the precise OS reason was not separately inspected; its preceding compiler output is retained as `evidence/unsigned-fixture-execution-attempt.log`. No signing or policy bypass followed. The final check uses compile-time assertions only. No addon was loaded, no real wait/TSFN/PTY lifecycle was exercised and no child/descendant runtime acceptance follows from compilation.

## Integration and remaining boundaries

The actual owned-entry projection in `aux-native-owned-entry-pty/source/project.mjs` routes the fixed supplied PTY loader. `aux-native-embedded-pty-policy/source/AuxFreshBootstrapPolicy.swift` v3 still pins original supplied module source `a8b049f93353a68a8c289c1a868e8c8ae29fa4caf2f56af676b57b780d25c19a` and helper source `b9cf27a0832388cf154434f192d59739b2ce4c18463d7b4387b0c49e2857f79f`. Those are module/helper artifact identities, not the new C++ source hash. They were not overwritten. Integration requires a separately reviewed successor source/build identity and paired signed module/helper/policy; none is authorized or fabricated here. The accepted app, packaged original addon/helper, signature checks, migration admission and default-off startup route remain unchanged.

This slice establishes source ownership only for the successfully spawned direct child. It does not establish Environment-wide creation admission: callback-capable argument reads still precede preparation. It does not bind helperPath natively, start suspended, add per-Environment generation custody, observe descendants, prove subtree drain, or wire an observer/coordinator. Linux/BSD code compiled from this Unix source also takes the prepared sole-reaper path, but only macOS was compiled here; Windows source is unchanged. The upstream spawn routine's existing slave/low-FD cleanup leaks and ignored attribute/file-action return checks are separate remaining work. No owner profile, key, grant, provider, policy, UI or accepted runtime was changed.
