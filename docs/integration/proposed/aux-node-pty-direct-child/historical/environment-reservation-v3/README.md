# Direct-child PTY source correction

This is a distinct buildable successor source proposal for the official pinned node-pty1.1.0 Unix implementation, not a replacement installed/signed module. The unchanged upstream source, helper and MIT license remain in `../aux-native-pty-custody-feasibility/upstream/`. `pty.patch` applies exactly to that `src/unix/pty.cc`; `source/pty.cc` is the complete result, with its required new `direct-child-wait.h`. Copyright notices and LICENSE are retained. Source provenance is Microsoft commit `1def5774632305246fe21f0f69e23a664d6c5910`; `source-pins.json` records this distinct source revision and compiler dependency lock. This does not assert that the supplied signed prebuild was compiled from these official upstream bytes.

The implementation prepares its TSFN, native state/unknown record and sole reaper thread before spawning. The thread initially waits for either the actual successful syscall PID or cancellation when no child was created. A successful parent publishes the actual child immediately, before nonblocking setup or JS result construction can throw. A scoped master FD closes on those errors; it transfers only after construction succeeds. No signal-by-PID rollback or second reaper is added. Closing the master is not proof of child exit: the original direct-child wait remains pending until its real wait result arrives.

The sole wait retries EINTR, interprets status only when waitpid returns this child and a terminal exit/signal status, and never fabricates an exit on ECHILD/other failures. A preallocated native record retaining the syscall PID and error is retained in a process-local atomic list before best-effort separate JS error delivery. The existing `onexit(code,signal)` is never called for that unknown state, so its JS lease remains unresolved. The completed worker can be joined normally. Environment closing skips further TSFN use after `napi_closing`, following the actual Node26.5 N-API contract. No unknown-record recovery/reset API is introduced; these records intentionally persist until process termination. The PID records are creation provenance, not authority to signal a potentially reused PID.

## macOS spawn setup correction — source revision2

The next source revision fixes the actual macOS `pty_posix_spawn` setup/cleanup path. Every successfully reserved low FD is counted before the break; a failed open stops immediately. Separate local master/slave ownership attempts their close on every prespawn failure, attempts the parent slave close on success, and transfers only the actual successful master to the caller. A close attempt is resource cleanup, not evidence of child exit. Each grant/unlock, terminal ioctl/configuration, file-action initialization/addition, attribute initialization/setter and signal-set setup result is checked. Syscall errno is captured before cleanup; posix_spawn APIs retain their direct error code. Destroy operations run only for initialized spawn handles. After actual successful posix_spawn, no cleanup return overwrites success or conceals the real child from the prepared reaper. Descriptor close calls are not retried, avoiding a reused-FD close after an interrupted close.

This is still a distinct inactive successor source revision, not new signed policy/runtime authority. Earlier source, patch, pins, compiler recipe, log and receipt are retained under `historical/direct-child-reaper-v1/`; the current source inventory is revision2.

## Native Environment reservation producer — source revision3

The first native operation in `PtyFork` now calls `AuxNativePtyBeginCurrent`, before obtaining the N-API Environment or any callback-capable argument access. An allocation-free local guard cancels only a pending token on paths known not to have created a child, including argument/setup throws and refused creation. All three argv/environment pointer arrays are zero-initialized so conversion/getter exceptions cannot make their existing destructor free uninitialized pointers before reservation cancellation. The actual macOS spawn routine rechecks `AuxNativePtyCanSpawn` after setup and immediately before every actual posix_spawn attempt. It publishes the successful syscall PID through `AuxNativePtyChildCreated` before any cleanup or caller operation, and before waking the prepared sole reaper. The Unix fork parent similarly publishes its actual positive syscall return.

The sole wait's shared result now preserves both the actual waitpid return and raw status, separately from its checked JS exit status. `AuxNativePtyDirectWaitResult` receives those actual values before any JS/TSFN delivery; no expected or JavaScript PID is substituted as the wait result. The separately retained local unknown record remains fail-closed, and callback loss cannot manufacture successful completion.

These are native-only imports of the canonical `AuxNativePtyReservation.h` ABI from `aux-native-pty-environment-bridge/source`; no N-API/JS export is added. The host owns actual Environment lookup, reservation lifetime and admission. Building this successor addon now requires that host bridge. This source does not authenticate the addon/helper, authorize a generic helperPath, create an observer or prove descendant drain. Previous revision2 source/patch/pins/recipe/receipt/log remain under `historical/spawn-fd-v2/`. The revision3 source inventory binds the exact canonical header hash without duplicating it.

The exact upstream patch application matched the complete patched file. All five native bridge imports remain explicit unresolved host imports in the linked module: the host was not resolved, loaded or executed by this check. The canonical header matches host commit `7a3503003`, and source/header hashes matched before and after compilation. `evidence/receipt.json` records source/header/output hashes and compiler commands; `evidence/compile.log` records the actual result. No signing or policy bypass followed. The final check uses compile-time assertions only. No addon was loaded, no real wait/TSFN/PTY lifecycle or spawn-setup failure injection was exercised and no child/descendant runtime acceptance follows from compilation.

This slice establishes source ownership only for the successfully spawned direct child. The corresponding host implementation is a separate proposed source, and the addon compile does not establish its runtime binding.
