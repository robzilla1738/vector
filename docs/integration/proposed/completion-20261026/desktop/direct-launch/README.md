# Self-contained ordinary local launch

The actual A78 native browser already owns ordinary v9 startup. `BasicStartupComplete` validates the packaged identity, exact current signed browser/daemon and sealed policy, derives OS-user locations, captures native roots and authenticates the bundled daemon before Local State/profile I/O. Its non-official build already appends `use-mock-keychain` before Chromium OS crypt initialization. The native child gets a cleared environment, bundle-relative resources/current directory and fixed Aux endpoints. It does not need `/opt/homebrew/bin/node`, workspace JavaScript or an external acceptance Boolean.

The current `Launch Aux.command` does depend on a hardcoded workspace and Homebrew Node, but those are diagnostic-launcher dependencies. `scripts/aux.mjs` only adds package preflight, ordinary command flags and an external process-group guardian/observations; those do not grant installation or profile authority. `aux-user-launch.mjs` explicitly calls itself package preflight and derives/creates no user roots. The old unmanaged A12 receipt reports never-ready cleanup without a diagnostic proving a remaining native direct-launch failure; it predates the final accepted auth/shutdown repairs. That receipt does not prove direct opening works either.

One actual source difference remains: the development script always supplies `no-first-run` and `no-default-browser-check`, while ordinary native direct opening does not. Chromium's first-run implementation consumes the former and its native main/infobar checks consume the latter. The one-anchor **root-owned** `root-integration.json` / `.patch` applies those same two flags inside the existing non-official, ordinary browser-only branch. It preserves all existing native authentication/root checks, mock Chromium Keychain policy and real Aux onboarding/provider/account state. It writes no completion marker and skips no Aux installation authentication. No native build, execution, state or permission action was performed here.

## Reliable local successor path and remaining gate

The intended self-contained path is to open the **exact final successor `Aux.app`** in Finder after root has verified that direct path against its exact bytes. No new wrapper or launcher architecture is needed. Keep the current Node launcher available for diagnostics until actual direct acceptance passes. Do not replace the accepted A38 app or rewrite its historical receipts.

Root should perform one final-candidate direct/Finder opening from fully stopped owned candidate processes, observe genuine native/browser/daemon readiness and restored supported profile, then normal Quit. A second Finder open while already running must reach the same instance rather than initialize another daemon. Bind those observations to the exact package identity. If a demonstrated failure remains, its native diagnostic should drive the next bounded repair; do not call static source presence runtime acceptance.

The current native v9 namespace is persistent across normal sessions even though its approved name is `Aux Browser A38 Disposable`. No `/private/tmp` scope or workspace bootstrap script chooses it. Replacing that name/location, using the original nonempty `Aux Browser` container, making an installer/updater, production cookie-key behavior, distribution portability and release are separate unchanged boundaries. This source patch neither initializes a new namespace nor adopts owner state. Keep that limitation explicit in the local handoff.
