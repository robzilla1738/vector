Adding a browser can transfer desktop accounts and encryption keys and makes unlocked vault information accessible. Browser-profile isolation does **not** isolate a real unlocked desktop account. To satisfy the no-owner-data boundary, companion acceptance needs an operator-provided disposable 1Password membership and a desktop app session containing only disposable data (for example a separately arranged test OS user). If that environment is unavailable, stop companion acceptance at the precise vendor prerequisite; do not read or trust the owner's desktop session. No new account is created by this packet.

The [connection troubleshooting instructions](https://support.1password.com/connect-1password-browser-app/) name desktop Settings → Browser → Connect with 1Password in the browser, extension Settings → General → Integrate this extension with the 1Password desktop app, and macOS background activity for 1Password. Vendor instructions do not require Accessibility, Input Monitoring, Screen Recording, Full Disk Access, or AppleEvents for this browser journey. 1. **Bind the artifact.** Record the final approved app/inventory/signature receipt, exact running app path, OS/build and two actual disposable Aux profile IDs (A/B). Use that final successor, not A38. Keep all extension operations inside these profiles. No private state-file inspection.
2. **Store installation once in A.** Open the exact official store URL through Aux and use its native install control. Record offered publisher/ID/version, actual permission decision and installed enabled state shown in Extensions. If the store refuses Aux or offers no supported install, record exact error and stop that branch; do not sideload a reconstructed copy. Check B's Extensions UI: the A install must not appear there. This is the profile-local installation check.
3. **Standalone official autofill.** In an isolated test membership, sign in through the extension's normal vendor flow, keeping desktop integration disconnected for this result. Use only a single uniquely named synthetic Login (e.g. Aux-X1-<run>), one loopback URL and clearly fake username/password. An operator supplies/enters membership secrets; receipts contain no account token, recovery key or password. The test form is a loopback HTTP page with username autocomplete=username and password autocomplete=current-password; POST remains on loopback, never sends data to a production site and returns a success page. Use the official popup's New Item route if automatic save does not offer on localhost; document which route was used. A missing localhost suggestion is an observed limitation, not proof the extension failed globally.
4. **Observe actual fill.** Reload the empty loopback login page, choose only the synthetic Login through the real 1Password inline/popup UI and submit. Verify both fields correspond to the synthetic fixture through the page's success result, without logging the password. One reload/refill is enough. Record extension fill, lack of competing built-in Aux password prompt and normal navigation. Do not call a content-script fixture a vendor result.
5. **Separation and normal restart.** With B still uninstalled, visit the same form: no 1Password extension UI/fill should appear. Install the same official extension in B once only if independently verifying extension storage/auth state: its standalone session must initially require setup rather than inherit A's sign-in. Do not assert the same vault must be invisible after explicitly signing both profiles into the same membership. Normal Quit/reopen of A should preserve the official installed extension and expected lock state; one synthetic refill suffices. No crash campaign.
6. **Desktop companion, separate result.** Only in the isolated test desktop environment, and only after the actual browser satisfies the documented Applications/signature picker condition, have the operator add the exact final Aux app via 1Password Settings → Browser → Add Browser. Record selected path and observed acceptance/rejection; no allowlist file edit or verification bypass. Perform one synthetic refill. If native connection fails, record the extension's exact connection error and nonsecret Aux host phase/result. Do not classify it as vendor signature failure without an actual error proving that, or treat extension-only success as companion success.
7. **Owned cleanup.** Delete/archive only the unique synthetic Login through the official UI in the test account, remove only this test browser trust entry if created, remove the official extension from the two disposable profiles if requested by the acceptance scope, and stop the loopback server. Verify absence by those same UIs. Keep evidence, and do not delete unrelated profiles, desktop accounts, host registrations or credentials.
