# Native CLI Space routing

The actual packaged ordinary CLI parser rejects `--space`, and its native OS-envelope receiver populates only `routing::Intent.profile`, even though the existing routing resolver already supports exact Space UUIDs or unambiguous names. This is a missing requested D2 boundary, not a failed UI test.

The five-file counted successor joins `aux open URL --profile … [--space …]` across argument parsing, strict percent-encoded envelope encoding/decoding, native help and the existing external routing receiver. Space requires an explicit profile; that destination wins over automatic site rules. Names are bounded UTF-8 data at the receiver, not filesystem paths or shell command text. Duplicate, malformed, control-character, empty and overlong fields refuse. The same native resolver handles missing/ambiguous/unavailable Spaces without opening an alternate profile. Prior commands omit the new field and keep their original wire envelope.

The inactive retained peer command explicitly refuses a Space argument instead of accepting then silently ignoring it. That peer role is not the actual `AUX_BROWSER_ONLY_NATIVE_STARTUP` packaged ordinary CLI. Supporting it remains part of its existing unpaired retained-runtime join; this patch grants no task or installation authority.

The pure-data `cli-space-fixture.cc` covers name/URL preservation and explicit refusal cases. The actual overlay parser compiled with C++20 and `-Wall -Wextra -Werror`; that fixture passed once, serialized through `scripts/native-build.py`. `focused-check.json` records the actual result; the temporary executable was removed. Root owns native projection, affected translation-unit compilation, browser/CLI packaging and one actual command targeting a known disposable profile/Space. OS dispatch acknowledgement still means queued, not successful network navigation; native routing reports actual refusal in the browser.
