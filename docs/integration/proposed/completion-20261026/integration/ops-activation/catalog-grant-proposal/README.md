## Observed PUBLIC TEMP conflict: owner decision required

The actual database ACL grants PUBLIC **CONNECT and TEMPORARY**. The public schema grants PUBLIC USAGE and **no CREATE**. PostgreSQL combines direct, role-membership and PUBLIC privileges; NOINHERIT or `REVOKE TEMPORARY ... FROM aux_backup_capture` cannot subtract PUBLIC's TEMP right. The official [GRANT reference](https://www.postgresql.org/docs/18/sql-grant.html) describes this additive authority.

Therefore the currently observed catalog cannot satisfy the existing strict no-temp capture contract solely by granting a dedicated role. The SQL deliberately raises an approval-dependency error **before role creation** while PUBLIC TEMP exists. That is an honest source guard, not an observed attempted execution.

Removing this inheritance would mean a separately reviewed **REVOKE TEMPORARY ON DATABASE neondb FROM PUBLIC**, with exact replacement TEMP grants only to any identified legitimate consumers. That is a shared database policy change affecting every current/future login that depends on PUBLIC TEMP; it is **not included in the SQL**, and this preparation grants no authority to perform it. Existing explicit TEMP grants to neondb_owner/neon_superuser are visible in the observed ACL, but the catalog does not establish all application/operator reliance on inherited TEMP. No broad revoke, principal inventory expansion or application permission change is presumed safe.

The owner can instead explicitly accept a capture-role exception that retains inherited TEMP. That would require a revised exact proposal and a truthful claim: persistent application table access is SELECT-only, while temporary object creation and inherited PUBLIC capabilities remain. It must not be labeled the strict no-temp role. This packet chooses neither shared policy mutation nor that exception; its strict fence remains in place. Other runner/billing/storage approvals do not silently approve this new shared database implication.
