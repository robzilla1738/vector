# Backup runner: bounded source-access proposal

Preparation only. No role, password, server, token or provider setting was created or changed by this document. The owner must approve the exact production recipients before activation. Current signed-in provider observations are in [the dashboard receipt](../../integrator/backup-dashboard-review.json).

The existing capture uses a PostgreSQL repeatable-read, read-only transaction, exports its snapshot, and invokes `pg_dump` against the same direct endpoint. That transaction mode does not restrict what a stolen database credential could do. Do not place the migration/owner role on the runner merely because the capture code requests a read-only transaction.

Before proposing executable grants, inspect only public PostgreSQL catalog metadata on the exact production branch: database/schema ownership, roles and memberships, table/sequence owners, RLS and large objects, extension definitions, and inherited PUBLIC privileges. The proposed dedicated capture login must own no database/schema/table, have no membership in the application/admin role, and receive only CONNECT, USAGE and SELECT needed to export the complete approved schema12 snapshot and sequences. Granting sequence USAGE or UPDATE is unnecessary for reading current sequence values. Do not grant BYPASSRLS, a superuser role, a database-wide read role, schema CREATE or temporary object privileges by assumption. Existing PUBLIC privileges must be audited; a role-level REVOKE does not cancel rights inherited from PUBLIC. If RLS prevents complete capture, record that incompatibility and obtain a specific decision instead of silently backing up a filtered subset. Future table grants/default privileges belong to the actual migration owner and require the same explicit scope. The restore credential is separate and never stays on the capture server. See the official [GRANT reference](https://www.postgresql.org/docs/current/sql-grant.html) and [pg_dump reference](https://www.postgresql.org/docs/current/app-pgdump.html).

Vercel's current [private storage documentation](https://vercel.com/docs/vercel-blob/private-storage) and [security documentation](https://vercel.com/docs/vercel-blob/security) specify `BLOB_READ_WRITE_TOKEN` for private reads. A supported read-only private-store credential has not been established. The exact proposed recipient is private store `store_UUr9bRkRQm4lu0Z2` on the runner, with its real read/write breadth stated explicitly. The code's GET-only behavior does not narrow the credential. No account-wide Vercel token, other store token, browser cookies or generic password-manager token belongs on the runner.

The existing Cloudflare credential is Object Read & Write for `aux-recovery-prod` only, active through the displayed November22 date. The `daily/` prefix is a code restriction, not a provider-enforced prefix ACL. The bucket has no public development URL or custom domain. The default seven-day multipart-abort rule is not backup retention or an object deletion schedule. Do not infer either from that rule.

Activation still needs the exact administrator network range, billing authorization and payment activation, registered dedicated public SSH key, independently recoverable private-key custody, three monitor check IDs and approved recipient, exact credential cutoff, and an empty isolated restore destination. Neither an unused local SSH key nor an encrypted capture proves emergency custody. The proposed server remains `aux-backup-prod-01`, Basic Regular bundled 2GiB NYC3/Ubuntu24.04, subject to actual selection/quote; the prior $17/month combined runner/R2 target is not a provider spending cap.
