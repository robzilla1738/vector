# One bounded hosted acceptance journey

Execute only after the separate current-source/configuration/activation approval. Reuse the underlying current source tests and prior development delivery. Backups and setup are deferred and excluded from this campaign. This is one new Production integration journey, not a request to repeat unchanged suites.

## Frozen inputs and limits

Record the actual new deployment ID/unique URL, service tree/lock/manifest, integrated disposable desktop candidate and current target/alias mappings. Resolve two **fresh owner-controlled test recipients** before approval; their addresses are intentionally absent here. Verify they do not identify preexisting owner production accounts. Capture every newly created Clerk/Aux/device/session/object ID in a private fixture ledger so cleanup never selects by a broad email/name match.

Proposed maximum: two new disposable account identities; two independent installations/sessions for the main account; three actual code emails total (native Resend path, hosted Clerk path, second-account boundary). Stop on an unknown send result; do not automatically resend. No old development sign-in email is repeated. At most10MiB of generated objects total, one synthetic transcript share, one private TXT, one small PNG/avatar and one paused device routine. No provider key, paid inference, checkout, hosted speech, cookie capture, owner-profile content or real-user message enters the fixture.

The current `/desktop/connect` page intentionally does not auto-sign-in a browser profile from a web login or invent a localhost callback. Use the supplied browser email-code UI for its native path, and the actual hosted Clerk session/token-exchange contract for the portal/session boundary. A successful website login is not native sign-in acceptance.
