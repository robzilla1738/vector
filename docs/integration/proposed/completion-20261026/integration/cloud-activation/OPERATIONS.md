## Incident, maintenance and rollback ownership

The owner names the operating/incident administrator before enablement; no external operator is assigned by this packet. That operator monitors failed capture, failed expiry, missed heartbeat and expiry warning; knows how to disable only these three timers/owned units; and keeps independent recovery access. A functioning API/uptime monitor is not backup success.

On unknown capture/delivery/delete outcome, preserve active.json, process-independent lock and exact authenticated job/inode bindings. Do not recapture, clear stale locks by absent PID, remove arbitrary metadata or copy an unfinished job to a new filesystem. Use only reviewed `resume REVIEW_JSON JOB_ID` or `resume-expiry REVIEW_JSON` after actual writer/control-group closure and exact-job review. The existing wrapper deliberately has no generic reset/purge command.

Runner rollback stops/disables owned timers/units while retaining pending intent, original key and remote ciphertext; point only to a compatible pinned code release. Do not destroy the server, revoke the only recovery key, rotate the production wrapping key or delete unfinished jobs as rollback. R2 renewal stops timers/units first and updates only the approved bucket-specific key/deadline after uncertainty review. Decommissioning and restore/cutover are separate decisions.

For the scheduled-output restore, record a real new unserved Neon target and private Blob destination before writes. Existing historical branch is deleted. Development Blob was approved for synthetic historical drills, not an automatic new recipient for real Production content.
