## Armored recovery labels are plaintext, not ciphertext format

In `recovery-key-CPOQuYx2.js`, `A()` writes a text file containing BIP39 words between `m`/`h`. `E()` extracts that block; `B()` then invokes the existing unchanged BIP39 checksum decoder. The labels are not a KDF domain, AAD, encrypted-envelope discriminator or stored cryptographic record.

New files use explicit `BEGIN AUX RECOVERY KEY V2` / `END AUX RECOVERY KEY V2`. The paired reader accepts exactly one new block or one known original `BEGIN ASIDE RECOVERY KEY` / `END ASIDE RECOVERY KEY` block, preserving the mnemonic unchanged through the original normalizer and decoder. Duplicate, mixed, reversed, empty or incomplete recognized blocks and unsupported version headers fail with an actionable error. Plain phrases and numbered-key input continue through the original parser. There is no automatic file rewrite, no fallback decryption label and no existing export/ciphertext reinterpretation.

The original BIP39 dictionary, entropy generation, checksum, byte/base64 conversion and recovery calls remain unchanged. Desktop separately updates explanatory filename/instruction text; it must retain the literal old markers in this explicit legacy reader rather than globally branding them. The separate `aside.recovery.auk.v1` validator in the types asset is a closed unused encrypted-setup graph handled by `aux-closed-recovery-ui.mjs`, not this text transition.
