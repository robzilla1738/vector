# Actual native profile-writer custody integration map

This read-only map pins the **currently applied** Chromium sources, including Aux changes. It adds no native patch, build, profile action or approval. The present native code has useful bounded admission/drain pieces, but no aggregate whole-profile custody coordinator. Neither a flush, profile destructor, PID census, singleton, advisory lock nor a success Boolean supplies that missing authority.

## Profile/storage teardown is not a ready-made migration acknowledgement

`ProfileImpl::~ProfileImpl` destroys OTR profiles, runs the real interlocked two-phase keyed-service shutdown, shuts policy providers down, then calls `ShutdownStoragePartitions`. This is an irreversible profile-destruction lifecycle; using it as a live migration toggle would disturb existing browser/UI ownership and does not produce a typed whole-writer completion value.

`BrowserContextImpl::NotifyWillBeDestroyed` marks shutdown, invokes loaded-partition destruction notifications, conditionally cancels navigations and disables RenderProcessHost keepalives. The storage-partition notification explicitly shuts down service/shared worker machinery because it can retain renderers. Those calls are useful concrete owner boundaries, but none is an authenticated aggregate backend-closed callback. `ShutdownStoragePartitions` resets the map and related browser-context services; it is not a cold-start reservation or reopening permission.

The source itself disproves the shortcut “profile destroyed means no writes”: `ProfileManager::UnloadProfile` warns that pending tasks can write after Profile destruction and that LevelDB locks may remain. Ephemeral/deletion handling can schedule `NukeProfileFromDisk`; **never invoke that deletion path for migration**. `ProfileDestroyer` waits/observes owned renderer hosts and has timeout-driven destruction, but its timeout is not successful storage-drain proof.

Concrete backend gaps:

- `StoragePartitionImpl::Flush` only calls DOM storage Flush; it is not a comprehensive cookie/IndexedDB/extension/prefs barrier and does not close admissions.
- `DOMStorageContextWrapper::Shutdown` resets local/session control remotes and observers. Flush sends Mojo calls. Neither method returns a durable all-backend-closed acknowledgement.
- `IndexedDBContextImpl::Shutdown` posts work to the IDB sequence; the UI call returning precedes that work. The backend has `ForceClose(..., callback)` with an explicit `delete_bucket_data` parameter, but an individual bucket callback is not aggregate profile exclusion and the destructive purge path must not be repurposed. A future nondeleting drain must bind real owned bucket/connection operations and their completion, not infer them from a UI task queue being empty.
- `PersistentPrefStore::CommitPendingWrite` has actual write-completion callbacks, useful after admission closes. They confirm that store's pending writes, not the absence of future writes or completion of other services. Session-service shutdown also flushes Aux workspace state before closing services; keep that final write ordered before any snapshot.

## Smallest coherent next implementation slices

1. **Native participant admission, source-implementable now:** a profile-scoped, generation-checked owner that closes new/queued ProfileManager creation, browser navigation/reuse/renderer launch, extension activation/retry and Aux snapshot scheduling. Hook actual entries above and acknowledge only their own admission/pending-generation state. Retain process handles/objects for owned work; do not discover/kill arbitrary PIDs. This can be implemented as a bounded admission participant, but must remain inactive until the trusted coordinator supplies real scope and lifecycle ownership.
2. **Owned normal shutdown observations, source-implementable now:** retain and aggregate direct-daemon result plus the separate carrier snapshot, then add explicitly scoped profile/renderer/storage completion observations to normal teardown. Distinguish admission-closed, no-owned-work and exit/closed-observed from timeout/error/unknown. A renderer acknowledgement must include pending launches and live reuse; a storage acknowledgement must come from its actual sequence/owner. Do not name an incomplete aggregate “all writers.”
3. **Cold-only migration, preferred supported ordering:** keep state2 before-state entry refusal; arrange an owned normal shutdown of the accepted disposable cohort, wait for explicit owned participants/backend closures, and execute migration before any new ProfileManager/renderer/extension initialization. Profile destruction can be part of genuine normal shutdown, not a reversible UI pause. Reopen only through a new reviewed accepted generation after durable terminal verification.
4. **Still blocked on actual trusted coordination:** authenticate exact browser/profile/Aux-home/cohort scope, prevent all separately invocable CLI/runtime/helper and escaped descendants from opening it, bind current on-disk snapshot lineage, and consume real typed participant observations in the migration/host handoff. Current native source lacks that whole-cohort coordinator and enforceable handoff. Merely adding the local gates above cannot retroactively constrain an old uninstrumented process or certify exclusive storage custody.

No API or runtime activation is implemented by this audit. Existing UI and profile persistence behavior remain intact. The actionable next code work is bounded admission/observation plumbing; the unsafe shortcut is to accept a synthetic receipt after flush/shutdown calls and run migration against a live profile.

`source-map.json` records hashes, exact source anchors and current line positions. `verify.py` only rereads those static source files and checks their pins/anchors; it runs no build, process enumeration, native loader, profile/OS action or protected operation. Paths/lines are a snapshot and must be re-pinned if the integrator changes these sources.
