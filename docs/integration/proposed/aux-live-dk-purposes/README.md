# Inactive remaining live DK-purpose composition

This proposal prepares actual bytes and paired source consumers for the three live non-CSK DK uses found in the pinned supplied daemon audit. It does not activate startup, rewrite owner files, execute the supplied addon, query Security, launch the daemon, call providers, or change UI. Original domains are confined to external `source/prepare.mjs` and synthetic fixture/audit inputs. The new runtime and its Aux crypto/parser dependencies contain no original product bytes.

| Boundary | Exact original contract retained | Explicit Aux-v2 change |
| --- | --- | --- |
| Skill cache | Purpose `skill-cache.<skillName>`; plaintext JSON `{cachedAt,expiresAt,value}`; ChaCha20-Poly1305, nonce12, tag appended to ciphertext. Writer still serializes metadata/value, writes mode0600 and chmods; reader still decodes JSON. Cache path/account routing stays in original caller. | Explicit `aux.dk.v2` envelope; HKDF-SHA256 empty salt and AAD `aux.dk.<purpose>.v2`. Runtime purpose retains arbitrary supplied skill names, including slashes/dots/Unicode; cache JSON content and size follow the supplied caller. Only versioned envelope shape/purpose/cryptographic authentication is enforced. External importer stays bounded and conservative. |
| Context evidence | Account-specific HKDF key; AES-256-GCM; raw `nonce12 || tag16 || ciphertext`, **no AAD**. Same source key memoization and actual encrypt/decrypt functions. | Key info `aux.dk.context-awareness.evidence.<account>.v2`. No header is invented or prepended; external prepared receipt identifies `aux.context-evidence.v2`. Only new key is tried; old/wrong-account ciphertext fails authentication. |
| Daemon auth | Purpose `daemon.auth.token.v2`; actual HS256 JWT issuer, TTL, audience/issuer, browser-subject restriction and shared session verifier stay as current Aux-protocol source. | The single shared cached key getter derives `aux.dk.daemon.auth.token.v2.v2`. This double `v2` is intentional: original purpose already ends `.v2`, outer domain version is `.v2`. Every issuer/verifier must transition together and cached keys must be retired. |

`prepareLegacySkillCache` takes bounded original bytes/hash, expected purpose and same captured installation DK. It authenticates old-envelope input, reseals and verifies exactly the original plaintext bytes, returning only replacement encrypted bytes and lineage. Cache owner/account is not encoded or authenticated by the original envelope (purpose contains skill name only); the preparer does not pretend to add an ownership guarantee. Caller must retain exact authorized path/account routing and original hashes in the durable transaction. Valid JSON values/prose are not rebranded or recursively transformed. Only the known cache metadata representation is accepted.

`prepareLegacyEvidence` requires original bytes/hash, explicit original variant and integer account ID; authenticates the exact original account-specific key, reseals with new label and verifies byte equality. It retains container length and plaintext content, never re-encodes image/document bytes or invents AAD. The variant string is an input constraint, not evidence of snapshot provenance or writer custody. Each file/captured row still requires actual owner/path/custody admission. Empty evidence is representable as a valid 28-byte container; malformed/truncated/unknown authentication fails. External capture budget is 16MiB. External cache snapshot budget is 2MiB, and external evidence capture budget is 16MiB; larger or other captured source variants explicitly refuse. These are importer budgets, not new runtime file/content restrictions. Runtime cache reader still uses ordinary JSON.parse and the actual writer retains any JSON value accepted by the supplied source.

Auth tokens are not encrypted records to rewrap. `prepareDaemonTokenRotation` expressly records invalidate-and-reacquire with `oldTokenResigning:false`. It does not accept old JWTs, impersonate a client, preserve stale authentication or sign a migration token. After coordinated issuer/verifier rollout, clients must use the existing installation challenge/session exchange again. Existing dev installation-signature verification remains unchanged and distinct from this derived HS256 key. No stale/old-key fallback is introduced. Cold reload and worker/key-cache retirement are actual prerequisites, not supplied by this preparation.

`source/adapt.mjs` makes four count/hash-pinned exact-source edits: cache reader and writer, evidence key resolver, and shared token-signing-key getter. It imports fixed sibling `./aux-live-dk-runtime.mjs` and returns `activation:false`. Both the exact base state2 composed daemon and the exact earlier CSK-v2-prepared source are accepted, allowing explicit composition. No global `deriveSubkey`, `DK_SUBKEY_INFO_PREFIX` or `DK_WRAP_INFO` replacement is performed. The full bundled source still contains original generic-domain definitions and excluded Vault/Windows fallback code; safe final exclusion/materialization remains work, and this proposal does not claim full-app no-trace or Windows/cloud compatibility.

Focused check: `node docs/integration/proposed/aux-live-dk-purposes/tests/check.mjs <explicit frozen daemon-original.mjs path>`. One fixture covers each changed boundary using fixed synthetic DK/material and the actual extracted/adapted consumer function structures. Cache uses captured memory IO; evidence uses actual source AES-GCM functions; auth uses exact extracted JOSE producer/verifier calls with a real Node HS256 fixture adapter. The bundled JOSE library and app initialization are not executed. It checks old→new authenticated data continuity, actual new writes/reads, wrong purpose/account/key-domain refusal, issuer plus both verifier sharing, old-token rejection, and exact source composition with CSK preparation. Unchanged CSK fixtures are not repeated.

Remaining before activation: native authenticated same-DK capture, stopped cohort admission and old selection retention, actual durable multi-file preparation integration with every original hash, precise cache/evidence path inventory and ownership, coordinated token producer/verifier/client reacquisition, private runtime asset graph materialization, old generic/Vault/Windows code exclusion, and bounded disposable real integration. Module source paths are review-source dependencies, not a deployable single-file asset. No signing, grant, Keychain or owner-profile authority is implied by passing fixtures or receipts.

Runtime compatibility correction: the focused `tests/runtime-source-compatibility.mjs` executes actual adapted cache functions with a slash/dot/Unicode skill name, an additional JSON field and a value over2MiB. It passes without repeating unchanged migration/token/evidence fixtures. The external importer's stricter known-record validation remains explicitly separate from runtime behavior.
