# Actual loaded PDF image lifetime consumer

The production worker host now consumes the real PDF native close/pending exports during **explicit** `AuxDevelopmentWorkerHost::CloseAndDrain()`. It captures the fixed already-loaded PDF image only after `AuxCreateSignedDevelopmentOwner` succeeds. That actual producer authenticates the sealed policy and loaded-image signatures/identity/file pins; the new C++ path/hash checks do not replace that authorization or mint profile admission.

`AuxLoadedPdfLifetime` derives `Contents/Resources/native/aux-pdf.node` solely from the real running bundle executable. It inventories actual non-system dyld images, rejects duplicate/aliased/misplaced modules, hashes an owned regular no-link/no-write file with before/after FD metadata, and accepts only the two immutable current/historical own-PDF pins. It obtains a reference with `RTLD_NOLOAD|RTLD_LOCAL|RTLD_NOW`, never loads a new image, and resolves each symbol ONLY from that handle. `dladdr` must identify both pointers as the exact observed image path and Mach-O base; there is no process-global symbol fallback. Future signing/module changes require new reviewed pins.

- v1/no PDF: absent remains compatible; no PDF image is silently loaded.
- v2/old reviewed PDF: registration ABI remains compatible. Explicit close reports untracked and never invokes nonexistent close exports.
- Current reviewed PDF: actual native close plus pending are consumed. Pending is never promoted to drain; wrong-process/refused/changed or late-image conditions cannot become success. A status observation without explicit closure does not imply drain.

Ordinary environment cleanup does **not** initiate process-image-wide PDF closure. The PDF reference lives on Worker independently of the command Owner, so cleanup can retire a command owner without losing the later host-close target. A host-close intent racing factory/cleanup remains sticky; unresolved PDF intent prevents the existing process registry from releasing the worker. Pending/untracked exact image contexts are additionally held in native process-lifetime quarantine, including when host destruction drops State. Quarantine entries are removed only after actual observed drain/not-present. No host/worker mutex crosses PDF native calls. The retained NOLOAD reference is intentionally not unloaded by a destructor that cannot prove complete custody.

The new build recipe links `pdf-lifetime.o` into the actual production worker graph and existing software fixture graph. Existing historical source/evidence pin receipts are preserved; `inputs.json` is a separate successor inventory, not a claim the older43 lifecycle tests ran against these changes. The actual changed WorkerHost C++ translation unit compiled after the last sticky-intent fix. The real consumer plus its TEST-only Node producer compiled/linked; four focused disposable-Node scenarios passed: absent compatibility, real current operation getter reentry returning pending then drain/permanent seven-method refusal, late image untracked, and old reviewed module untracked. Pending quarantine count was1 during the active real operation and0 after actual drain. No PDFium rebuild, browser/package rebuild or unrelated method/lifecycle test repetition occurred.

The TEST producer has no scope/path/handle inputs and invokes no signed factory. It runs the same fixed-path capture against copies of the pinned frozen Node and own reviewed PDF modules in a disposable `.app` shaped directory. It is not a production initializer or authority grant. Only one synthetic document is read; the two copied modules are Aux-owned builds, never the original common native addon. Temporary bundle/home/documents are removed. Production signed-policy loader/factory, protected imports, OS utilities and real worker attachment were not executed.

## Limits

The PDF module's own admission PID is lazily initialized on its first native operation/count call. Capture therefore calls the actual pending export immediately in the captured parent before publishing this capability. This establishes subsequent-fork refusal for that captured lifetime. It does **not** prove rejection of a fork that precedes capture/first use; fixing generic module-load PID semantics requires a separate module rebuild/review. The consumer checks its own capture PID before any inherited mutex or function call.

Closure affects the loaded image across all process workers. It belongs in a real final process/cohort shutdown, not arbitrary per-environment cleanup. A zero-ever-registered host has no authenticated PDF capture and its result covers only its owned registrations; it cannot certify all process PDF writers. Changed/late non-system image inventory remains untracked. There is still no accepted trusted production module/bootstrap/preload consumer owning the complete profile, renderer, CLI, descendant, browser storage and crash-recovery interval. The native factory's caller-held writer-admission prerequisite remains unmet. State2 startup refusals, accepted app, UI/assets/CSS/geometry, signing/provider/owner state are untouched.
