# Installed-web-app session writer in loaded-profile close

Source-only successor for the actual loaded session-writer participant. Two exact current native inputs and eleven count-one edits are pinned in `inputs.json`. No checkout, shared GN, aggregate owner, UI geometry/assets, provider, profile, service factory or startup acceptance is changed or invoked by this proposal.

The gap is a **separate real writer**, not another view of SessionService. Actual AppSessionService is a SessionServiceBase sibling constructed with `kAppRestore`. The base selects a distinct app backend task-runner key and AppRestore CommandStorageManager. AppSessionService's reset builds commands using its app browser filter, and its destructor saves/destroys that same manager. Closing only the ordinary SessionService cannot close this sibling manager. `service-contract.json` pins these actual source anchors and the shared manager/backend completion implementations.

The participant now captures both existing sibling services for every loaded-profile inventory row. Browser observation fields remain unchanged; a separate `app_session` record retains installed-app outcome/write/close observations. Lookup uses only `AppSessionServiceFactory::GetForProfileIfExisting` (`GetServiceForBrowserContext(profile,false)`). It never calls GetForProfile, GetForProfileForSessionRestore, ShutdownForProfile or WebAppProvider. The factory shutdown route would force service creation and SessionData cleanup and is deliberately excluded.

Actual app final writes call inherited `ResetFromCurrentBrowsersWithWriteCompletion`: app-specific virtual command reset followed by real SaveWithCompletion. Actual close calls the inherited manager/backend admission-and-close seam. Raw write/backend results pass through unchanged, including disabled saving, encryption/deferred work, failed write, rejected task and owner loss. No absent or failed callback is converted into a successful close.

Both sibling submissions stay inside the **same** existing write/close submission windows and pending counters. A synchronous/nested browser callback cannot advance before the later app submission has occurred. The weak profile is checked again before the separate app lookup because an earlier browser write may reenter destruction. Each weak app-service owner and callback outcome remains independent from the browser-service owner. Dropped asynchronous callbacks retain the existing participant's pending accounting/self-retention; there is no timeout/destructor success.

Root can apply the complete two-file `followup.patch` and integrate the appended record into its existing native composition. The already-used `//chrome/browser/sessions` declaration target exports AppSessionService and its factory under enable_session_service, so no new service/provider dependency is needed by this source. Root owns any GN or aggregate changes. No ordinary shutdown hook is added.

This covers only services already owned by the captured loaded profiles. Later factory creation/restoration, different profiles, app installation/update systems, WebAppProvider storage, running renderers/worker code and other storage writers remain outside this participant. Append return and backend file-object release are not fsync/durability or whole-profile exclusion proof. The state-2 cold refusal remains unchanged.

`verify.py` checks exact source replay, independent app results, existing-only lookup and nested submission guards. `compile-check.py` prepares one real changed-TU compile with current GN flags/read-only VFS mapping plus one captured accounting/schema fixture. No compiler or fixture was launched in this lane while root's build and earlier requests hold the native lock. Compiled/runtime evidence must be recorded separately.
