# Versioned Aux cryptographic identity

This is an inactive, implementation-level migration proposal. It changes no existing adapter, schema, manifest, native registration, package, UI, profile, Keychain row or accepted app. No signing, native addon execution or provider request occurred.

The owner's 2026-10-22 identity override requires Aux-only delivered identity while retaining existing data and the current UI. Domain labels are authenticated format inputs: changing their spelling without a versioned migration destroys decryption compatibility. The accepted app stays intact until a complete successor is verified.

## Implemented hooks

`vendor/provided/aux-crypto-identity.mjs` supplies Node implementations using the same HKDF/ChaCha20-Poly1305-IETF primitives:

- `deriveAuxSubkey`, `encryptAuxBlob`, `decryptAuxBlob`: new explicit v2 writes/readers. Unknown versions and legacy/unversioned input fail closed. No retry under another label after authentication failure.
- `wrapAuxDk`, `unwrapAuxDk`: explicit v2 P256 wrapping. The injected ECDH callback must use the existing installation KEM key; no initialization/reset/generation fallback is provided. It returns an owned temporary shared-secret buffer, which is erased after use.
- `migrateAuxBlob`: accepts a caller-read, version-pinned snapshot; explicitly calls an injected legacy reader; creates a v2 envelope; decrypts/verifies it; then invokes a storage compare-and-exchange callback with a cloned expected value and exact revision. Conflict or failure never reports success. Input/source/key buffers are preserved; owned temporary plaintext is erased. The caller's CAS must atomically compare both serialized expected record and revision and retain recoverable original bytes in its migration journal.
- `prepareAuxInstallationMigration`: calls an injected, already-authorized legacy DK unwrap, rewraps exactly that DK to the same public KEM authority, verifies through that authority and returns an additive candidate/metadata. It performs zero IO. The injected unwrap returns an owned temporary DK, erased before return. It rejects unsupported schemes; it never downgrades PQ or enclave authority into a new software identity.

The separate `aux-crypto-identity-legacy.mjs` is an explicit read-only migration input with the truthful original labels. It is **not** imported by the Aux-only module. Exclude it from the final runtime once the authorized migration is complete. Encoding or hiding old strings in the final app would not satisfy the owner's request. Keeping a legacy reader indefinitely is transitional compatibility, not completed Aux identity.

## Integration sequence and crash safety

1. Inventory only the disposable/authorized Aux state by owner, persisted format and generation. Preserve exact encrypted source records; do not enumerate/read owner's Aside state. Distinguish absent, inaccessible and partially present authority; never treat an error as a fresh installation.
2. Add explicit versioned schemas at every encrypted-blob consumer. The current `encryptedBlobSchema` contains only three fields; a parser that strips `format` would erase the new version marker. Update every serialization/parse/read/write path together, including SQL/JSON/cloud boundaries, before introducing any v2 writes. Local `encryptedBlob` migration is not a generic migrator for differently encrypted cloud file or recovery formats.
3. Keep the installation signature/KEM keys and root DK unchanged. Prepare the additive v2 wrapper, verify it and persist a durable migration journal plus new record using a reviewed storage transaction. Record original revision and public authority fingerprint, not plaintext/keys. Keychain has no multi-item transaction here: use an explicit journal/read-state machine, not an assumed atomic two-row replacement. A crash leaves the original installation usable; an incomplete new record is never selected as authoritative. This proposal does not implement that native persistence transaction.
4. Migrate local records with explicit old-format reads and per-record CAS. Journal completion only after actual durable write acknowledgement, then read/decrypt the persisted v2 record. Retry from actual record versions after interruption; never infer completion from an in-memory result. Preserve old records until all dependent consumers and rollback behavior are accepted.
5. Root-derived ephemeral auth token keys can move to Aux v2 with the coordinated protocol rollout; old local bearer tokens expire/re-authenticate instead of being interpreted under a different key. Separate user/device session state from those ephemeral tokens; do not force sign-out/delete account credentials to simplify migration.
6. Account-sync derivation changes require a new generation: freeze capture/upload per binding, stage versioned re-encryption of that user's cloud payloads and recovery envelope, verify all objects, CAS the active generation, then resume clients. A version marker must select the existing CSK until completion. Never derive a different CSK for the same active sync generation. Server/client generation and recovery support remain separate work.
7. Only after all authorized state is durably migrated and the new native authority implementation is accepted can the final package omit legacy readers and format literals. Acceptance must cover interrupted migration/restart, stale concurrent writers, locked/inaccessible authority and multi-profile ownership. The current seven fixtures are deliberately narrower than this product acceptance.

## Immutable native constraints

macOS `unwrapDk` delegates to original `runMacInstallHelper("dk-unwrap")`; changing JavaScript's `DK_WRAP_INFO` does not change its native wrapping. The original addon embeds product names, original access group/selectors, Swift string lengths and ARM64 inline small strings. Its installation code includes P256 software/Secure Enclave and PQ paths. The existing mapper isolates queries as `aux.<scope>.<original logical name>`; this is isolation but still retains the original name and therefore does not meet final Aux-only identity.

A new reviewed native implementation or complete instruction/data patch must support both authorized old readers and explicit Aux writes while retaining the same private authority. It must preserve DP/enclave ACL semantics and journal record migration. Replacing ASCII occurrences alone is unsafe, and this P256 hook does not claim native PQ support. Do not re-sign/replace the immutable addon, reinterpret existing native ciphertext, create a replacement authority or call `install-init`/`destroy-keys` as a migration shortcut. No new signing or Keychain authorization is granted by this proposal.

## Lean evidence and remaining gaps

`node --test vendor/provided/aux-crypto-identity.test.mjs` passes seven synthetic checks: WebCrypto-equivalent HKDF/new-domain separation; explicit format/purpose/tag denial; verified/idempotent CAS migration; conflict/corruption/unknown-version refusal; existing-authority P256 wrap; same-root legacy-to-v2 preparation; and wrong-authority/unsupported-scheme refusal. The legacy fixture implements the inspected wire algorithm with Node's ChaCha20-Poly1305; it does not execute the original sodium/native addon.

These results prove the new pure hooks on synthetic bytes. Native migration persistence, actual DP authority, PQ/enclave behavior, complete consumer schema integration, cloud generation migration, final package zero-brand audit and actual desktop acceptance remain unimplemented or unverified. No UI files are part of this change.
