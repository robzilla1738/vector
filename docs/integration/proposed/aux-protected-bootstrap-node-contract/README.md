The supplied frozen runtime's public `node.h`1364–1400 exposes `node::AddLinkedBinding(Environment*, ...)`. Its own contract says the target Environment and **all Worker threads it creates** can access the binding through `process._linkedBinding()`, and the registration function must remain usable for the Environment's lifetime. Thus registering once is not an admission proof for every future worker or a lifetime guarantee for a native captured owner.

The NAPI overload accepts `napi_addon_register_func` plus an API version, with no owner argument. `node_api_types.h` defines that callback as `(napi_env env, napi_value exports) -> napi_value`; it receives no trusted Aux WorkerHost/custody reference from JS. The alternative V8 `addon_context_register_func` overload accepts native `priv`, but does not itself supply the `napi_env` required by the current WorkerHost API. `napi_module` contains private/deprecated registration fields; their existence does not establish a current Aux producer or permission to reinterpret an arbitrary pointer as an owner/environment.

Actual Aux source exposes only `AuxDevelopmentWorkerHost::RegisterCurrentWorker(napi_env, target)`. Its implementation validates actual current V8/Node Environment/event-loop identity, reserves one Environment, installs cleanup ownership **before** invoking `AuxCreateSignedDevelopmentOwner`, and retains pending/late owners and loaded-image custody. Its public contract explicitly says construction establishes process-local ownership, **not cohort admission**. Current non-test source has its declaration and definition but no production call site or linked-binding registration producer. `AuxAttachSignedDevelopmentDispatcher` is a refusal tombstone and cannot be used as a shortcut. The tests' module initializer is explicitly synthetic and is not a production loader.

There is also a real order requirement: the signed loader authenticates the already-loaded fixed native runtime image and, for the corresponding daemon policies, exact PDF/utility images before the protected owner factory can succeed. A JS wrapper cannot turn a file path/hash into that native admitted lifetime or load the runtime through a nonexistent module initializer. Preloading by a real native embedding can be a future implementation path, but it must first receive actual lifecycle/cohort authority, own those exact image references, register the actual Environment/descendant worker callbacks, and retain/drain them using the existing real WorkerHost methods. A new global selected handle, environment variable, untrusted receipt or standalone `require()` initializer would not provide that authority.

The still-delivered common binding route remains the fixed `aux-native.cjs` seam, which conditionally prepares the old guard then loads pinned `provided-native.node`. Merely replacing its require path with `aux-runtime-owned.node` cannot work: the latter intentionally has no production `NAPI_MODULE` initializer and no caller currently transfers genuine admitted ownership into an Environment. The new atomic registry callback makes the mismatch explicit rather than silently falling back: the old binding does not provide the paired `withAccountRegistryLock` operation. Removing the unconditional state2 throw to test that path would bypass the still-missing admission boundary; this review did not do so.

The next production change therefore belongs at the **real native embedding/admitted process/worker bootstrap**, not another source-only JS capability façade. After that concrete producer exists, its fixed linked-binding/native-registration consumption can be paired with daemon/CLI synchronous and worker loaders and the original common addon can be retired against the existing command/export inventory. Those remain genuine implementation/acceptance gaps, not tested successes.
