# Exact unsigned successor assembly

`prepare.py --help` produces the exact recipe from successful browser/daemon/source/entry receipts and existing static inputs. `assemble.py RECIPE.json` assembles a fresh inactive candidate from the successfully rebuilt native app, never the old warm native objects. It requires explicit hashes of the successful browser receipt, complete source-native and baseline-app inventories, successful unchanged-input daemon link receipt, and every source/replacement leaf. The browser receipt must contain stable complete app inventory and unsigned Mach-O evidence. Native Mach-O files are independently checked for signatures. Contained links, exact native receipt leaf coverage and modes, the five unique fixed replacement leaves, source immutability and every unrelated supplied resource are checked. Output cannot be nested inside either source app.

The copied current supplied resource tree is overlaid into the fresh native app. Explicit replacements select the exact daemon, contained PTY, refused ordinary index, dormant native entry and native loader. The old source app is never edited. The result records its complete inventory and exact receipt/recipe provenance. All other resource leaves, including UI CSS/assets, must compare identically before success. Failures leave a distinct failed candidate and failure receipt rather than declaring acceptance.

Recipe fields: `output` (new absolute directory), `baselineApp`, `baselineInventorySha256`, `nativeApp`, `nativeInventorySha256`, `nativeReceipt`, `nativeReceiptSha256`, `daemonReceipt`, `daemonReceiptSha256`, and `replacements` containing fixed relative `path`, exact `previousSha256`, absolute `input`, `sha256` and `mode`. Inventory digest is SHA256 of the sorted compact JSON leaf array produced by the assembler (regular file hashes/modes and contained link targets/modes). These pins must be prepared from completed build outputs; the build currently has no successful receipt, so no executable recipe is fabricated.

The assembler is source/syntax checked only. Actual assembly, post-package runtime acceptance and UI comparison remain pending successful browser build and final lane integration. It intentionally records `testable:false` and no runtime authority: packaging cannot supply missing browser drain or startup authorization. No signing, release or accepted-app replacement is performed.

A focused inert temporary-files check passed for receipt normalization, mode-change refusal and extra-leaf refusal. Its first run used an incorrect assumed macOS symlink mode; the corrected check reads the actual link mode. No executable was built or run. Actual final assembly is still pending.

The recipe now requires `--source-pair` and binds all five inputs to that exact frozen tuple. Both preparation and assembly verify source/entry receipt paths and hashes, including the entry projection’s source-receipt hash, and the paired daemon-link receipt hash. A focused check accepted the current final tuple and refused a mixed daemon and changed source receipt; this does not execute any product.

Assembly preserves the pinned outer `Contents/Resources/package.json` Node scope boundary, updates `finalApp` and current projection/native metadata, and archives superseded declarations under successor baseline metadata. Original delivery provenance stays labeled historical. This prevents the new app from declaring the old app path or old daemon/entry hashes as current. Runtime provenance/task-root integration is being corrected separately before final assembly.
