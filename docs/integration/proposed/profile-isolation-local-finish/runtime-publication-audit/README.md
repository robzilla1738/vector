# Runtime cache publication audit — inactive interface proposal

The current native interfaces cannot publish the runtime directory atomically and exclusively. This batch changes no native ABI, daemon recipe, runtime seed, bootstrap, executable, runtime distribution, UI or accepted app. The coupled native recipe must be reviewed before implementation. `evidence.json` pins the actual copied seed and matching linked native sources/receipts; this is an implementation blocker, not runtime acceptance.

## Actual behavior and available interfaces

The copied `runtime-seed.cjs` first prepares a complete sibling staging directory, then creates an empty `runtime` exclusively and moves its children one by one, ordering `version.txt` last (lines 114–125). A process crash after reservation or any intermediate move can expose an incomplete runtime directory. Writing the version last is not atomic publication.

**A preexisting safe runtime directory is retained without completeness validation.** Both the early check and racing `EEXIST` branch return `{retained:true,seeded:false}` after directory/ownership/mode checks. The seed itself does not reject a partial cache, verify its version, or prove it is usable. Downstream supplied validation is a separate boundary. No existing cache may be deleted, overwritten or adopted as a verified distribution to repair this gap.

The actual linked WorkerHost is SHA `e36e5c25c822879302a7f83fa5329305ba79f4d000ac45cd721cb820eaa81dd7`, compiled as object `d9847f322f8da7a58b737ffc94b12c8c1702974cbbe215208f48c2754c53c17e`. Its dependency receipt selects the audited `AuxStorageRootsNapi.inc`; the exact daemon link receipt includes that object. Registered broker methods are `captureStorageRoots`, `assertBrokerOwner`, `withBrokerSync`, `withBrokerAwaited`, `closeBrokerWriteAdmission` and `noteUntrackedBrokerWork`. None publishes directories.

`AuxNativeContextCopyStorageRoots` already duplicates authenticated control/task directory FDs with a native transport generation. `captureStorageRoots()` converts them to locator strings and closes both duplicates on return. The frozen JS snapshot grants no FD-relative filesystem operation. `withBrokerAwaited` retains finite-operation custody; it cannot turn JS pathname renames into an exclusive native transaction. The matching `AuxNativeTaskLayout` supports authenticated FD duplication, `mkdirat`, `openat`, identity checks and fsync, but no `renameatx_np(RENAME_EXCL)` publisher. No such primitive exists in the audited host/root/dispatcher seams.

## Concrete minimal successor proposal — not implemented

Add exactly one readonly/nonconfigurable NAPI method, `publishRuntimeSeed(stagingName, expectedOwnerGeneration, expectedTransportGeneration, expectedStageDevice, expectedStageInode)`. All values are strings. The staging name must be one basename matching the existing generated `.aux-runtime-seed-` naming scheme, never an absolute path, slash-containing name or destination selector. The decimal generation/device/inode values are mismatch checks, never authority. The native method derives Worker, Environment, Owner and owner generation from its current registered native context; callers cannot supply an Owner or FD. Publication always targets the literal `runtime` child.

The proposed paired C seam is described in `proposed-interface.h`. It must execute inside the actual retained native Owner's admitted action lifetime, using the actual retained task-root capability and matching transport generation. Obtain and retain the staged directory FD with `openat` plus `O_DIRECTORY|O_NOFOLLOW|O_CLOEXEC`; check ownership/mode and the native entry's device/inode against the completed stage. Revalidate actual owner, task-root identity and generation at the publication boundary. Call `renameatx_np(taskFd, stagingName, taskFd, "runtime", RENAME_EXCL)` exactly once. There is no preceding destination reservation and no fallback to ordinary rename. `EEXIST` retains the destination unchanged and reports only existence, never completeness. Other refusals leave existing caches untouched. A successful rename followed by a failed authority/durability check is an unknown outcome, never rollback, destination deletion or automatic reseed.

Count-checked JS changes would be limited to: (1) capture the new immutable native method alongside the two existing bootstrap methods; (2) pass a bound operation into the seed with the existing native generation snapshot; (3) replace the single reservation/per-entry-publication block with the single awaited publication call after all existing copy/hash/relocation/symlink work settles. Staging creation/copy, nine exact text reversals and all runtime executable bytes remain supplied behavior. Cleanup must distinguish unpublished owned staging from a successfully renamed or uncertain destination; never recursively remove `runtime`.

## Exact open implementation work

The new NAPI/C method is absent, its native action admission and error/outcome contract are unimplemented, and the daemon recipe has not been changed or rebuilt. A future implementation must establish namespace custody between stage-entry identity checking and the atomic syscall; a separate `lstat` or JS marker does not make source identity atomic against another writer. Concurrent native retirement must be serialized with publication or recorded as unknown. These are required native guarantees, not proven properties of this proposal. The exclusive syscall prevents destination replacement; it alone does not prove pin completeness, fsync durability or resistance to arbitrary same-UID stage mutation. No new root selector, environment authority, cache migration or persistent completion marker is proposed.

The focused future check set is one tiny disposable payload: complete whole-directory visibility, `EEXIST` preserving an empty/nonempty directory and symlink, stale owner/transport refusal, changed-stage refusal, and unknown-outcome retention. A crash before rename must leave no `runtime`; a crash afterward must never expose a top-level partial move. That check needs the actual coupled native implementation; a fake JS publisher is not evidence of this syscall or authority contract. This batch performed only bounded hashes/counts of ten named static inputs, with no payload copy, native compilation, product/module execution, signature, network or owner-data access.
