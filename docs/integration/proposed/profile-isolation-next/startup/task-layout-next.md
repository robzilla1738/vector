# Concrete next task/control layout

A native fresh producer can create a separately authenticated task sibling, but creating that directory alone does not make the supplied daemon safe or usable. The current v4 policy parser has an exact key set and authenticates only `canonicalPrivateParent`; `AuxFreshNativeHome` reserves the selected home beneath it. There is no trusted task-root capability today. The supplied account/runtime paths include legitimate memory/routines writes beneath that home, so a blanket private-parent deny would break those tools. Merely moving `AUX_RUNTIME_DIR` leaves the account roots under the denied parent.

Next implementable source slice:

1. Introduce a new sealed policy version with an explicit canonical task-parent field and a fixed layout version. Preserve v1–v4 parsing for historical evidence, but refuse them for the new split runtime. Authenticate both actual parent directories with retained no-follow FDs, owner/mode/ACL and path/entry identity; require task/control roots to be distinct and neither nested in the other. Never take this field from JS, environment, argv or an API caller.
2. Extend the one-shot native reservation/journal with a paired task-home identity bound to the same actual transaction, generation and authenticated policy hash. Create only fixed child names through retained parent FDs with exclusive reservation and fresh inventory rules. Partial creation remains resume-only or blocked; no reset/adoption fallback. Existing marker formats need a versioned read-only refusal path, not reinterpretation or automatic migration.
3. Add native finite capability roles for the selected task home/account task projections. Carry them through the actual staged context, captured context and per-Environment Owner, exactly as the browser roots in this successor. An exposed path is a locator; retained FD identity and the same live owner/generation are the authority. Revalidate on use and fail closed after Owner closing. Do not accept arbitrary “allowed roots” from the worker.
4. Count-map actual daemon path constructors: runtime/extraction/cache roots, per-account memory/routines/workspaces and their permission roots. Private account records, provider credentials, auth state and installation journals stay in control state. Tools receive only task projections or narrowly brokered APIs. Calls that currently read whole `accountRoot` must be inventoried and split; a blanket account-root allow is not an acceptable shortcut. Root's permission/broker lane owns this caller inventory and projection contract.
5. Update fresh/resume selection, durable journal readers, provider preparation, native WorkerHost/PTY/process-spawn permission construction and exact sealed entry/package pins together. Keep old cold startup refusal until that full composition is compiled and reviewed. A new policy alone is insufficient.

Inputs needed for that source implementation are the selected v4 parser/loader, current fresh/resume owners and journal formats, actual supplied daemon account-path constructors, the permission broker consumer, and native Owner/spawn custody interfaces. These are local source inputs; no cloud account setup is needed.

Owner-dependent boundaries remain: choosing/approving the exact disposable destination and a new exact-byte local signing/protected-authority scope before any protected startup, later explicit treatment of existing owner state/credentials if migration is desired, and actual disposable UI/provider journey observation. No owner-state migration is necessary to implement and compile a fresh-only split; legacy state can continue to refuse. This source pass does not request or perform signing, credentials, profile IO or runtime admission.
