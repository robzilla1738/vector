# Aux-v2 browser Sync recovery — local backend integration

The backend routes, additive migration manifest, ordinary Sync guards and bounded maintenance are now integrated in local service source. **No real database has been migrated and nothing is deployed.** The desktop client remains inactive; real atomic publication and confirmed enrollment are still missing. The current accepted app and UI are unchanged. See [local integration evidence](LOCAL-INTEGRATION.md). The sections below preserve the initial preparation contract; the local successor completes only the backend source integration items explicitly listed in that evidence.

## Implemented

The four `services/aux-cloud/src/sync-recovery*.ts` modules use the existing Hono auth/session and server-wrapped Sync custody model. Only a live bound macOS installation session may request a 60-second operation-bound challenge. Submission verifies possession of the recorded signing key, not merely its fingerprint: actual SHA256/DER P256; explicit raw ML-DSA-65 branch refuses unsupported crypto. No Windows fallback.

`migrations/012-sync-recovery-v2.sql` is a **review artifact outside the active migration directory**. Its transaction rechecks session, account generation, challenge, recovery head and captured current server-key row. Recovery revisions append; challenge retries return the same result while the head and challenge remain current. After challenge expiry a new challenge is required; retrying enrollment with an old expected revision fails rather than creating a second backup. Recovery inserts a missing server key only; it cannot overwrite a different/stale existing key. All errors preserve the current key/generation. Challenges contain no recovery entropy or plaintext key; cached responses contain encrypted backup/public receipt only.

The Aux-v2 envelope encrypts the **existing 32-byte CSK directly**, preserving encrypted browser data. It uses a 16-byte random recovery secret (the existing 12-word UI), HKDF-SHA256 with random 32-byte salt and `aux.sync-recovery.csk.v2`, ChaCha20-Poly1305 with random 12-byte nonce, and authenticated user/generation/recovery-ID/revision binding. A CSK-keyed commitment proves the recovered CSK; enrollment additionally proves possession of the current CSK over the signed challenge. The server retains existing `aux.sync-key.v1` AES-GCM wrapping. Recovery CSK is transmitted over the existing authenticated TLS service, consistent with **server_wrapped**, not end-to-end custody. Recovery entropy is never uploaded. No password manager/Vault code is added.

The inactive `source/desktop.ts` prepares locally verified enrollment only after the user saved/confirmed their key. It retains a non-secret signed prepared enrollment for a lost-response retry. It validates the exact challenge before native signing, fences account/generation, and requires **atomic absent-or-same CSK + owner/generation publication** after the network await. This is a required real storage operation, not a Boolean authorization. A generic setter does not meet this contract; unsupported publishers must refuse. Returned read buffers are treated as borrowed; only client-owned copies are cleared. Publishers must copy the submitted key before resolving.

`source/materialize-desktop.mjs` produces a pinned standalone inactive ESM asset with only builtin external imports, using existing esbuild/Zod dependencies. It returns bytes and never patches or loads an app entry. Ninety-seven source inputs plus the retained Zod MIT notice/compiler/output hash are pinned; project-relative imports are bundled. It does not solve entry activation or native atomic publication.

## Exact supplied flow and incompatibility

Source hashes are in `source-pins.json`. Supplied `recovery-DY2UC0Rx.js` fixes the form at 12 words, decodes with `recovery-key-CPOQuYx2.js`, then sends `accounts.auth.recoverSyncKey({accountId,recoveryEntropyB64})`. Supplied `account-Dr_CA8LL.js` enrollment sends only `{accountId}`; it does **not** provide confirmed entropy. Automatically creating an unseen recovery secret there would make recovery unusable. Keep the existing form/layout; wire an actual saved/verified 12-word confirmation flow before enrollment. The shared recovery-key download wording is Vault-specific and cannot be reused for browser Sync as-is.

The old `/auth/onboarding/recovery-material` backup decrypts an AUK using original domains then derives CSK. This Aux-v2 format instead seals the already-existing CSK. It never reinterprets old ciphertext or imports old passwords. The exact legacy gap is retained in `aux-macos-crypto-exclusion/recovery-contract.json`. Existing legacy recovery remains an explicit refusal until a separately reviewed authenticated import exists.
