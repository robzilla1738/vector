## New proposal interfaces and the missing pair

The parallel fresh-policy lane defines `AuxSignedFreshBootstrapPolicyLoader.load() -> AuxAuthenticatedFreshBootstrapPolicy`. Its private construction requires live/static Security authentication of a fixed sealed policy resource and the current exact loaded-image inventory. The authenticated value's `createFreshHome()` revalidates its policy/host and calls the fresh-home lane's `AuxFreshNativeHome.create(inCanonicalPrivateParent:)`. The home object retains real directory descriptors, exposes its canonical home/scope/transaction ID, and has `validateRetainedIdentity()`, `requireEmptyBeforeAuthorityGeneration()` and `duplicateDirectoryForNativeBootstrap()` operations. Those are source-level interfaces under implementation in the separate proposals; this map does not claim their protected authentication was executed.

They do **not** currently reach the actual selected protected producer. `AuxCreateSignedDevelopmentOwner` loads `AuxSignedDevelopmentPolicyLoader`, captures the selected existing four Data Protection rows, imports that exact authority, and uses `AuxReviewedDevelopmentIdentity.home` for the atomic registry context. Its selected policy requires existing public keys/row hashes. Substituting a newly created home string into this path would neither create source-faithful fresh authority nor preserve its selected-policy contract. The new home and authenticated policy must be consumed by the actual fresh authority coordinator first; no such production caller is connected here.

The actual registration consumer is `AuxDevelopmentWorkerHost::RegisterCurrentWorker(napi_env, napi_value)`. It derives the current V8 isolate, actual Node Environment and event loop, installs cleanup ownership before invoking the protected selected factory, then publishes via `AuxAttachOwnedDispatcher`. It retains pending/late owners and exact image custody. Its header explicitly distinguishes this process-local lifetime ownership from whole-profile admission. A native C++ instance or raw owner pointer in the browser process cannot be transferred into the separately spawned daemon process through an environment string, JavaScript handle or `AUX_HOME`.

There is still no production native Node initializer or embedding call site for `RegisterCurrentWorker`; the only module producer in this graph is explicitly test-only. The frozen Node `AddLinkedBinding` contract also makes a registration available to child Workers, while its NAPI callback receives only the actual environment/exports, not an authenticated native host/custody object. The earlier `aux-protected-bootstrap-node-contract` pins that exact API constraint; it remains unchanged. Therefore adding a standalone `NAPI_MODULE` or changing a JS require path would initiate protected factory calls without producing the missing native custody/admission relationship. No registration-only source patch is safe to activate under the present caller contract.

## Concrete next implementation boundary

A real cold native coordinator must run before mutable profile startup, authenticate the separately reviewed fresh policy, retain/validate the fresh directory object, and invoke the source-faithful fresh authority coordinator without regenerating inaccessible existing state. It must then launch/own the exact daemon/CLI process family through an authenticated native channel with explicit descendant worker registration and drain ownership. The in-child real native embedding/bootstrap must consume that genuine authenticated process admission and the resulting immutable authority, preload the exact signed images required by policy, and call the real WorkerHost registration on each actual environment. Current direct helper/session/extension/async-profile component observations remain narrower than complete whole-profile custody.

No existing environment switch, sealed resource alone, hash-only image record, test factory, local Node initializer or zero participant counters supplies those missing facts. The current first refusal and selected policies remain unchanged. The corrective non-creating profile-manager accessor is a separate necessary fix; it does not solve this cold bootstrap boundary.
