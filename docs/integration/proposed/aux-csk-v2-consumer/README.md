# Inactive versioned CSK rewrap and paired consumer

This proposal supplies an actual authenticated legacy-CSK→Aux-v2 preparation and matching narrow daemon source adaptation. Nothing is installed, activated or connected to owner state. No addon, Security, provider, OS or cloud operation executes.

`source/prepare-legacy-csk.mjs` accepts only explicit bounded snapshot bytes, exact original hash, 32-byte installation DK and matching explicit owner for owner-bound records. It opens the original `csk` encryptedBlob with the original HKDF/AAD domain via the migration-only legacy reader, requires a 32-byte CSK, reseals under `aux.dk.csk.v2`, opens and compares it, and replaces only the actual encryptedBlob JSON token. All surrounding schema/account/bound-user/sync-generation/order/whitespace bytes remain exact. Bare original envelopes are supported only as explicitly ownerless input; supplying an owner expectation cannot promote one to owned. Duplicates, unknown schema/version, wrong owner/key/hash/purpose, wrong CSK length and already-v2 input refuse. The root passed by the caller is used for both sides, never regenerated; this does not authenticate the authority provenance or prove a captured native installation root. Plaintext temporary CSK buffers are cleared; neither root nor plaintext is returned in receipts. Original input bytes are unchanged and never written.

`source/aux-csk-v2-runtime.mjs` contains only Aux-v2 readers/writers; it has no original-domain fallback. Its explicit envelope format is `aux.dk.v2`, purpose `csk`; HKDF info and ChaCha20-Poly1305 AAD are `aux.dk.csk.v2`, with 12-byte nonce. It preserves the supplied outer schema/owner representation. Old or unknown envelopes fail closed. This is the previously reviewed Aux crypto implementation, paired here with actual CSK consumers rather than simply asserting generic fixtures imply integration.

`applyPinnedAuxCskV2({original,composed})` accepts only the exact original and current composed hashes. Three exact-function replacements affect `saveInstallationDerivedKeyBlob` (one actual CSK caller), `readLocalChromeSyncKey`, and `parseLocalBootstrapSecureStorageBlob`. The real account-change/sync-generation guards, secure write/readback/retry sequencing and owner mismatch refusal stay present. It imports a fixed sibling `./aux-csk-v2-runtime.mjs` module. The adaptation is **not in the active pipeline**; source asset materialization/bundling of that module and its pinned Aux-only dependencies still requires integration. Its imports are review-source paths, not a promise that copying a single file into an app is sufficient.

`domain-audit.json` enumerates every reference to the two original constants and all direct real DK derivation/encryption consumers. CSK is only one purpose. Other live gaps are skill-cache encrypted files, daemon token HMAC derived key, and context-awareness evidence AES-GCM keys. Excluded Vault auth/session/biometric uses are not restored. `DK_WRAP_INFO` feeds the supplied Windows JS P256 wrapper/unwrapper; macOS uses the separate native `dk-unwrap` path. This proposal does **not** globally rename these constants or silently reinterpret any existing ciphertext. The full composed daemon consequently retains original-domain references outside this inactive CSK slice; it is not yet a clean final runtime.

Focused fixture: `node docs/integration/proposed/aux-csk-v2-consumer/tests/check.mjs <frozen daemon-original.mjs path>`. It uses fixed synthetic DK/CSK, authenticates/reseals an owner-bound and bare original payload, verifies exact surrounding metadata bytes, and executes the actual three adapted daemon functions with synthetic storage/account dependencies. It proves migrated read, newly written v2 read, owner/key/version refusals and runtime rejection of original ciphertext. It does not execute original app initialization or claim actual native authority acceptance. Original crypto/identity/daemon source dependencies and exact adaptations are pinned.

Before activation: finish other-purpose domain migration, supply authenticated same-DK native provenance plus real stopped/cohort admission and selector/entitlement capture, integrate prepared bytes with the existing durable copy-only transaction and a coordinated reader/writer rollout, and package the fixed runtime dependency graph. Durable journals prove publication mechanics, not that these prerequisites hold. Root/API caller material remains an external responsibility; no new custody Boolean or fake admission token is introduced here.
