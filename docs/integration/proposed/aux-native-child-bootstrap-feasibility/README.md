## Preferred full embedding seam

Frozen `node.h`775–809 explicitly guarantees `LoadEnvironment(..., EmbedderPreloadCallback)` runs before any userland loader code and propagates the callback into child Worker environments. `ModuleData` can retain the supplied ESM entry rather than rewrite its implementation. A native embedding could own a process host, register each real Environment before supplied entry evaluation, then feed the actual NAPI callback to `RegisterCurrentWorker` through a private native Environment-keyed record. The NAPI linked callback has no `priv`, but native lookup of its actual current Environment avoids giving JS a scope/handle. The V8 linked callback accepts native `priv` but does not supply `napi_env`; no pointer cast between those interfaces is valid.

This requires an exact reviewed Node library/source build and real host main/worker teardown, not a new JS flag. No source acquisition or rebuild was started. Replacing the runtime also requires matching module ABI147, NAPI8 behavior, V8 ABI/config, SEA layout/execution arguments, snapshots/code-cache, system-CA behavior, ESM/CJS loaders, native addon/pty integration, child/Worker behavior, signal handling and graceful shutdown. Every runtime/native-image and SEA-source pin, signed-policy image identity and bundle manifest must then be deliberately recomposed. Binary compatibility or behavior parity cannot be inferred from matching the version number.

## Linkable alternative using the supplied executable

A fixed native bootstrap addon can be loaded by a reviewed native launch preload before the supplied entry. A tiny fixed JS preload would only load the signed fixed addon; it supplies no admission value. Actual NAPI initializer receives the real Environment callback and uses kernel-authenticated native IPC before creating/retaining a process-lifetime WorkerHost. The existing WorkerHost then reserves the Environment, installs cleanup before owner creation, validates the current runtime Environment, and retires pending/late owners. Per-Environment cleanup must not close a host that other Workers still use; process host lifetime is native, not a mutable JS singleton or replacement-handle API.

Available Chromium transport is concrete: `LaunchOptions::mach_ports_for_rendezvous` plus `process_requirement`, or `fds_to_remap`; `MachPortRendezvousServerBase::HandleRequest` receives a kernel audit trailer. Mac server validates the live client with `ProcessRequirement::ValidateProcess(audit_token)`; client can set a server requirement before acquiring its one-time ports. However stock rendezvous validation/enforcement is feature/environment-policy dependent and its registration map is PID keyed. **Unchanged stock rendezvous is not sufficient protected admission.** A successor must enforce exact signed live peers regardless of environment policy, bind the retained actual child identity/audit PID-version, transfer a private endpoint once, and retain/close that endpoint with the real native parent coordinator. A live Unix connection with `LOCAL_PEERTOKEN` is another available kernel-authentication primitive. A pre-spawn socketpair alone is not evidence of the post-exec child's identity.

Before allowing any protected factory, the child must authenticate the native parent and its still-live actual admission, preload/retain the exact policy runtime/PDF/utility images, and obtain the correct selected or fresh authority through its genuine consumer. An audit-authenticated connection proves a process peer, not that the parent owns all profile writers. Current direct-child launch lock only serializes that spawn with direct-daemon closure; it is not whole-profile custody. Current selected producer requires existing four target rows and fixed home; fresh policy/home cannot be substituted into it.

The addon alternative can enforce **protected-command** registration for each Environment that loads it. It cannot by itself force future Workers to load the preload (Worker execArgv may differ), or stop JS-only workers, processes and filesystem writers. Worker inheritance defaults or an empty native registry do not prove complete enrollment. The SEA and CLI preload ordering/flag support must be verified separately; no supplied SEA was changed or executed here. Full embedding's inherited native preload is the stronger future seam for complete Environment registration.
