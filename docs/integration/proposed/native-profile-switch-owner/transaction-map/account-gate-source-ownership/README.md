# Browser gate ownership and actual preference registration

Five-file source-only incremental proposal after the canonical identity/gate chain. The manifest pins exact existing source/output hashes. Independent disposable patch replay passed. No shared native file was changed; GN generation, native compilation and runtime verification have not run.

Actual current GN inspection establishes two distinct ownership problems:

1. `//chrome/browser/aux:profile_state` currently includes `profile_security_client.cc` and the standalone `profile_state_probe` links that entire source set. Adding the real browser-owned UUID lookup to this set would pull ProfileManager/browser-process references into a pure JSON fixture executable. Keep `profile_state.cc/h` pure and separate browser identity and the authenticated network client into explicit source sets. The client still receives the actual UI-captured ID and checks the loaded identity before replying; there is no path-hash, missing-browser fallback or successful stub.
2. The supplied bootstrap popup uses real `CreateBrowserWindow`, `chrome::AddTabAt` and `UnloadController`. The implementation lives in the actual full browser UI (`browser_tabstrip.cc`, `unload_controller.cc` etc). UI already depends on `:profile_gate`. A gate implementation target that depends back on full UI would form a cycle. Use the existing `:ntp_prerender` pattern: `:profile_gate` exposes only its header, and `profile_gate.cc` is compiled once in the existing full UI target. Do not depend on `:profile_manager_impl` from the low-level identity/client targets: its public interfaces are sufficient for includes and final browser linkage owns their implementations.

`gn-targets.gn.txt` contains the precise target split/dependency additions for root integration. Existing target files were inspected, not modified. In particular `profiles:profile_manager` and `profiles:profile_util` are public interface targets; their implementation targets are deliberately absent. The pure probe retains only `:profile_state` and `//base`.

This patch moves the original preference registration out of the UI gate implementation to `profile_gate_prefs.cc/h`, a low-level registration-only unit. `browser_prefs.cc` includes that header under the actual `ENABLE_AUX_BROWSER` build guard and calls the local-state registration from real `RegisterLocalState` and profile registration from real `RegisterProfilePrefs`. Registration therefore precedes actual loaded profile access and does not initialize a gate, daemon, account, UUID or window as a side effect. Existing finalization/BrowserView callbacks keep the header-only gate API.

Registered original keys/defaults are `aside.onboarding_completed=false` in local state; profile `aside.profile_id=""`, `aside.account_user_id=""`, `aside.account_id=-1`, `aside.bootstrap_complete=false`, `aside.automatic_password_gate_suppressed=false`, `aside.account_password_extension_available=false`. They remain original preference identities inside Aux's isolated state, not altered authentication or crypto wire labels. No account completion/binding/unlock is fabricated by registration.

Root must apply the source proposal and the matching GN split together. Header-only targets alone do not provide implementation symbols. The original full account/avatar reconciliation producer remains a separate incomplete source port; this wiring does not pretend to supply that producer.
