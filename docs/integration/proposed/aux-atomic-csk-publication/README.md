# Fixed-home account registry / CSK publication successor

This is implemented inactive source, not current app activation or an ownership/admission receipt. It preserves UI files, the original cryptographic authority, original optional capabilities, and all unflagged command behavior. No current profile, credential, Security operation, protected factory, browser or provider was accessed.

## Actual transaction

`AUX_ATOMIC_CSK_DISPATCH` adds `csk-publish-absent-or-same` to the genuine owned dispatcher and a synchronous native `withAccountRegistryLock(callback)` on the same immutable instance. No JS supplies scope, home, handle, lock token or selected authority. The native host must construct `ScopedAuxCommandContext.runtime(..., atomicAccountHome: <its already reviewed immutable home>)`; SHA256 of exact home UTF-8 must equal that captured installation scope. This is not a caller-provided authority Boolean. The coordinator also rejects use after fork from its construction process.

Each call acquires the real registry lease before touching callback input or state. The fixed-home `.aux-accounts-csk.lock` is a persistent owner-only regular flock inode: bounded contention fails closed; no stale-lock timeout steals, deletes or replaces it. Account JSON transactions and CSK publication hold the same exclusive lock. The NAPI callback remains inside the actual native call/lease until the callback returns; exceptions release it, Promise results are rejected. The new property is non-writable/non-configurable. Each function has its own reference; collecting one sibling cannot retire the other. Environment cleanup retains existing actual owner/retirement behavior. Reentrant retirement refuses to drain its own callback, as the existing registry contract requires.

Under that lock the publisher reads **the actual** `<fixed home>/accounts.json`: schema `version:1`, unique `accounts[].id`, `userId`, and `sessions[String(id)].accessToken` payload `sg`. It checks the requested owner/generation against those persisted values, rather than trusting JS's expected context. Parsing stored JWT metadata is not independent token authentication or cloud ownership proof. Owned ordinary files are size-bounded at 4 MiB; malformed/duplicate-field JSON, unsafe files and unsupported context fail closed.

The CSK selector is the existing reviewed `aux.csk_<safe integer>` logical key in the captured installation's Aux secure-store namespace/group. The existing captured P256/PQ authority opens its genuine root; native CryptoKit derives `aux.dk.csk.v2` and encrypts the existing Aux-v2 envelope (ChaChaPoly, same AAD/purpose, no legacy reinterpretation). Publication uses **Add only**, never Update/delete: absent -> stored; exact same plaintext/current account/generation -> same with the original ciphertext unchanged; any other existing row -> conflict. Duplicate Add rereads and compares under the same accounts lock. Native root/plaintext working copies are cleared; existing string/base64 ABI copies do not acquire a new zeroization guarantee. Generic CSK secure-save/clear are refused in this graph; ordinary non-CSK secure credentials and secure-read retain their existing path.

## Actual supplied writer pairing

`source-pins.json` pins the original1852 daemon and existing CSK-v2 consumer table, exact count-one source anchors, and the two actual current development outputs (SEA and node-development) with full before/after SHA256. `source/adapt.mjs` accepts only those reviewed full source projections, preserving every byte outside five edits. It is not connected to root staging.

1. The actual `FileJsonStoreBackend.withLock` is renamed `withAuxOriginalLock` without changing its contents. Only the Darwin fixed `ACCOUNTS_JSON_PATH` call is wrapped in the owned native callback **before** ensure/create, existing proper-lockfile, recovery/defaulting, read, update callback and atomic write. The existing proper-lockfile (mkdir lock, stale30s/heartbeat15s) stays intact inside; native does not pretend to implement or reclaim it.
2. On Darwin the existing asynchronous method refuses this accounts path: no current `AccountRegistryStore` uses it. Other JSON stores retain the original behavior.
3. On Darwin `AccountRegistryStore.fromFile` rejects alternate accounts paths for this graph. Native never accepts an arbitrary path from JS.
4. The actual `saveInstallationDerivedKeyBlob` uses the typed publisher through the existing owned binding. On macOS it no longer rereads and blindly rewrites with generic secure-save or relies on a per-account Promise map. The non-macOS setter body remains the exact prior implementation; this Darwin-native coordinator does not silently replace the Windows backend. A small `publishAuxRecoveredCsk(account, bytes, {userId,generation})` producer has the recovery client's stored/same/conflict/unsupported result contract and clears its copied bytes; connecting RecoveryClient to that actual daemon producer remains an integrator step.
5. On Darwin destructive `repairInstallation` explicitly refuses before installation-destroy or CSK clears. Reset/migration needs the real stopped-writer coordinator, not ignored clear errors.

The original daemon has four references to `ACCOUNTS_JSON_PATH`, one literal `accounts.json`, two `saveInstallationDerivedKeyBlob(` occurrences (definition+one caller), four `storeLocalChromeSyncKey(` (definition+three callers), three `stampLegacySyncKey(` (definition+two callers), and five `getChromeSyncKeyStorageKey(` (definition/read/evaluate/store/repair). Exact original offsets/guard excerpts are retained in the pins. The CLI1852 code has no `accounts.json`, `ACCOUNTS_JSON_PATH`, `secure-save`, `saveSecureStorageItem`, or Chrome Sync key writer references.

**No new local-login requirement was inferred from nullable historical records.** The three primary CSK setter callers are legacy stamp, cloud fetch/resolve, and authenticated recovery. `fetchAccountSyncPassphrase` immediately returns null without session/user and also when token `sg` is null. Its legacy-stamp call follows those guards. The second stamp caller is `fetchAccountSyncKeyStatus`, after successful authenticated `/sync/key/status`. Recovery explicitly requires signed-in user. Stamp failures already warn and retain the old row. Existing ownerless CSK *reads* remain unchanged; this successor never silently promotes/relabels those records or generates a replacement. Installation root/provider credential initialization is separate and is not changed into CSK initialization. AccountRegistry itself requires the new native callback at startup in the activated successor; trusted native bootstrap must exist before that init, otherwise it deliberately refuses instead of falling back to the original uncoordinated addon.

## Integration and remaining real prerequisites

Root staging/manifests, signed policy, production host and startup are untouched. To compose later: add the coordinator source and `AUX_ATOMIC_CSK_DISPATCH` to both Swift/C++ graphs; pass the native reviewed fixed home at the existing runtime scoped constructor; apply the five source edits **after** current crypto CSK-v2 transforms in every participating daemon graph; derive/review new full output pins for other modes before accepting them. Do not enable only one side. Keep existing unconditional state2 refusal until actual trusted host/cohort admission exists.

This lock coordinates **participating** instances/environments/processes using these fixed APIs; the cross-process fixture establishes real flock, not custody over unrelated processes. Old accepted apps/addons, unmanaged file writers, original-runtime CSK writers and separately reviewed offline migration/restore/reset operations do not acquire it. Actual native whole-profile admission must exclude those writers and bind/recover their transactions before activation. The lock is not an authentication proof, protected-factory authorization, whole-profile writer census, ownership migration or readmission receipt. Native CLI/browser/account restore writers, if added, must use the same coordinator or be stopped under that real lifecycle authority. No owner state was read to decide this.

The desktop recovery client is implemented but its live call route is not installed; cloud CSK generation changes with existing conflicting keys require explicit migration, not overwrite. Real DP Security behavior, owner-profile startup, all-worker producer ordering and multi-process application admission remain unexecuted. Current accepted app and outer state2 startup refusals remain intact.
