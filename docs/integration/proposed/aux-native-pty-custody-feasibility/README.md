# Actual PTY native custody feasibility

The requested kqueue descendant scheme is not implementable on current macOS. The [pinned Apple kernel filter](https://github.com/apple-oss-distributions/xnu/blob/f6217f891ac0bb64f3d375211650a4c1ff8ca1ea/bsd/kern/kern_event.c#L1037) returns ENOTSUP for NOTE_TRACK, NOTE_TRACKERR or NOTE_CHILD. Its [event header](https://github.com/apple-oss-distributions/xnu/blob/f6217f891ac0bb64f3d375211650a4c1ff8ca1ea/bsd/sys/event.h) also excludes child PID from delivered NOTE_FORK events. The installed macOS27 SDK agrees. Suspending the initial helper can close its own pre-registration gap; it does not restore recursive tracking after resume. Process groups, scanning parents and a zero JS PID map cannot replace the missing kernel primitive, especially after setsid/reparenting.

The official node-pty v1.1.0 source is now pinned at [Microsoft commit1def5774632305246fe21f0f69e23a664d6c5910](https://github.com/microsoft/node-pty/tree/1def5774632305246fe21f0f69e23a664d6c5910). The full unchanged MIT-licensed pty.cc, helper, package metadata, build description and LICENSE are retained under upstream/. Their version matches the supplied package. That establishes an authorized upstream source candidate, not byte equivalence with the supplied signed prebuild or proof those binaries used this exact source. No original addon was executed and no binary provenance is invented.

A second waitpid in a new coordinator would compete with the existing reaper. A detached new observer that accepts a JavaScript PID would not establish creation provenance. The upstream wait path also needs explicit failure-state handling before reuse: stat_loc must only be interpreted following successful waitpid; callback failure or Environment closing is not proof of child exit. These are source findings about this pinned upstream candidate, not an unverified claim about original prebuild behavior. Linux/BSD/Windows paths, licenses and ordinary PTY API behavior must remain intact in any real successor.

A concrete modern alternative exists: Apple's [es_new_descendants_client](https://developer.apple.com/documentation/endpointsecurity/es_new_descendants_client(_:_:)) is declared by the actual macOS27 SDK for the caller's recursive subtree. Its header says root and TCC approval are not required, but the Endpoint Security client entitlement is mandatory. This differs from the older systemwide [es_new_client](https://developer.apple.com/documentation/endpointsecurity/es_new_client(_:_:)), which has broader approval requirements. No entitlement, signing, new access or execution is authorized by this finding. Versions below27 need a separately supported solution; not a kqueue downgrade.

Even the new API is event provenance, not automatic custody. A real fresh producer would need to create/subcribe it before any subprocess, keep exact audit/process identities and actual event sequence/loss state, and establish a source-verified completion/barrier before calling an observed set empty. Existing descendants being eligible for events does not document an initial census. Missing events, deadline failures, client loss or unknown initial children must withhold drain. Forked code can write without exec; AUTH_EXEC alone is insufficient. No source reviewed here supplies an atomic subtree-empty/closure proof.

Recommendation: do not implement the requested NOTE_TRACK tree tracker or claim a true descendant-custody bridge. The smallest coherent future source slice can own direct-child creation/sole reaper and close admission, explicitly retaining descendants unknown. True subtree custody requires the supported macOS27 entitlement-backed path plus its actual delivery/closure proof, or a separate enforced writer/containment boundary. Neither prerequisite is created by this proposal. Cold first installation before Node/PTY start can remain a distinct supported ordering; it must not be reinterpreted as later live migration custody.
