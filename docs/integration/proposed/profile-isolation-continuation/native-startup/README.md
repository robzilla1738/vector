# Cold-only final network-path admission

This successor preserves the UI and the ordinary default-off cold-entry route. It implements a real refusal at network-context creation for cache overrides which exceed the immutable browser-root denial set. It does not enable protected startup or authorize an existing browser profile.

`native.patch` adds `ContentBrowserClient::CanCreateNetworkContext`: ordinary embedders return true. StoragePartitionImpl calls it on final native params after embedder, DevTools and shared-dictionary configuration, before delivering paths to the NetworkService. A refused context gets bound but disconnected context/verifier endpoints, with no reconnect handler and no substituted fallback or preference mutation. Existing NetworkContexts keep their original paths. On network-service recovery the same creation gate evaluates the new params again.

Only `ENABLE_AUX_BROWSER && AUX_SEALED_NATIVE_COLD_ENTRY` selects the strict Chrome implementation. It checks all six directory slots in NetworkContextFilePaths: shared dictionary, HTTP cache, No-Vary-Search, logical invalidation, data directory, and unsandboxed migration data. `prefs::kDiskCacheDir` feeds the actual HTTP-cache path before this final gate, so an override outside the held data/default-cache pair is refused even when changed while children exist. This intentionally does not expand the roots denied to an existing child. A preference can remain saved while its new context is refused; no value is silently rewritten. No observer is needed to move a live cache: this Chromium implementation reads that preference at context creation and exposes no cache-directory mutation method on NetworkContext.

The native validator obtains the actual retained root pair itself, duplicates both finite role FDs, derives physical names, and revalidates the held root identities after all path checks. No JS, environment, CLI or preference supplies an allowlist. For prospective directories it resolves the nearest existing ancestor and permits only an absent suffix on ENOENT; malformed components, files, dangling links, permission errors and loops refuse. Existing symlinks resolve physically, so an alias into a covered root is accepted and an alias outside refuses. Path-component boundaries prevent `data-other` matching `data`.

Neither check launches Chromium/daemon, receives an owner lease, reads a real profile, signs or changes OS grants.

## Explicit remaining boundaries

* This is final NetworkContext path coverage, not a universal filesystem broker. It does not make path validation and later filesystem creation atomic against descendant symlink replacement. The network service's eventual filesystem/sandbox behavior, other browser writers and already-existing external-cache contexts are not covered by this result. No all-writer custody is inferred.
* It checks directory roots, not arbitrary database filename mutations or every file-valued NetworkContext parameter. The supplied native builder's names are unchanged. Broader NetworkService file-parameter/broker coverage needs a separate finite audit and implementation.
* Refused Mojo endpoint behavior and real cache/UI recovery still require a disposable actual-candidate check after integration. The pure fixture is not a fake network-service acceptance result.
* `ChromeFeatureListCreator::CreatePrefService` still calls JsonPrefStore::ReadPrefs before the current real StartSealedNativeDaemonBeforeProfiles hook. Prior pre-read root capture proves native provenance only. The current selected-home registry holds a real shared SelectedNativeHome and generation/ready pulse/child authority, but has no browser-root IO-admission operation. Its active_reads guards installation challenge/key operations, not a browser lease. Moving the startup call alone or checking route/current would not authorize browser IO.
* A genuine early grant requires a separate finite audited browser-root-admission operation: actual captured user-data FD identity/name digest bound to sealed fresh-root authorization, exact current owner/transport generation and retained native lifetime, with refusal for old policy/state. No such grant is implemented or fabricated here. Root's v6 contained-PTY/task-layout policy remains separate. No runtime policy is created or approved.
* Mach launch rendezvous itself uses GCD and native launch interfaces, and ThreadPool instance creation is early on macOS; those facts do not prove every readiness callback is safe before prefs or solve the absent authorization protocol. The remaining early-IO lifecycle must be checked with that actual protocol, not assumed from moving a function.
