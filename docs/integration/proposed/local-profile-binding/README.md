# Preserve real profile account identity

Status: staged proposal only. Apply **after** `local-vault-bootstrap` from commit `17a54f903`, which itself follows the combined native entrypoint/profile-security proposals. The six file baselines and outputs are pinned in `manifest.json`. No shared Chromium source was edited.

The gate previously called `accounts.ensureProfileAccount` with `localOnly:true` on every startup. That procedure intentionally resolves a local account, including replacing cloud profile bindings. Local service unavailability does not authorize changing a cloud account into a local one. The account API also inferred `localOnly` from an absent bound user, which could send malformed cloud records into the supplied UI's local branch.

This proposal changes those native boundaries:

- Registry classification returns an explicit optional local/cloud choice. A valid registry with no profile binding is local-creation eligible. An exact existing local account is local only if it carries no user, session dictionary or prior cloud-binding marker. An existing cloud account requires its actual nonempty user ID. Account zero remains valid.
- Startup reads metadata on a blocking worker. Existing bindings are never rewritten by the native gate, regardless of cloud availability, Vault status or onboarding. Only a verified fresh local profile invokes the existing `ensureProfileAccount` procedure with its real Chromium ID/path/index. Missing registry metadata is retried through the existing gate timer; it is never permission to create an account.
- Invalid/missing accounts, unsupported modes, inconsistent bindings and incomplete cloud identities remain unclassified and locked. `getProfileContext` returns an error for them. It cannot return a v1 context missing the identity discriminator and accidentally request local resolution. Valid cloud contexts carry `localOnly:false`, their real user ID and the actual bound account ID.
- Vault status revalidation also compares this identity classification. Authenticated Vault errors remain distinct from registry identity errors: a real, locked or unavailable Vault does not erase the known cloud binding.

Conservative migration rule: where no exact current `profileAccountBindings` entry exists, any nonempty legacy `profileBindings` dictionary blocks automatic anonymous creation. The native reader cannot safely establish that such a cloud mapping belongs to another profile. Explicit migration is required; no mapping is deleted. Malformed dictionary values are also rejected. This can block creation of a new profile beside an unmigrated cloud mapping; it deliberately preserves the mapping rather than guessing identity. Exact current bindings remain usable.

`profile_state_probe.cc` exercises disposable metadata cases: valid fresh profile; anonymous account zero; cloud account zero and real user; incomplete cloud; prior cloud marker; local session; unknown mode; wrong path; missing bound account; legacy map; malformed binding container; missing account inventory; permissive file mode. Every read checks the registry bytes are unchanged. This probe is prepared for the existing focused native probe target but **has not been compiled or run** in this lane. No daemon/owner state, network, Keychain or OS grants were accessed.

Verification performed here: patch `git apply --check`, replay into an isolated temporary tree, all six replay hashes equal the manifest, API/header symbol inspection and focused source invariants. Native compilation and disposable packaged local/cloud behavior remain integrator acceptance work. The original flow anchors and route rationale remain in `docs/source/provided-first-launch.md`; this proposal does not modify UI routes, supplied flow checks, onboarding timestamps, cloud sessions or cloud service responses.
