# Explicit embedded-daemon PTY policy v3 — inactive source

This successor admits two finite **future Aux-identified arm64 artifacts** only through a new sealed `aux.fresh.bootstrap.policy.v3`. It does not approve or accept the current original-team artifacts. v1/v2 decoding, signature validators, existing PDF/OS preparation loop and resource paths remain unchanged. No active policy, package, main input list, compiler queue or native checkout was changed.

The v3 envelope retains the exact v2 daemon-only `nativeHostLayout:"embedded-daemon"` and adds exactly `ptyModule` and `ptySpawnHelper`. Each is an exact object with `path`, `identifier`, `sha256`, `bytes`, `sourceSha256`, `architecture`. Paths and identifiers are fixed in source:

| Resource | Exact relative path | Aux identifier |
| --- | --- | --- |
| Node-API module | `Contents/Resources/native/node-pty/prebuilds/darwin-arm64/pty.node` | `dev.aux.browser.pty` |
| Separate helper executable | `Contents/Resources/native/node-pty/prebuilds/darwin-arm64/spawn-helper` | `dev.aux.browser.pty-spawn-helper` |

The provenance hashes are the exact frozen files from `aux-native-fixed-pty-loading/inventory.json`. They are provenance, **not** proof that every non-signature byte in a future artifact is unchanged. The output SHA and byte count must be those of an explicitly reviewed future signed artifact, recorded in the sealed policy after module/helper signing and before host/policy signing. There is no self-hash cycle. No output hash/size has been invented, no signing is authorized here, and no real v3 policy is supplied. Output hash must differ from the original hash. Both actual resources must have the fixed Aux team/certificate/identifier, hardened runtime, no ad-hoc flag and empty entitlements/application identifier/access groups. Original public vendor legal attribution must remain in the package.

The existing no-argument `AuxPrepareSealedNativeDaemonImages` is preserved. For v3 only it holds every path component for all four native resources in the existing root-owned, no-ACL, non-group/world-writable namespace before any load. It authenticates the exact policy-pinned whole bytes, actual thin little-endian arm64 Mach-O type, individual signature and enclosing bundle seal. The helper must already be executable; there is no chmod. The module is `MH_BUNDLE`; helper is `MH_EXECUTE`. Helper is authenticated first but never dlopened or launched. The original `utils.loadNativeModule` probes `build/Release/pty.node` and `build/Debug/pty.node` before prebuilds, so v3 refuses either candidate's existence before Node can run its constructors. The paired fixed-package transform remains a separate required staging integration.

Only the actual module is added to the expected daemon image set. Preparation retains its exact-path `RTLD_NOW|RTLD_LOCAL` handle permanently, then verifies that both `napi_register_module_v1` and `node_api_module_get_api_version_v1` resolve inside that exact image. It does **not** invoke either function. Full later policy checks recheck module bytes and its finite Aux signature; the helper is not represented as a daemon image or an observed running child.

The pinned official Node26.5.0 `src/node_binding.cc` provides the load-order evidence: `DLib::Open` (line351) calls `dlopen`; `DLOpen` (line484 onward) subsequently looks up the Node-API exports and calls `napi_module_register_by_symbol` for the actual Environment. Therefore retaining the image is not a substitute for real per-Environment `require`. `dlopen` may run constructors; this proposal trusts only exact reviewed artifact bytes under the root-owned namespace, and does not claim absence or safety of constructors without artifact inspection. The current main plan's `-export_dynamic` is not proof that the final linked executable exports all PTY imports: exact final-binary undefined/export resolution and actual Node-API require remain unverified. There was no addon load, Node entry evaluation, signing or protected call.

The separate helper's actual spawn, PID ownership, termination, callbacks and pending descendants are **not covered** by image preparation. The supplied native module does not expose an authenticated whole-process custody token merely because its file was validated. Its existing JS terminal/exit callback paths and native spawn need the separate owned-PTY lifecycle integration; no drain/success Boolean is added here. This does not close the whole writer/cohort gap or weaken the first state2 refusal.

Integration is source-only: replace the two logical Swift files from the existing embedded-image proposal with this successor **only as a coordinated v3 review**, update the distinct parent read-only policy subset to the same new schema, compose the existing fixed-package adapter, and supply actual reviewed Aux-signed outputs/sealed policy before any activation. Today v3 cannot run because those reviewed artifacts/policy do not exist. `verify.py` checks frozen hashes, v3-only anchors, original finite validators/old module-loop preservation, exact paths and custody/role distinctions. It is a static source check, not Swift typechecking or runtime proof.
