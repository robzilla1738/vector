# Native extension worker start admission

Inactive source proposal against the pinned 778-source/23-asset session-writer-close parent. It changes `ServiceWorkerTaskQueue.cc/.h` and adds one small native admission header. No supplied UI, normal-open activation/start behavior, BrowserPlatform, GN or live Chromium source is changed here.

`ServiceWorkerTaskQueue::CloseStartAdmissionForMigration()` closes a browser-process-owned, UI-sequence native gate **before** cancelling retry timers on every registered real queue. The gate has one irreversible generation transition (1→2); there is no reset/reopen API. Every new queue captures that actual process generation and remains refused after closure. `InspectStartAdmissionForMigration()` observes the same owner without changing it. Call both only on the browser UI sequence. BrowserPlatform integration and registration of `service_worker_start_admission.h` in the existing extension browser source target remain root work.

Both APIs return `ProcessStartAdmissionSnapshot {admission_open, generation, queues, destroyed_queues}`. Each queue snapshot retains its actual BrowserContext token, captured generation, current activation/start/ready/optional WorkerId observations, retired activation observations, pending tasks, registration/verification callbacks, pending storage/unregistration counts, and late registration/verification results observed after closure. The queue owner records destroyed queue observations rather than treating destruction as a stop acknowledgment.

Fifteen activation, registration, start, retry, readiness, listener completion and task entry routes check the process gate. This includes delayed registration verification/results, registration retries, start retries and `MaybeStartWorker`. Dispatch rechecks before **each** task, so a task that reentrantly closes admission cannot deliver later tasks to the worker. Closed new tasks receive null ContextInfo. Existing pending tasks stay owned and observable; closing timers does not discard them or clear worker states. Late renderer initialization still tracks the actual running instance, but does not grant file-scheme access or activate extension API work. Existing renderer start, stop, process-exit and worker-stop observation bodies are byte-identical. Late registration/verification replies resolve their pending counters and retain their actual result without retrying or writing the normal registration preferences.

## Exact remaining boundary

This closes **new extension-layer requests** within this browser process, including future queue instances. An already-issued content-layer `StartWorkerForScope` or registration may still finish, execute installation/start code, or autonomously restart inside content. This proposal observes such ownership; it does not cancel those requests, stop an already-running renderer/service worker, wait for actual renderer/content storage termination, or prove every profile writer is stopped. Deactivation, empty task/retry maps, destroyed queues and UI closure are not stop proof. Retired observations deliberately remain conservative rather than becoming false success. Separate browser processes and other renderer/storage/CLI/native writers need their real native admission/drain participants. No aggregate migration acceptance, readmission, state-2 bootstrap bypass, PID kill or receipt-as-authority is introduced.

No worker/profile/application was launched and no owner data, original addon, credentials, Security/Keychain, OS grant, signing or provider call was used.
