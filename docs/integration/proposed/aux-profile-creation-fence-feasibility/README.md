# Profile creation participant: concrete pairing blockers

No central nullptr fence or fake creation-complete receipt is implemented. Static inspection of the currently applied source found that a small sync/async/OTR gate cannot safely be inserted as a complete participant without first pairing refusal and completion ownership. This follows the explicit instruction to report actual blockers rather than deliver an inactive scaffold with unsafe hooks. No native checkout, UI, build, profile, process or OS operation changed.

1. **OTR creation is currently treated as infallible.** `Profile::CreateOffTheRecordProfile` constructs a profile, invokes Init and returns it. `ProfileImpl::GetOffTheRecordProfile` immediately obtains its raw pointer, stores the unique_ptr and notifies creation without a null branch. Beyond that central function, `browser_commands.cc` NewWindow dereferences `otr_profile`, OpenURLOffTheRecord directly constructs a browser displayer with the result and NewIncognitoWindow passes it straight to NewEmptyWindow. Returning nullptr from a new central closed-admission check can therefore crash valid queued or reentrant work. Required first: actual outer command/activation admission (or a cold-only owner lifecycle in which these commands cannot execute), plus a typed/refused failure path propagated to callers. Adding a new nullptr return alone does not preserve the product's behavior.

2. **Delegate callback time is not construction completion.** `ProfileImpl::DoFinalInit` calls the delegate's OnProfileCreationFinished, then still executes NotifyProfileInitializationComplete, RecordPrefValuesAfterProfileInitialization and keyed-service creation. The source also warns the delegate may immediately delete the current Profile after failure. A lease completed in the manager's callback falsely drains before these tail writes; a lease that blindly touches the Profile after the callback risks use-after-free. Required: lifetime-safe tail accounting in actual ProfileImpl ownership, with failure/deletion becoming explicit unresolved state unless observed, and a separate manager outer-call lease through service/registration/caller callbacks.

3. **Async creation includes work outside the profile callback.** CreateProfileDirectory synchronously creates the directory but posts the README write to ThreadPool. ProfileManager::CreateProfileAsync can queue closures in deferred_asynchronous_loads_ and profiles_pending_destruction_, can join an already-initializing ProfileInfo, and can run callbacks immediately for an existing profile. Required: generation-check queued closure entry and explicit owned completion for its deferred write/callback work; dropped closures or lost callbacks stay pending/unknown. A destructor decrement is not a successful completion observation.

4. **A constructor gate is not an existing-profile reuse fence.** GetProfile returns a loaded profile before calling CreateAndInitializeProfile; OTR lookup returns an existing OTR profile. The smallest participant must state whether it covers new construction only or new use of existing profiles. A construction-only counter cannot become whole-profile custody. Native renderer/extension/storage admissions remain the separate actual paths listed in aux-native-writer-custody-map.

A safe future sequence is to establish the real native cold/outer-command owner first, then implement one versioned per-profile generation fence with actual owned tickets spanning constructor, manager callbacks, queued closures and direct child tasks. Permanent close must have no JS/environment bypass, lost work must remain pending, and ordinary open behavior must remain byte/behavior compatible. Until those refusal/lifetime contracts are paired, the existing pre-state state2 quarantine is the correct enforced boundary; weakening it in favor of this incomplete gate would reduce safety.

`evidence.json` pins the exact six current source files and concrete anchors. Verification only checks static hashes/anchors; no compile/test/runtime acceptance is claimed. The next smaller native implementation assessed separately is aggregation of already-real direct-daemon and installation-carrier observations, explicitly scoped to those owned helpers.
