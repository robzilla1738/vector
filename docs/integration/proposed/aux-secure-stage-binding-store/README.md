# Private durable nonsecret secure-stage binding store

This inactive source successor supplies the missing filesystem persistence for `FreshSecureStageBinding`. It preserves the reviewed fresh journal's private descriptor/custody mechanics in a distinct Swift file, with no visibility changes, source concatenation, shared reducer edits or generic storage callback. The only public data operations are typed `publish(FreshSecureStageBinding)` and `load()`; neither accepts arbitrary Data, a filename or a secret stage payload.

The store validates the caller's exact fresh journal and reviewed fifth selector, then uses `.aux-secure-stage-binding-<lowercaseUUID>/binding.json` beneath an explicit canonical private disposable root. The UUID is the journal transaction. Publication first validates the binding's format, complete immutable initial-draft digest, transaction/candidate/scope, exact selector and stage-payload digest against that journal. This does not independently prove the supplied journal was durably published or that its caller assertions establish never-used scope/writer custody.

The binding file contains ONLY schema fields: format, transaction UUID, scope, candidate SHA256, initial-draft SHA256, stage-payload SHA256, service, account and access group. It contains no four-row payloads, wrapped-root bytes, root plaintext, software private keys or enclave representations. Exact keys, canonical encoding and the bound journal are checked on every read. Secret Keychain stage bytes never enter a filesystem write API in this store.

## Durability and refusal

Root/private directory and fixed files use the pinned FD checks: canonical path, owned directory0700/file0600, no extended ACL entries, no symlinks, regular bounded single-link files, descriptor/path identity and stable before/after read metadata plus extra EOF. LOCK and file reads are nonblocking, so FIFO inputs refuse. The local advisory lock serializes binding publication only; it is not all-writer/profile/Keychain authority.

`publish` validates the exact binding, compares an existing file or exclusively creates the fixed file, syncs the file and directory, decodes/readbacks the exact bytes, and returns the resulting SHA256 acknowledgement. Creation is allowed only against revision0/draft with no intended target rows. Existing byte-identical valid binding is idempotently revalidated/synced; a different file is never overwritten. `load` also validates, syncs and rereads before issuing an acknowledgement. No rename, replacement, delete, repair or cleanup API exists.

Partial, corrupt, mismatched, unsafe-mode, link/ACL, busy-lock, I/O and sync failures throw. No success acknowledgement is returned after a failure. A failed write may leave a partial immutable file; subsequent access refuses and retains it for review. A failure after sync may leave a complete file; reopening exact valid data is allowed, never assumed rollback. There is no fake CAS head: the only state is one immutable binding; O_EXCL plus byte-equality and the reviewed local lock implement compare-or-create. This cannot protect against an unrelated writer that owns the same directory and ignores the protocol; native custody remains external.

The returned acknowledgement is compatible with the existing process-local secure-stage intent and source restore adapter. A future reviewed coordinator must first durably publish the fresh draft journal, then this binding, then submit the one-shot stage Add and verify its captured readback, before any target Add. Publishing a binding does not authorize the fifth selector, execute Security, establish secure staging, or activate a profile.
