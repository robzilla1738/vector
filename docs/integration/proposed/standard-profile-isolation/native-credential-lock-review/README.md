# Authenticated ChatGPT credential lock — bounded source feasibility review

**Recommendation:** add a private, fixed-role native credential-lock lease using `flock(LOCK_EX | LOCK_NB)`. Do not relax the generic child-process descriptor policy. The current native Owner/root registry provides the required root authority, but it does not yet contain a credential-lock lease or an authenticated caller-FD registry. `withAuthFd` was shorthand in the task, not an existing verified API.

This review introduces no source changes outside this directory, executes no native/client/provider code, and reads no credential/profile data. The prepared ChatGPT cleanup shim must continue recording unknown when it uses `lockf` until this successor is actually implemented and integrated. No current uncertainty marker is cleared by this review.

## Why the existing spawn is refused

The selected reviewed `process_wrap.cc` reserves `AuxNativeExecBeginCurrent` before reading callback-capable argument/stdio properties. At line 343 it invokes `AuxExecDescriptorOptionsAllowed(options)` before `uv_spawn`. The descriptor policy requires exactly three stdio slots, each either `UV_IGNORE` or a new non-IPC pipe. It rejects `UV_INHERIT_FD`, inherited streams, extra slots and UID/GID changes.

`LocalChatGPTStore.diskLocked` opens its permanent lock inode and calls `/usr/bin/lockf -s -t 0 3` with `stdio: ['ignore', 'ignore', 'ignore', fd]`. That has four slots and an inherited descriptor in slot 3; both conditions fail the policy. In the protected producer this is a definitive pre-spawn refusal, not proof that `lockf` descendants actually existed. The cleanup successor's conservative unknown marker is currently set before requesting that spawn; it is not evidence of a successful child launch.

The fresh descendant observer does not fix descriptor admission. It accepts native reservation tokens, original successful-spawn PIDs and original reaper observations. Those establish process identity/lifetime, not which object a JS integer descriptor represents. A matching device/inode snapshot alone would not establish the current open-file description or prevent caller-close/reuse between checking and spawning. Do not permit arbitrary fourth descriptors or infer authority from executable name, argv, `AUX_HOME`, marker text, or an ES empty cohort.

## Existing reusable authority

- `CaptureBrokerOwner(napi_env)` obtains the exact active Node environment's Worker/Owner, rejects closed/terminal/detached/initializing states, checks current native authority, then rechecks the same Worker/Owner. No JS profile/path/generation selects it.
- `AuxNativeContextCopyStorageRoots(owner, &generation, &control, &task)` already returns native-owned duplicates of the authenticated control and task home. Its Swift implementation calls `duplicateRetainedHomeDescriptor()` for control, `duplicateAuthenticatedTaskHome()` for task, and brackets capture with current authority checks. Use control; close the unused task duplicate. Retain generation and the actual control-directory identity for the lease.
- `InstallReadyHomeEnvironment` derives `AUX_HOME` from the ready service's retained home FD. The existing shim's `AUX_HOME/local-only/chatgpt` location therefore has a native authority counterpart. The new operation must derive it from the authenticated control FD, not accept the environment/path as input. Refuse any discovered mismatch; do not migrate/read alternate owner homes.
- Existing host `broker_pending`/`broker_untracked` and final clean query already keep real pending and uncertain work visible. New credential leases must participate for their entire retained lifetime. Reuse this accounting rather than introduce a second unaudited clean signal.

Local SDK `lockf(1)` documents BSD `flock` semantics, a permanent descriptor-form inode, `-s` as silent, and `-t 0` as immediate acquisition or refusal. `flock(2)` documents `LOCK_EX | LOCK_NB` and `EWOULDBLOCK`. Calling that syscall on the native-owned open description avoids a child, preserves cross-process cooperating lock behavior, and does not require a new signing identity or entitlement. It does not establish hostile same-UID mandatory isolation, which is outside the selected standard profile scope.

## Proposed private contract

Names below are proposed, not implemented exports. Reuse the existing linked binding; keep the paired addon and its imports unchanged.

1. `beginChatGPTCredentialLock(logicalAccount)` captures the current native Owner first. The argument is a bounded logical key in the existing exact `aux-local-default` / `account:<original key>` grammar, not a path/profile/generation/FD. Compute SHA-256 from the exact UTF-8 key natively, without normalization or changing saved account identifiers. Never permit a caller-provided digest to choose an arbitrary filesystem name.
2. Native code opens/creates only `local-only/chatgpt` beneath the retained authenticated control FD using fixed components and no-follow directory traversal. It creates/opens only `<digest>.lock`, preserving private modes, regular-file/single-link/UID/size checks and the exact existing `aux.chatgpt.auth-lock.v2` marker whose `account` field is the digest. Preserve permanent inode identity; do not truncate, unlink, replace, rename or reinterpret a malformed/legacy lock. Keep exact JSON semantics, allowing the existing serialization's key order.
3. Hold the exclusive nonblocking BSD flock on that native-owned descriptor. Contention is the existing “another local credential operation is in progress” outcome; no background wait, timer or child is needed. Definite refusal before lock acquisition closes native duplicates and settles its reservation. Partial marker creation/error stays an explicit refusal/recovery case; no automatic delete/reset.
4. Return a native-branded opaque lease, never a numeric FD or reusable global identifier. Lookup binds the exact Worker, Owner, native generation and originating environment. Native lock, root FD and operation state remain retained in the host registry even if JS drops the receiver.
5. While open, the lease admits only the pinned local credential transaction's operations. **Required integration:** every synchronous store read/write/registration/host-ID operation in that transaction must use its retained native scope; shutdown must not unlock while an already-admitted write can still run. The smallest cooperative implementation can reuse the existing finite synchronous-callback reservation pattern, with a per-lease active counter and non-Promise enforcement, wrapping the complete known synchronous store methods. The stronger, still finite alternative is native fixed-record read/write/delete operations for only this store. Do not implement an acquire/release token around unguarded later Node filesystem writes.
6. `closeChatGPTCredentialLock(lease)` closes future lease admission under the same native mutex used by those operations. It is a request, not a completion assertion. Actual unlock/descriptor close occurs only after all admitted synchronous/native operations return. Queued or late store writes refuse after admission closes, including a late token response following cancellation. A JS Promise, `finally`, abort, timeout or GC callback never proves that native work completed.
7. Keep the lock across the ordinary credential read → scoped provider response → identity check → atomic write transaction. On cancellation, late HTTP work may finish but cannot commit after lease admission closes. The existing retained ChatGPT HTTP scope still owns DNS/socket/client cleanup independently; unlocking the local credential file does not certify network drain or whole-Worker cleanliness. Preserve request cancellation and stale-registration comparisons.
8. Track the lease in existing `broker_pending` from admission until actual native unlock/close. Cleanup detaches the environment and requests close, prevents further callback dispatch, and retains the Owner until the last native operation settles. If close/unlock/identity/accounting is uncertain, retain `broker_untracked`; do not decrement to a fabricated clean result. Avoid re-entering the Swift dispatcher while its entry mutex is already held; copy roots first and perform retained native cleanup without JS or dispatcher calls.
9. No lease transfer across profiles, Workers, environments, processes or owner generations. Reject stale token reuse and forked-process registry access. Do not change any provider URL, registration/token payload, lock format, account digest, UI or credential migration policy.

The exact synchronous store scope in step 5 is mandatory. Merely moving `flock` into C++ while retaining an unguarded JS `fn()` and releasing on its Promise would leave a close/write race and does not satisfy this review.

## Why not a generic FD3 exception

If retaining `lockf` itself were required, the host would first need a new private registry that creates and owns the authenticated fixed-role lock descriptor. An exact one-shot native spawn role would have to supply its duplicate itself, enforce literal executable/argv/env/stdio layout, retain the same open description in the parent for the entire transaction, bind the existing Exec/cohort reservation and original reaper, and reject all JS-supplied FDs. The present registry does not provide that capability. This touches the Node process wrapper/envelope and descriptor policy in addition to the credential owner and keeps an unnecessary child/cohort. The direct native flock operation is smaller and preserves the documented semantics.
