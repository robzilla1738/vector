# Main-browser custody registration proposal

Seven counted changes to the exact current a5 `base/BUILD.gn`, `chrome/BUILD.gn`, and Crashpad util `BUILD.gn`, plus one new primary-only exports file. The native tree, build inputs, existing exports and all predecessor proposals remain untouched. Integrator applies this only with the pinned custody, reservation-refusal, Crashpad-close and a5 content-rebase source layers listed in `manifest.json`.

The new `//base:aux_browser_descendant_client` contains only the bridge/client headers. Chromium base publicly forwards this target. Crashpad util publicly forwards the same header-only target, which also satisfies the actual Crashpad client → util public dependency. Neither introduces a dependency on the full base component or the observer implementation, avoiding the Crashpad/base cycle.

The new `//base:aux_browser_descendant_engine` contains exactly the engine and bridge C++ units plus the engine header. Visibility permits only `//chrome:chrome_app_executable` and its `//chrome:chrome_app` bundle: the actual `mac_app_bundle` template forwards the dependency to both targets, while only the executable links objects. The engine never enters the Framework or helper targets. Only this finite source set exchanges `no_exceptions` for `exceptions` and adds Blocks support. The selected compiler default already supplies C++20 or newer; its original warnings, module compatibility logic, target architecture, deployment target and libc++ implementation remain unchanged. Chromium's selected libc++abi target itself already builds exception support; this proposal does not switch the product to the system C++ ABI.

Only the primary app with `enable_aux_browser` receives the engine dependency and `AUX_BROWSER_DESCENDANT_CUSTODY` definition. `-u` retains the one C bridge symbol; its source declaration has explicit default visibility. Stripped primary builds use the new exports file containing `_main` and `_AuxGetBrowserDescendantBridgeV1`. Helpers retain the original exports file and receive no custody definition/engine dependency. Component-build rpath flags now append rather than overwrite the primary retention/export flags. The export file is a real linker input so edits invalidate the link.

The finite source set links `EndpointSecurity` and `bsm`. The primary app's existing library verification adds only their two actual SDK install names, pinned in `graphEvidence`. No broad verifier bypass or unconditional library allowance is introduced. Hermetic Chromium libc++ retains its existing link behavior.

`python3 check.py` checks immutable hashes, all seven count-one literal replays, source equality, unchanged helper/Framework registration spans, and the finite dependency/config structure. It does **not** generate GN, compile, link or execute anything. Root must perform the actual GN graph and compile/link checks under the existing native build lock, inspect the primary symbol and helper exclusion, and retain honest failures. This proposal makes no runtime acceptance claim.

macOS 13.5 deployment targeting is not elevated. The observer source's guarded capability still requires macOS 27 and the separately approved restricted Endpoint Security entitlement. No entitlement, signing, OS grant, app launch or replacement is performed or authorized here.
