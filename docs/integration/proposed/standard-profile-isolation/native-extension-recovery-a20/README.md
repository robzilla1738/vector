# Fresh-process recovery of the six extension preference records

This proposal implements real backend and frontend recovery, rather than replacing a newly captured target with an alleged original source. It composes over the actual A10 retained-backend implementation and A10b original-request/lost-Begin observation (`a8b92a9d2`, `e1bee6c7e`). Ten existing files have 38 exact single-match anchors: ValueStore/LeveldbValueStore, the real quota and weak wrappers, and StorageFrontend, each h/cc. No controller, UI, native checkout or shared GN file is modified here.

The fixed-size native descriptor contains exactly six optional original raw JSON records, their reviewed derived target records, both complete-six-record SHA-256 fingerprints and a descriptor fingerprint. It contains no key names, arbitrary roots, store/Profile selector or readiness flags. `MakeAuxUiPreferenceRecoveryDescriptor` and `ValidateAuxUiPreferenceRecoveryDescriptor` share the actual reviewed three-family schema/transform; the backend recomputes the target and exact-compares all bytes and digests. The original source and target must each fit 64 KiB across all six raw records; excessive data is explicitly refused, never truncated. This bounds recovery data without changing normal UI or normal preference storage.

The fingerprint codec uses the domain `aux.ui-preference-records.v1` followed by NUL, unsigned little-endian uint64 record count six, then each record's one-byte presence tag, unsigned little-endian uint64 raw length (zero when absent), and exact raw bytes. Presence distinguishes missing from present empty bytes; raw JSON is never reserialized. The descriptor uses `aux.ui-preference-recovery.v1` followed by NUL and the two computed lowercase 64-character source/target SHA strings. These are complete fingerprints of the six allowed records, **not** of the entire extension store. Journal authentication and actual Profile admission remain separate native prerequisites; knowing a digest grants neither.

The real frontend `RequalifyAuxUiMigrationLease` first validates this bounded descriptor, then uses the existing actual admission gate and backend queue sentinel to obtain a genuinely fresh opaque capture. The backend entry is forwarded through both real wrappers and refuses on unsupported backends. LevelDB checks its actual open owner/weak capture, rereads the six fixed raw records, exact-compares them with the fresh capture and one recorded alternative, and recomputes the matching digest. Requalification itself performs no Write/Sync, repair, database creation or target replay and makes no durability claim.

The new private recovered capture retains its newly observed `records` separately from the immutable `recovery.source/target` descriptor. The frontend likewise retains `fresh`, original `source`, and original `target` separately. It accepts the backend result only when fresh/original/target values match the original held state and descriptor. `CopyFreshRecords`, `CopySourceRecords`, `CopyTargetRecords`, `IsRecoveryQualified` and `RecoveryDescriptorSha256` expose factual native observations for the controller. Unqualified recovery does not expose fresh current values as original source and cannot validate as a usable source lease.

Commit is refused for every recovery request at both frontend and actual backend, including the legacy one-shot commit path. The existing same-owner retained Readback can perform a real empty-batch sync and exact raw read without changing those keys. Only after that known observation can retained Restore write the immutable original records to the six fixed keys and obtain actual sync/readback. Unrelated entries are never in the batch. An unknown physical result clears its proof; another restore requires actual same-token readback first. The original capture weak ownership is preserved, so intervening ordinary backend operations still invalidate it.

A lost callback retains the original request, actual pending/qualified phase, descriptor correlation and opaque capture through the A10b owner state. A failed/mismatched recovery remains explicitly held and unqualified; it neither silently releases nor reruns the original target. Recovery release requires the current exact extension/backend route and actual synced original-source readback. It records a distinct finite `recovery_source_released` correlation with request/descriptor SHA, rather than incorrectly classifying restoration as a generic no-target Begin abort. That receipt is a past release observation, not current writer readiness.

The native controller must load the actual verified journal from the retained native authority, join the actual Profile/epoch/generation and immutable intent, and require the stored source/target/descriptor fingerprints before calling this API. Its future intent writer must call the shared helpers and record those fingerprints before target writes. Old journals missing required facts must refuse automatic recovery; recomputing a convenient descriptor from unverified/partial data is not authentication or a replacement for missing journal evidence. Root/navigation own this actual caller/load path. No page API or Mojo binding to the frontend entry is added.

`source-plan.json` records actual beforeimages and counted overlays, and `native.patch` replayed and reversed in an isolated source mirror. `dependency-pins.json` pins the paired A10/A10b owners. `gn-request.json` asks the root integrator to add the actual `//crypto` dependency for the shared SHA helper; root owns that exact shared-file change and native generation/compilation. No compiler, native API/product, signing, owner-state or provider operation ran here. Source checks are not runtime acceptance or startup activation. Actual changed-owner compilation, verified native journal/caller integration and bounded disposable recovery observation remain required.
