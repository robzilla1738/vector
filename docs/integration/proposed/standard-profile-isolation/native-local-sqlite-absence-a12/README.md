# Exact Local SQLite absence cleanup

This fixes a real existing database-owner ordering error. `maps.row_id` is allocated by SQLite and looked up by the unique actual storage key. `map_entries` has no foreign key or cascade. The previous deletion removed metadata first, so `FindMapId()` returned absence and skipped the actual raw rows. The successor looks up and deletes those exact rows before deleting metadata, inside the existing transaction. A failure rolls both operations back. Caller shape, schema and UI stay unchanged.

One native source file, two counted anchors, pinned to the actual current native bytes. `project.py` emits the overlay and manifest; `check.py` verifies exact replay/reverse/whitespace plus three bounded synthetic checks using the actual pinned SQL: the previous ordering leaves rows, rollback restores both tables, and the corrected ordering removes only the actual target while preserving an unrelated map. These checks do not execute the native product or access owner data. Root owns compilation and integration.

Local absent-map creation remains explicitly refused by the A11 Async owner. The actual `UpdateMaps()` calls `PutMapMetadata()` to allocate an AUTOINCREMENT row and resolves its identity privately, but returns only `DbStatus`. The pre-attempt target digest cannot truthfully predict that ID. A complete successor must persist an explicit allocation action keyed by the native captured storage key, bind the actual unique allocator/readback result, prove unrelated metadata unchanged, and record that physical target observation before publication. This patch provides the genuine exact deletion primitive needed by that recovery; it does not claim creation or restart recovery.
