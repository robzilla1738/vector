# Extension preference backend migration

This is a native backend implementation proposal for the three existing Chrome-local preference families: color scheme, capture enabled and Tidy Tabs prompt. It does not change UI, ordinary storage semantics or the accepted app. `project.py` contains count-checked edits to two original Chromium files; `source-plan.json` pins both originals and outputs. The native checkout remains unchanged.

The backend capture reads only the six old/new keys directly from an already open LevelDB. It never calls the ordinary read/open/recovery helpers, which can delete malformed values or repair/recreate a database. Malformed supported values, conflicting targets, unavailable storage and failed reads refuse without modifying data. The prompt length retains the supplied JavaScript UTF-16 counting rule.

A private capture belongs to its live backend instance. Ordinary ValueStore reads and writes invalidate captures, including reads that can invoke original corruption recovery. Commit consumes the capture, compares all six raw values again, and writes the new keys plus legacy-key removals in **one LevelDB WriteBatch with `sync=true`**. Original JSON bytes, explicit `false`, and all unrelated keys are retained. Existing equal targets are supported; unequal raw representations conservatively refuse. Even an empty retry requests sync. A failed write/sync is an unknown outcome, never completed migration; the native owner must requalify recovery before recapturing. This does not repair, reset credentials or delete an old profile.

The changed backend actually compiles against its real Chromium target command. `actual-compile-a2.json` records the object, dependencies and unchanged original inputs; object SHA256 is `6a9307478b8c265ba64d1578c51706ce21b3b99f5dee4433909b6dd37758d7cf`. The first compile found Chromium's requirement for complex constructors/destructors to be out of line. Its failure, command, producer and exact edit plan are retained; the successful compile keeps the original compiler policy intact.

Five focused native fixtures cover reopening/idempotence with capture disabled, target conflicts, non-destructive corrupt-record refusal, stale/foreign captures and unopened-store refusal. Their object compiled using the real headers/compiler; **the fixtures have not linked or executed**. `actual-test-compile-a1.json` records only that compilation. No database or browser ran for these checks.

Still required: an authenticated native profile/epoch owner, original Aux extension/backend selection, writer quiescence, an importer that journals and commits this store together with DOM/page storage, interruption recovery, integration into the native build and actual disposable acceptance. There is no renderer/extension migration endpoint or startup acceptance bypass. Neither these methods nor a synchronous LevelDB result constitute complete-profile or multi-store migration. The latest inactive app does not include this source; no new signing or lifecycle authority is inferred.
