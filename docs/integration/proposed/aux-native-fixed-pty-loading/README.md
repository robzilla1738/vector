# Supplied PTY image: fixed embedded successor proposal

Current supplied daemon lazy loading conflicts with the finite signed image guard. `loadNodePty()` runs only from `spawnPtyProcess()`: it first tries package resolution relative to daemon code, then two executable-relative fallback packages. `lib/index.js` initializes `lib/unixTerminal.js`; that calls `utils.loadNativeModule('pty')`, trying build/Release, build/Debug and platform/architecture prebuilds. The arm64 supplied module is Node-API (`napi_register_module_v1`, `node_api_module_get_api_version_v1`), not legacy V8 registration. It imports only system libc++ and libSystem. A `dlopen` used for native image preparation does not invoke the JS package or spawn a terminal; subsequent real Node require is still needed for each Environment's exports.

Current sealed policy `AuxSignedFreshBootstrapPolicyLoader.images()` refuses all non-system images outside exact host/PDF/macOS-utility paths. Loading this actual arm64 PTY later therefore makes the next genuine authority revalidation fail. Ignoring an unknown image, permitting arbitrary future loads or treating failed revalidation as success would conceal the defect. The snapshot contains no other additional native daemon addons: only original common addon and arm64/x64 PTY; node:sqlite is builtin. Local-memory ONNX runs in its own executable process and does not justify admitting an ONNX image into the daemon.

The concrete transform requires explicit `embedded-daemon-arm64-v1`, whole-original SHA and exactly one original paired function block. It changes only embedded successor loading: one fixed executable-relative package and no current/project fallback; rejects unsupported targets; requires the already sealed helper to be executable instead of chmod of a root-owned installation. It leaves the supplied package/native API, terminal structure, shell arguments, environment, PTY dimensions, streams, callbacks, exit handling and UI untouched. It is not integrated into ordinary accepted adapters or current package, whose behavior remains unchanged. The composed text must still contain the exact pinned pair or transformation refuses.

`unixTerminal.js` passes the derived `spawn-helper` path to native `pty.fork` with file/args/environment/cwd/dimensions/uid/gid/UTF8/onexit. This helper is a separate child executable, not a dyld image of the daemon. It needs its own exact resource-seal and execution-role signature validation, root-owned namespace/FD custody and lifecycle tracking before fork; admitting pty.node does not admit arbitrary executable children. Both fixed arm64 files currently have original identifier `pty` / `spawn-helper`, team `8CPD4K4TBB`, Developer ID At Inc.; their exact bytes, public signatures and system dependencies are captured in inventory.json. These are historical source facts, not Aux trust approval. They cannot satisfy current Aux-only signed-image requirements. No new signing or trust exception is implied.

Smallest remaining coordinated integration: authenticate and retain the two fixed resource files under the actual root-owned sealed bundle; choose an explicitly reviewed Aux PTY/helper artifact identity (or separately approved exact third-party identity), not generic same-team trust; add one exact arm64 PTY image to a distinct signed policy successor while preserving older formats; load only that held fixed path before complete image capture; require same actual Node-API image through this fixed package; validate the helper's separate execution role before native spawn. Package JS resources must remain sealed and all fallback build candidates absent or rejected by exact guard. Current native PTY child lifecycle is not the existing PDF/OS drain and must be included in future actual writer/descendant closure; no whole-writer custody claim is made.
