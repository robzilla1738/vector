# Inactive fixed crypto assets and guarded entry preload

This external preparation closes two concrete source-integration gaps: review-relative runtime imports could not be copied into the application, and prepended static ESM imports would evaluate modules before state2's existing refusal. No shared staging, pipeline, launcher, native registration, UI, owner state or admission behavior is changed.

`materializeAuxCryptoRuntimeAssets({mode})` returns four fixed source descriptors and hashes for either actual application layout:

- SEA: `apps/daemon/Aux Daemon.app/Contents/Resources/aux-crypto/`
- Node development: `apps/daemon/Aux Daemon.app/Contents/Resources/node-development/aux-crypto/`

The exact CSK and corrected live-purpose module sources are pinned; only their precise project-relative dependency specifiers become fixed sibling imports. `aux-dk-crypto.mjs` is a pinned source-prefix projection of the actual Aux crypto helper, exposing only format/subkey/blob functions needed by the consumers; unused wrapping/migration functions and their extra builtin imports are excluded. `aux-json-tokens.mjs` projects only the actual bounded parser, excluding the external fixed-offset mutation helper. There are no external legacy importers in this graph. Outputs contain no original product bytes or upward/project-relative paths. Returned modes are0644, matching existing packaging source descriptors; the fixture writes actual output bytes into its own private disposable directory.

`prepareAuxCryptoRuntimeEntries(originalBinary)` parses the exact supplied static SEA binary without executing it. It uses the **actual** `adaptDaemonCode` and `buildDaemonNodeDevelopment` implementations, pinning the generated node entry and unchanged original asset inventory. The supplied SEA input has flags25 and ESM source; node development is an actual `.mjs` entry on unchanged Node. It returns prepared SEA source plus its fixed assets, and the actual generated development files with the one entry replaced plus four new fixed assets. It does not inject a Mach-O binary or claim native SEA execution.

`composeDeferredAuxCryptoEntry` applies the three proposals' exact function/schema edit tables directly to whole-hash-pinned real guarded SEA and node-development inputs. It deliberately does **not** use their old static import prefixes. The exact existing `AUX_COLD_ENTRY_REFUSAL` stays the first executable statement and appears once. Only **after** it, a top-level awaited preload establishes the synchronous CSK/live consumer bindings before any original initializer body. The existing node-development `assets.mjs` dynamic import also remains after refusal. No ready/cache/admission flag or caller-controlled runtime module URL is introduced.

SEA's deferred base URL uses builtin `node:url` plus actual `process.execPath` to resolve the fixed `../Resources/aux-crypto/` directory. Development uses its real entry `import.meta.url` and fixed `./aux-crypto/`. Dynamic imports select only the two fixed consumer modules; those modules statically import only their fixed app-contained dependency siblings and Node builtins. This handles synchronous helpers through **asynchronous entry preload**, not an uninitialized mutable shim. The macOS-only check remains after quarantine refusal and before asset preload.

Focused check: `node --experimental-vm-modules docs/integration/proposed/aux-crypto-runtime-assets/tests/check.mjs <explicit frozen daemon binary path>`. It constructs the actual two full prepared entries, parses/links their static builtin imports using inert builtin stubs, and evaluates only their existing immediate quarantine refusal. The four actual rewritten assets are physically materialized, parsed and linked without body evaluation, proving sibling/export inventory and syntax without repeating any CSK/cipher/credential fixtures. No daemon/native/helper/OS/provider launch occurs.
