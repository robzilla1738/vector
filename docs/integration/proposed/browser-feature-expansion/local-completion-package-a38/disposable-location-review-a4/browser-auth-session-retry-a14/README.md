# Renew a consumed authentication challenge after terminal session failure

Actual A15 logs show an installation-authorization failure followed by repeated HTTP401 session responses every second. The supplied server removes a challenge before public-key verification/token issue. The native browser stores a completed signature until success; after a terminal failed/lost session response it currently keeps that consumed challenge and resubmits the same proof forever. A first HTTP timeout is plausible but not established by the logs, and no claim is made that A72 changed signature verification.

This single counted anchor changes only `DidReadSession`’s invalid/unsuccessful terminal callback. For the adopted native child, after actual native signing has completed and no sign RPC is in flight, clear that completed id/challenge/signature cache. The existing failed-state retry can then fetch a new server challenge. A pending native operation is never replaced or replayed: ObserveNativeSignature and DidObserveNativeSignature retain their existing exact nonce/body/callback fences unchanged. Unknown HTTP outcome grants no token or readiness. All server challenge TTL/signature checks, native code/root authority, success parsing, token authorization, one-loader serialization and the non-adopted signing path remain unchanged.

The pure source check verifies exact forward/reverse replay, the completion/no-inflight guard, and that Authenticate/ObserveNativeSignature/DidObserveNativeSignature/DidSignChallenge and the successful session body stay exact. No key, ciphertext, profile or owner state is read/reset/migrated. No native tree mutation, compilation, signing or app action occurs in this lane. Root owns actual compiler/build and one supported authentication/Quit observation; the previous failed runtime remains failed.
