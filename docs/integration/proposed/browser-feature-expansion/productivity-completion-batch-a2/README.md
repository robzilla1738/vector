## Concrete fixes

- **Unknown rename/Undo recovery:** a physical `FAILURE_UNKNOWN` keeps its durable `planned` or `undo-planned` phase. The previous code converted it to `failed`, which the actual `RecoverPending` scanner skips, even when the file might already have moved. The response and existing Files UI now explain that the prepared rename needs recovery rather than claiming failure or an active background check.
- **Exclusive move completion:** the actual move stays within one retained parent-directory FD using `renameatx_np(...,RENAME_EXCL)`. It verifies the expected source identity, observes the moved destination and missing source, syncs and revalidates the named parent before success. Existing destinations are not overwritten. Post-move readback, sync, parent change or revoked authorization returns unknown and preserves the prepared record. Recovery inspection also syncs the parent before reporting a move complete. Original fingerprint fields and file bytes are unchanged; no original credentials or installation formats are touched.
- **Fingerprint preflight and refused recovery work:** rename preparation now retains the existing native file-operation ticket through its background metadata read/reply. A definite ThreadPool non-start returns the one refused response via `SplitOnceCallback` and settles only that refusal. A recovery inspection that cannot start retains an uncertain prepared recovery state rather than treating its incremented last index as completed. Ticket settlement retains the exact lifetime object across observer callbacks that can publish the next owner.
- **Chosen-file drag:** the paired helper receives the actual profile and a native callback over the real record/owner epoch. Path/fingerprint data are copied before entering Cocoa. Weak actual BrowserView/window/profile binding, record identity and file metadata are rechecked across `ReleaseCapture` before starting the drag. A profile/window/record change stops the original action. No renderer-selected profile, arbitrary path, extra file-content read or OS grant is introduced.
- **Referenced-tab CDP sessions:** session bindings retain the original selected document URL/capability and profile route. Removing or changing the live attachment cannot silently turn its existing session into an ordinary read or rebind it to a new document. Early child-session events inherit the pending real parent binding. Previously ordinary sessions upgrade when they become explicitly selected context. A stale session attempts cleanup of only its actual owned root session, retaining the guarded binding on lost cleanup until the real native detach event; the supplied SessionManager can then evict its page-session cache and attach anew. Retiring bindings never revive just because a record reappears.
- **Admission races:** bridge routes are copied before asynchronous validation, so mutating the same route object cannot conceal a profile change. Queue drain also compares the captured tab-reference values; in-place attachment changes cannot bypass the existing object/array-identity checks. Failed validation preserves queued messages.

Default UI/style/classes, geometry, fonts, icons and artwork are unchanged. The only UI wording change is the honest prepared-rename recovery status. The existing SDK/native services remain the producers/consumers; no competing file or tab store is added.
