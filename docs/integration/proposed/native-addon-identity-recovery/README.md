# Original native addon: bounded identity recovery

Read-only investigation of the two exact frozen supplied addons; no target was loaded or executed, and no binary, owner data, Keychain, signing authority or running analysis job was changed. This evidence is outside the delivered app.

## Inputs and limits

`static-map.json` pins the original daemon (`bfe946e05fbaf2ae68d0560258f50e63a6c3ff6da2937e0aa8f9f19016e1f7fb`) and original CLI (`66368b6846d2842a5ee0ba3d5c6d5d094fd40098d7819dbb63ef17600c85c3fc`) binaries under the project-owned `out/provided-source-snapshot-1.26.1016.1852`. These are distinct original binaries, not a transformed copy of one another.

The prior bounded source inventory found no original Swift source, matching `.swiftinterface`/`.swiftmodule`, dSYM payload, or addon build project in the authorized downloaded/static package inputs. `recovered-cpp` reconstructs 2,392 Chromium UI functions rather than this addon. The binary itself has symbols and Swift reflection metadata, but no `__DWARF` section. Source absence remains scoped to these inputs.

REA `open_binary` verified the daemon SHA; `inspect_macho` retained evidence `ev_b3add60f32a74cb4da5ed6cfa5e9e9fbcd612204f943f03d273f265e5b26c7e3`, UUID `6146EB76-0AEC-3044-BCFA-B9B630222453`, SDK26.5/minimum macOS13.0. REA's native decompiler provider is unavailable: installed Ghidra12.2 is outside its supported12.1.x line and its current JDK21 is below the provider's JDK25 requirement. Hopper is absent. No provider repair/install or new full analysis was attempted. The attached assembly is ordinary Xcode LLVM output, not REA pseudocode or recovered original source.

Daemon C export `_AsideNativeRun` at `0x49af8` branches to the Swift body, which converts nullable C strings, calls original command dispatch at `0x48eb4` (`0x49b6c`), obtains the output C string with `strdup` (`0x49ba4`), and returns it. `_AsideNativeFree` at `0x49bd4` and its Swift body tail-branch to `free` at imported stub `0x51546c`. The install service, metadata/signing/agreement/DK account initializers pass suffixes `install`, `install.meta`, `install.sig`, `install.kem`, `dk` through the same merged Swift initializer at `0x30954`. At `0x30998..0x309c8` it builds either `aside-canary.` (13-byte small string, discriminator byte `0xed`) or `aside.` (6-byte small string, `0xe6`) in ARM64 MOV/MOVK immediates, then calls Swift `String.append` at `0x309d8`. These selectors are generated by instructions; a raw ASCII inventory does not find their final strings.

The wrap-context initializer at `0x30a60` independently builds the same prefix and appends `wrap.dk.v1` (10-byte suffix, `0xea`), then converts UTF-8 to Foundation Data (`0x30aec`) and stores it at global `0x744e88`. The resulting normal label is `aside.wrap.dk.v1`; neither addon contains that complete contiguous byte string. Its length and encoding are semantic inputs, not an inert display label.

Original installation initialization uses that global as HKDF sharedInfo at call `0x36050` to CryptoKit's imported `hkdfDerivedSymmetricKey` stub `0x514218`, with output byte count32. Original unwrap uses the same global for HKDF and for ChaChaPoly authentication. The attached unwrap assembly shows the authenticated-open calls at `0x3f32c`, `0x3f69c` and `0x3fb00` to stub `0x5141ac`. Renaming the context without explicitly rewrapping/authenticating old ciphertext would break existing installation state.

Actual unwrap branches call the CryptoKit Secure Enclave MLKEM768 key initializer at `0x3c3f0`, decapsulation at `0x3d000`, software P256 agreement at `0x3d554`, and Secure Enclave P256 agreement at `0x3d614`. This is observed call-site evidence, not proof that any branch executed or that a fallback is safe. Preserve all original schemes and key storage semantics.

Original `installBaseQuery` loads the service global at `0x32c54`, stores the supplied account String at `0x32c80`, loads `kSecAttrAccessGroup` through GOT `0x724070`, and loads `kSecUseDataProtectionKeychain` through `0x7240e0`; the DP value is true. Any new selector or authority migration must preserve the current reviewed fixed Aux scope and cannot manufacture entitlements.

## Why a blind brand patch is insufficient

The module name occurs in Swift mangled symbols (`$s16AsideNativeSwift...`), an actual module descriptor and other metadata, plus dynamic exports and the Mach-O install name `@rpath/aside-native.node`. The map records610 daemon and618 CLI raw module-name occurrences, including symbol strings; these counts are not a patch list. Renaming the module to `AuxNativeSwift` changes its mangled byte-count prefix from16 to14. Export trie, symbol table string offsets, relative Swift metadata references and load-command lengths need format-aware rebuilding or a faithful recompile. Shorter ASCII bytes alone are not sufficient.

The finite next actions are:

1. Recover the remaining original installation read/write, wrapped-record serialization, per-scheme key import and error paths from the named addon functions. Keep the exact current function bodies and CryptoKit calls as reference, including PQ/enclave behavior. The selected disassembly narrows this work to the actual addon instead of the much larger Chromium framework.
2. Produce a reviewed versioned selector and wrapping-context migration that uses the original private authority to authenticate/decrypt old records and rewrap the same DK under an explicit new Aux format. It must be retryable, non-destructive and use disposable fixtures first. No old key may be reinterpreted under a new label, regenerated to hide failure, or read without authorization.
3. Choose a source-faithful rebuild or a complete format-aware Mach-O identity rewrite only after Swift metadata/export/relocation coverage is established. An instruction-aware patch would need both normal/canary prefix values and Swift length discriminators at every real construction site; a generic string substitution cannot provide this. That is preparatory work, not permission to alter current binaries.
4. Coordinate the new C exports with carrier dlsym callers, NAPI clients, native role hashes, packaging receipts and explicit migration adapters. Preserve original crypto primitive implementations, schemes, wrapper formats until their versioned transition, and the accepted app/UI.
5. Verify actual disposable native migration and private-authority behavior only after a concrete exact-byte signing/Keychain review is authorized. Compile, symbols and source fixtures alone do not prove it.

No deployable successor addon, complete original-source recovery, binary patch, migration execution or runtime acceptance is claimed by this investigation.
