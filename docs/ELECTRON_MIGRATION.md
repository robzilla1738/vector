# Electron Aux → Chromium Aux migration handoff

The host-neutral preparation step is `prepareElectronMigration` in the runtime package. It reads the Electron Aux data directory and creates a **new** standalone bundle. It never opens the source for writing, copies a consistent SQLite snapshot with `VACUUM INTO`, and never reads or copies Chromium/Electron Cookies, Login Data, Web Data, Keychain material, browser profile files, or OS credentials. The source app and profile remain usable.

## Preparing a bundle

1. In the Electron Aux app, open **Settings → General → Task data backup** and choose **Export layout for Chromium migration…**. This saves the current Space, folder, pin, split, tab order, and tab label layout as JSON without changing the profile.
2. Unlock **Connections → Vault**, enter a new 12+ character transfer passphrase, and choose **Export credentials…** if credentials should move. The `.auxvault` file is a separate AES-256-GCM package; the migration bundle contains no vault metadata or secrets. Use a different transfer passphrase from the vault lock passphrase and keep both files private.
3. With the source app closed or quiescent, build the current runtime (`pnpm build`), then run:

   ```sh
   node scripts/migrate-electron-profile.mjs --source "$HOME/Library/Application Support/Aux Browser" --output /path/to/new-aux-migration --layout /path/to/aux-layout.json --dry-run
   node scripts/migrate-electron-profile.mjs --source "$HOME/Library/Application Support/Aux Browser" --output /path/to/new-aux-migration --layout /path/to/aux-layout.json
   ```

   `--layout` can be omitted for older profiles, but the report sets `omitted.layoutMissing=true` and only DB Space metadata is available. The report includes counts for migrated and omitted tabs, bookmarks, artifacts, and vault metadata. The output directory must be new and outside the source data directory. A matching rerun returns `alreadyPrepared=true`; a conflicting or damaged output is rejected. Dry run creates no bundle.

The private bundle contains `manifest.json`, `aux-state.sqlite`, and bounded copied artifact files. The copied database retains tasks, conversations, history, bookmarks, Spaces, and available saved artifacts. It drops browser target bindings and live tabs, disconnects old sessions, cancels unfinished runs and pending messages, pauses routines, clears outstanding action intents to `uncertain`, strips host-bound grants/tokens and vault metadata, removes protected article recall, and omits download records and files. Missing or unsafe artifacts are marked unavailable. The manifest contains only HTTP(S) tabs/bookmarks/pins without URL credentials.

## Native apply contract (manifest version 1)

The Chromium host must **not** treat bundle metadata as commands. Before use, parse `ElectronMigrationManifestSchema` and reject unknown versions, wrong paths, oversized files, symlinks, duplicate identifiers, or any failed SHA-256 check. The `contentHash` is SHA-256 of the JSON serialization of `{sourceSnapshotSha256,databaseSha,layout,tabs,bookmarks,bookmarkFolders,artifacts,omitted}` in that key order, using the field order and values returned by `ElectronMigrationManifestSchema.parse`; `createdAt` is intentionally excluded. The source snapshot hash is provenance for the pre-scrubbed Electron runtime state. `database.sha256` and each artifact SHA-256 cover the actual files the native host will read.

Apply only to a newly selected Chromium profile, under a migration lock. Use the copied runtime DB as the initial runtime state (after the current runtime's schema migration if needed), then create native browser tabs from `tabs` and import bookmarks/folders via native APIs. Use `sourcePageId` only as a translation key to new Chromium page IDs; do not reuse Electron target IDs or controllers. Preserve each tab's `spaceId`, `folderId`, ordinal, active state, and reviewed label after translating IDs. Map `layout.activeTabs` and `layout.splits` through the same translation; drop references whose source tab was omitted. Import Space records by stable `id` and `workspaceId`, respecting archived state, color, optional grain, pins, folder metadata, active Space, and split ratio. Upsert bookmarks by URL so the same manifest cannot duplicate them. No cookies, sessions, saved browser passwords, extensions, or download files are imported.

The host-neutral destination step verifies the manifest schema and content hash, database and artifact byte counts and SHA-256, copied Aux SQLite marker/schema/integrity, tab references, and an optional `.auxvault` package's passphrase and AEAD tag. It copies the database and artifacts into a **new, isolated** profile data directory, changes only copied artifact paths, and atomically renames the staged directory into place. It writes `apply-receipt.json` with the source content hash and destination DB hash. A matching verified seed is an idempotent no-op; a changed or unmarked destination is rejected. Staging failure removes the stage and leaves the destination absent. The bundle and Electron source remain untouched. Hashes detect corruption; they do not authenticate the source profile.

After building the runtime, apply with:

```sh
node scripts/apply-electron-migration.mjs --bundle /path/to/new-aux-migration --profile "/path/to/new-chromium-profile/Aux Runtime Data" --dry-run
node scripts/apply-electron-migration.mjs --bundle /path/to/new-aux-migration --profile "/path/to/new-chromium-profile/Aux Runtime Data"
```

If transferring credentials, set a transfer passphrase in a private environment variable and add `--vault /path/to/credentials.auxvault --vault-passphrase-env AUX_VAULT_TRANSFER_PASSPHRASE` to the apply command. The passphrase is never passed as a command argument or written to the profile. The sealed package is copied to `vault-transfer.auxvault`; `apply-receipt.json` marks it `pending_native_import`. The native host must perform explicit OS-backed vault import after the new profile is ready, record its own completion receipt, then remove the staged package. It must not mark vault import complete on partial failure. Existing credentials are skipped by origin, username, and label. The offline seed never creates plaintext or simulated keychain secrets.

Stage the seed before the new Chromium Profile's first Aux runtime launch. In **Settings → General → Task data backup**, choose **Review Chromium migration…**. The trusted shell shows the manifest digest, imported counts, and omissions. Confirming creates a private native journal and imports bookmark folders, bookmarks, and tabs in 100-item batches. A restart replays those idempotent batches from the beginning; the same manifest and Profile are required. The importer assigns new Chromium page IDs from the manifest digest and source IDs, then translates Space, folder, order, active-tab, split, and pin references into the Profile organization store. Imported bookmarks live under a clearly named **Imported from Aux** folder, retain nested paths, reading-list state and creation dates, and are never allowed to replace existing Profile bookmarks. A native completion receipt is written only after tab, bookmark, and organization verification. A matching receipt is a no-op. An interrupted import can be resumed or explicitly rolled back; rollback refuses to remove bookmarks edited since the import. The offline seed's `apply-receipt.json` is not a native completion receipt. The 256 KiB native layout limit currently permits at most 5,000 tabs and 1,000 tab folders in one browser window; larger prepared manifests are rejected before import. Keep the destination Profile at its chosen path because artifact paths in the copied DB are absolute.

The seed receipt now contains `manifestSha256`, the digest of the exact staged `manifest.json` bytes. Chromium checks that digest before review, and every later operation is bound to the reviewed `contentHash` and `manifestSha256`. Native import never reads or copies the Electron source Profile. The sealed `.auxvault` stays pending; a separate OS-backed credential import is required before any vault receipt can be marked complete.

## Verification

`tests/unit/electron-migration.test.ts` and `tests/unit/electron-migration-apply.test.ts` cover both sides with copied fixture profiles, source preservation, destination artifact relocation, hash/AEAD failure, rollback, and idempotency. `tests/unit/migration-import.test.ts` verifies the reviewed native batch lifecycle, including an interrupted run. Chromium's `migration_import_unittests` validate bounded, safe manifest URLs and references. `tests/unit/human-vault.test.ts` covers encrypted vault round-trip and duplicate imports. For a real disposable source copy, run `node scripts/rehearse-electron-migration.mjs --source-copy /path/to/copied-electron-data --source-original /path/to/original-electron-data [--layout /path/to/aux-layout.json]`; it rebases artifact paths **only in the disposable copy**, builds a temporary bundle and profile, checks the copy's DB hash and repeat apply, then removes the temporary bundle/profile. Omit `--source-original` when artifact paths already point inside the copy. A live Chromium Profile import, restart/resume, and rollback remain release gates until the patch is built into the signed app.
