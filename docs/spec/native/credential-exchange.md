# Native credential exchange

Status: **ready** for the OS entry flow, supported data categories and session behavior below; real ad hoc app eligibility, OS chooser registration, private helper transport and actual end-to-end import remain **draft**. Sources VF6–VF8 in `../provenance.md`. No source credential export, helper launch or owner profile access occurred.

## Public OS flow

Native exchange is distinct from selecting a CSV or JSON export. On macOS26or newer, the source password manager begins an AuthenticationServices export. System UI explains the operation and asks the person to select a receiving app. The OS brokers the exchange and launches the receiver with an activity containing an opaque UUID import token. The receiver passes that token to `ASCredentialImportManager.importCredentials(token:)` and consumes the returned `ASExportedCredentialData`; it must not simulate a successful OS exchange from a file chooser. Apple documents this process as not writing exchanged data to the filesystem. [Apple import manager](https://developer.apple.com/documentation/authenticationservices/ascredentialimportmanager), [Apple export manager](https://developer.apple.com/documentation/authenticationservices/ascredentialexportmanager).

The receiver needs a credential-provider extension declaring exchange support and format version1.0, and its host app declares the credential-exchange user activity. Apple's public capability instructions require the AutoFill Credential Provider entitlement on both host and extension. These are public OS identifiers, not product-owned names. Aux supplies independent app/extension identities, usage text and helper binaries. Merely adding entitlement text to an ad hoc signature does not establish OS eligibility or registration; test that boundary in an isolated environment before claiming it works. No Developer ID signing, provisioning or release is authorized by the local rebuild plan. [Apple entitlement](https://developer.apple.com/documentation/bundleresources/entitlements/com.apple.developer.authentication-services.autofill-credential-provider).

## Data mapping

OS credential data contains accounts, collections and items; an item may carry multiple credential kinds and scope URLs. Preserve supported display metadata, URLs and notes without copying reference serialization. Password records need username/password values plus optional display title/subtitle and URL. Unsupported categories must be reported explicitly instead of being counted as imported.

Passkey data includes credential ID bytes, relying-party identifier, user-name/display-name, user-handle bytes and private-key bytes. Apple's public key representation is PKCS#8; JSON encoding uses Base64URL for these bytes. Feed imported private keys through independently implemented cryptographic validation and encrypted private-passkey storage, not ordinary login notes or public snapshots. Import only algorithms the actual authenticator can use, reject inconsistent/unsupported curves and malformed keys, and preserve a counter/creation time only if supplied and valid. Reference static conversion accepted P-256 PKCS#8 and JSON-key representations, but that does not justify accepting arbitrary unvalidated JSON keys. [Apple passkey type](https://developer.apple.com/documentation/authenticationservices/asimportablecredential/passkey), [Apple key format](https://developer.apple.com/documentation/authenticationservices/asimportablecredential/passkey/key).

The helper-to-daemon transport is an independent Aux design. It must bind a one-use import authorization to the selected local account/profile, destination Vault and active session. Caller-provided account/profile paths alone are insufficient authorization. Keep credential bytes out of logs, status/error metadata, clipboard and generic agent transcripts. Do not write an intermediary plaintext export as a substitute for the OS handoff.

## Session and progress

Starting import creates one active session for the selected account. It begins waiting for the source export. A new session cancels an earlier unfinished one. Public status distinguishes waiting, importing, success, failure, cancellation and timeout; metadata includes creation/update/completion times, total password/passkey counts and completed counts. During import, stages cover destination preparation, metadata resolution, key normalization and record creation. Optional display-name lookup must not disclose credentials; local-only operation may derive names locally.

An unfinished session expires after ten minutes without a progress update. Terminal-session status is retained for about24hours after its last update. Cancellation prevents subsequent steps and retires only verified Aux-owned helper processes. Late callbacks for cancelled/expired sessions must fail without writing records. Resolve the exact selected account/profile and require an unlocked selected destination before beginning and before each committed batch. A missing destination, lock, invalid key, OS denial or unsupported OS yields an actionable failure, never a successful zero-count placeholder. Retry must not silently multiply existing records.

Completion follows actual durable item acceptance; count passwords and passkeys separately. A locked Vault after the OS chooser must request unlock and revalidate session authorization before import resumes. Status reports contain no secrets. Clearing helper context after terminal state must not affect another account's import or unrelated OS application.

## Acceptance boundary

Verify with disposable source credentials and an isolated destination: OS lists the independently identified receiver; user activity carries a real one-use token; password and real ES256 passkey import produce usable encrypted records; cancellation/timeout/lock/navigation or account switch reject stale callbacks; retry deduplicates; helper retirement preserves unrelated processes. A mocked callback proves only normalization/transport behavior. OS eligibility, actual entitlement authorization and exchange interoperability remain unverified.
