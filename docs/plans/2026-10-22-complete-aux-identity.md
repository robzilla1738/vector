# Complete Aux identity, preserve the accepted UI

Active owner direction, 2026-10-22: “Everything that is currently pointing to aside or mentions them needs to be Aux. No trace of Aside or their brand anywhere”, followed by “while preserving our UI that we currently have - do not change that”.

This supersedes the earlier compatibility-name exceptions in the reuse plan. Reuse remains the implementation strategy. The accepted app stays intact during migration. This is an implementation migration, not permission to sign, inspect owner credentials, delete profiles, modify the installed reference product or activate production.

## Fixed visual baseline

Preserve current component structure, assets derived from the canonical Aux SVG, typography, spacing, glass, corner clipping, toolbar, sidebar transitions, chat panel and settings. No visual redesign. Compare CSS/font/image inventories byte for byte and observe the actual successor app before accepting it. Original static source and historical evidence remain unchanged and truthfully attributed. Standard HTML `aside` semantics and required third-party legal attribution remain intact.

## Implementation sequence

1. Inventory copied product payloads and native protocol surfaces. Categorize executable protocol names, persistence/crypto names, endpoints, identifiers, visible text and embedded residuals. Record hashes/counts without source snippets or secrets. The new read-only `scripts/audit-aux-identity.mjs STAGE NEW_REPORT.json` inventories an explicit generated supplied stage; it does not follow symlinks or claim compressed payload coverage.
2. Rename native/daemon/CLI/Agent session schemes, bridge schemas, dispatch prefixes, WebSocket authentication prefix, signed challenge domains, health identity, helper messages and diagnostics together. Derive challenge lengths from literals; the Aux HTTP domain including NUL is19 bytes, development domain23. Update injected commands after cloud composition as well as pinned supplied commands. A daemon-only or extension-only switch is not accepted.
3. Design versioned migration for installation records, HKDF domains, wrapped keys and cache identifiers. Verify with synthetic legacy/new fixtures before enabling. No blind string replacement of cryptographic inputs, silent fresh-key fallback, authority regeneration or deletion. Only disposable Aux state is authorized for runtime checks. If immutable native components retain embedded names, rebuild/adapt that boundary explicitly and report any unavailable source; do not overwrite arbitrary binary strings or misrepresent an inventory result.
4. Remove product links/update endpoints, product-named runtime paths, helper/bundle/extension IDs and metadata still present in the delivered package. Preserve third-party integrations and protocol standards. Repack embedded SEA/assets with recorded inputs and complete callers, not a text-only overlay. Source-only find strings and provenance live outside the delivered product and remain accurate.
5. Produce a separate unsigned successor with matching native and resource receipts. Audit actual packaged JS/SEA/native/PAK/compressed resources and file names, not just transform helpers. Do not reuse acceptance or signing receipts from older bytes. Any new signing request needs its own concrete exact-byte review.
6. Lean acceptance: parser/schema and auth-challenge fixtures, one disposable startup/handshake, profile switching and key-format migration, then real UI comparison and unchanged visual asset hashes. No paid provider call is needed for renaming. Record implementation versus runtime gaps honestly.

## Current evidence and gaps

The existing accepted desktop app is unchanged and still contains compatibility spellings. No full identity migration is activated. The first inventory runs against `out/provided-reuse-cloud-cookie-restore`, an intermediate unsigned resource stage; it is not a deliverable or accepted runtime. The read-only report is `out/aux-identity-baseline-2026-10-22.json` once its scan finishes. It deliberately reports `complete:false`: raw counts can overlap and cannot prove embedded/compressed/native absence. Native cookie recovery work is a separate prerequisite and adds no UI changes.

The prior pipeline explicitly restored compatibility names after branding. Removing that behavior alone would break native receivers and existing stored data. Keep the working product intact until all dependent changes above form a coherent successor. No “everything is Aux” or complete parity claim is warranted yet.
